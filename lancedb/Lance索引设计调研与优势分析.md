# Lance 索引设计调研与优势分析

> 调研对象：Lance / LanceDB 的索引设计，与本项目（openGauss + Iceberg 数据湖索引能力栈）的索引设计
> 调研目的：
> 1. Lance 索引设计有哪些优势；
> 2. 我们当前索引设计的优势（**不是与 Lance 严格对比**，双方共有、但确实是优势的点也如实列出）；
> 3. 相比 Lance 的索引设计，我们有什么相对优势。
>
> 说明：Lance 侧信息来自其公开文档 / 格式规范 / 第三方评测（来源见附录 4.1）；我方性能数据备注测试条件（附录 4.2）。推测性结论已显式标注。

## 一、Lance 索引设计概述与优势

### 1.1 Lance 是什么

Lance 是一个面向 AI / 多模态数据场景的**开源列式湖格式**（由 LanceDB 团队开发，Rust 实现，与 Apache Arrow 生态深度绑定）。它不是一个单一格式，而是一组相互配合的规范：文件格式、表格式、轻量 catalog 规范，以及索引格式。LanceDB 是建立在 Lance 之上的**嵌入式向量数据库产品**（无服务器、Python 原生），其底层存储引擎仍是 Lance。

关键设计取向：**索引是格式的一等公民**——索引与表数据存放在一起，随数据集共享，是"随数据走"的结构，而不是独立部署的服务。

### 1.2 索引设计：两层架构 + 量化

Lance 的向量索引是统一的两层架构：

| 层级 | 内容 | 说明 |
|---|---|---|
| 顶层：IVF 分区 | k-means 聚类，把向量空间分成若干分区 | 查询先找最近的 nprobes 个分区 |
| 底层：子索引 | 每个分区内的近邻搜索：**Flat**（线性穷举）或 **HNSW**（图搜索） | 决定分区内搜索方式 |
| 可选：量化 | **PQ**（乘积量化）、**SQ**（标量量化）、**RaBitQ** | 压缩向量体积、加速距离计算 |

由「分区搜索方式 × 量化器」组合出多种索引类型：`IVF_PQ`（默认）、`IVF_HNSW_FLAT`、`IVF_HNSW_PQ`、`IVF_HNSW_SQ`、`IVF_RQ` 等。

- **PQ 量化**：把向量切成 M 个子向量各自独立量化成码本索引；对 L2/Cosine 距离采用**残差编码**（量化"向量与分区质心的差"）。距离计算用两阶段查表（预计算距离表 → 查表+累加），压缩比约 8~32×。
- **构建流水线**（四阶段）：训练（采样训练 k-means 质心与码本）→ 按分区 shuffle（大表走磁盘操作）→ 并行构建各分区子索引 → merge 增量（新数据可复用已训练模型合并进既有索引）。
- **检索流程**：选分区（nprobes）→ 加载分区（带缓存）→ 子索引搜索 → 可选 `refine_factor` 重排（多取候选、内存重排，挽回量化丢的召回）。

### 1.3 索引存储：标准文件、随数据共享

- 每个向量索引 = **两个标准 Lance 文件**：`index.idx`（图结构 + IVF 元数据）与 `auxiliary.idx`（按分区排序的量化向量，带 `_rowid` 回溯原数据行），放在数据集目录下（`_indices/{uuid}/`）。
- 索引元数据存于 **Arrow schema metadata + 文件级 global buffer**（如 IVF 质心、分区偏移/长度以 protobuf 序列化在文件尾部的 global buffer 中）。文件自描述：从尾部 footer 即可解析出 schema 与各列的元数据。
- 因为是普通文件且随数据集目录存放，**索引可以和数据一起被共享**（例如直接放到共享数据集平台，另一方拿到的就包含索引，无需重建）。
- 索引文件走**内存映射 + 零拷贝**读取路径。

### 1.4 Lance 索引的优势（按层面）

**能力点层面**

1. **索引构建快**：IVF-PQ 构建天然便宜。第三方 7 引擎对比（FAISS/Qdrant/Milvus/Weaviate/Chroma/pgvector/LanceDB）中，LanceDB 以约为竞品 **11×** 的速度构建 SIFT1M 索引（约 43s）；RAG 场景小规模索引秒级完成，单位成本很低。
2. **磁盘驻留，无需全索引常驻内存**：内存映射 + 按需读，支撑百万→十亿级（宣称单节点 10–50B 行 / 10–30TB）数据规模。
3. **零拷贝随机访问**：Arrow 原生列式 + 小 fragment 布局，官方宣称随机访问比 Parquet **或 Iceberg 快约 100×**（Parquet 类行组格式对"随机取向量"不利），跨文件瞬时取单条记录。
4. **索引随数据可共享**：普通文件、随数据集目录走，免重建。
5. **索引类型丰富**：向量（IVF_PQ / HNSW 族 / SQ / RQ）+ 标量（BTree / Bitmap / LabelList / FM 子串）+ 全文（BM25），一套格式全覆盖。
6. **混合检索原生**：向量 + 标量过滤 + 全文搜索（BM25）可在同一数据集上组合，三类查询均有二级索引加速。
7. **原生多模态数据支持**：图像 / 视频 / 音频 / 文本 / 嵌入向量可与表格数据同格式存储，blob 编码高效处理大二进制对象并支持懒加载。
8. **高效数据演进**：回填列值（如补算 embedding）只需写新的 Lance 文件，不重写整表。
9. **GPU 加速训练（CUDA/MPS）、分布式索引**：宣称支撑 10B 级建索引。
10. **增量索引**：新数据 merge 进既有索引，复用训练模型，避免全量重建。

**设计层面**

1. **索引是独立于表布局的冗余数据结构**（官方格式规范的设计取向）：文件格式不受内置搜索结构的限制，**索引格式独立于表布局而发展**——索引优化 / 升级不触及底层数据。这对"索引格式可独立演进"提供了规范级依据（我们同样采纳了这一取向，见 2.2 共有优势）。
2. **索引即普通文件 + 按需 / 逐步加载**：官方规范明确"所有向量索引都存储为常规 Lance 文件，使其易于移植和管理"；数据集可在不加载索引的情况下打开，查询受益时才加载、且只加载必要的部分（如 BTree 先读小页表再定位具体页），冷索引查询成本被分摊；索引写入后不可变，可安全缓存；索引段可合并成比碎片更大的单位，减少查询期打开的文件数。
3. **类型 / 版本兼容机制**：引擎校验索引段的类型与格式版本，识别不了就跳过该段并**回退扫描**，允许索引格式随时间演进且保持向后兼容（向量索引格式已演进到 V3）。
4. **索引即普通文件、自描述、版本化**（`data_storage_version` 有稳定的长期兼容契约，未来版本继续读旧文件）。
5. **量化体系完整**：PQ 残差编码 + 距离表查表 + SIMD 友好的 transposed codebook 布局。
6. **预过滤 / 后过滤双模式 + 自适应 nprobes**：有过滤条件时从 `minimum_nprobes` 起扫，结果不足再向 `maximum_nprobes` 扩展分区；过滤掩码后台异步加载。
7. **列式按需读 + 行级掩码**（RowAddrMask：删除掩码 × SQL 过滤掩码），配合标量索引加速掩码计算。
8. **MVCC / ACID 版本化**：每次写入产生新版本，manifest 追踪。

**架构层面**

1. 格式 / 引擎 / 产品分层：Lance 格式 ← Lance 引擎 ← LanceDB，各层可独立使用。
2. 与大数据生态广泛集成：处理 / ML 侧（Pandas / Polars / Ray / PyTorch）、SQL 分析侧（DataFusion / DuckDB / Spark / Trino），并支持开放目录（Polaris / Unity Catalog / Gravitino / Hive Metastore）。
3. **embedded 免部署**：无服务器、库内嵌，Python 原生，起步成本极低。

**局限（如实列出，便于后续对照）**

- **默认配置召回率低**：多份独立评测显示默认 IVF_PQ 下 Recall@k 仅 0.15~0.48 档，需调参甚至换索引族（如调好的 IVF_FLAT）才能达到高召回；构建快很大程度是用召回率换来的。
- **单行更新（churn）吞吐低**：对比中约 2.6 writes/s（服务器型引擎为 144~149）。
- **嵌入式无 HA / 复制 / 数据库级权限**：权限仅是 OS 文件权限，持久性由宿主应用负责。
- **格式是目录结构**（非单文件），迁移成本高（数据需 re-embedding 成 Lance 格式）。
- 检索吞吐在服务器型引擎对比中偏低（磁盘驻留架构的代价，需高复用场景才划算）。

## 二、我们当前索引设计的优势

### 2.1 设计概览

我们在 **openGauss + Iceberg 湖仓**上为湖上 Parquet 数据补齐数据库式索引能力，构成完整链路：索引引擎（IVFPQ 向量索引 + BTree 标量索引）→ 桥接（跨语言 C ABI）→ FDW（索引下推）→ Catalog（索引管理）→ 内核（检索规划器与执行集成）。索引以 **Iceberg 官方标准的 Puffin 侧车文件**存储，与表元数据 / 快照统一管理。数据留在数据湖上不动，索引作为附属结构叠加。

### 2.2 优势（按层面；含与 Lance 共有的点）

**能力点层面**

1. **向量 + 标量索引一体**：IVFPQ 向量索引与 BTree 标量索引（支持多列复合）在同一套体系、一次索引定义中完成，覆盖等值 / 范围 / 最近邻检索。
2. **混合查询加速（两阶段物化，scalar-first）**：标量条件作为索引检索内的输入（预过滤）进入引擎，物化路径拆为「先读标量列 → 过滤 → 只物化存活行」，避免对整批候选做无效回表。实测（MoReVec 真实过滤负载、同环境 A/B）：
   - 1% 过滤档：K10 快 **11.2×**、K100 快 **13.8×**；
   - 5% 过滤档：K10 快 **7.2×**；无过滤无回归。
3. **官方 GT 召回验证**：SIFT **90.6%**、GIST **78.4%**（官方 GT @10，100 查询等距采样取均值）。召回指标有权威基准背书，非自洽验证。
4. **异步建索引 + 状态查询 API**：大表建索引不阻塞，索引状态可查询，管理路径与查询路径闭环。
5. **权限治理**：建表 / 建索引经数据库权限体系管控。
6. **查询级加速**：向量查询从秒级全表扫描降至索引查询（SIFT 0.2s / GIST 1.5s，11~13×）；分区并行下 DOP 1→8 加速 4.1~4.8×。

**设计层面**

1. **索引格式可独立演进**：索引的结构与算法升级**不触及底层 Parquet 数据与表格式**——索引是叠加在数据之上的附属结构，迭代更灵活（这是项目立项时就定下的关键设计取向）。
2. **存储为标准文件**：所有索引（尤其向量索引）都以 **Iceberg 官方标准的 Puffin 侧车文件**存储。Puffin blob 自包含（blob 数据 + 自描述 footer 元数据），与数据文件并列，可移植、易管理、易备份；任何 Iceberg 生态工具按规范即可解析索引。
3. **复合多列 BTree 标量索引**：支撑多列联合的等值 / 范围过滤，过滤条件直接在索引内求值。
4. **两阶段物化设计**：标量列先行、存活行才物化，从设计上消除"大面积无效回表"这一真实瓶颈（该瓶颈曾在实测中被反复定位）。
5. **数据湖一致性**：索引元数据进入表元数据 / manifest，随快照演进，是"数据湖的一员"而非数据库私有结构。
6. **真实召回保障**：评测体系以官方 GT 为基准；索引检索参数（nprobe 等）可控可调。

**架构层面**

1. **与数据库内核一体化**：索引经 FDW / 桥接 / 内核进入 SQL 查询链路，规划器感知检索（向量检索算子 / TopK），GUC 开关、权限、事务语义复用数据库既有能力——**索引对 SQL 用户透明**，一次建索引，之后就是普通 SQL 查询。
2. **分层解耦**：索引引擎 / 桥接（稳定 C ABI）/ FDW / Catalog 各司其职、跨语言协作，模块可独立演进与替换。
3. **直接索引既有 Iceberg 表，不搬数据**：数据留在数据湖，索引作为附属结构叠加，不改变数据生命周期。
4. **索引全生命周期治理**：定义 → 构建（同步 / 异步）→ 状态 → 查询闭环，元数据台账统一管理，权限可管控。

**与 Lance 共有的优势（诚实体现共同点；以下多项是双方都作为关键设计取向采纳的）**

1. **索引格式可独立演进**：Lance 官方格式规范明确将索引视为"分层在表行标识符之上的独立冗余数据结构……**使索引格式独立于表布局而发展**"；我们的索引同样是叠加在 Parquet 数据之上的附属结构——索引的优化 / 升级都不触及底层数据格式，迭代灵活。
2. **存储为普通文件，可移植 / 易管理 / 易备份**：Lance 官方规范写明"所有向量索引都存储为常规 Lance 文件，使其易于移植和管理"；我们的索引以 Iceberg 标准 Puffin 文件存储，同样是随表管理的普通文件。
3. **磁盘驻留 / 按需加载**，不需要全索引常驻内存；索引写入后不可变，可安全缓存；
4. **引擎对不兼容索引段回退扫描**（类型 / 版本兼容检查），格式演进不破坏可用性；
5. **向量 + 标量联合过滤**（混合查询）；
6. **量化压缩**向量体积（PQ 系）；
7. **格式开放**：Lance 本身开源；我们使用的 Puffin 是 Iceberg 官方标准；
8. **列式随机访问**显著优于全量扫描。

## 三、我们相比 Lance 索引设计有何优势

### 3.1 定位差异（一句话）

> Lance 是「为 AI 应用而生的一体化数据格式 + 嵌入式引擎」，要用它需要**把数据迁成 Lance 格式**；
> 我们是「在既有 Iceberg 湖仓上为数据库补齐索引能力」，**数据不动，索引叠加**。

这一差异决定了后续多数相对优势的方向。

### 3.2 相对优势（对照展开）

1. **不迁移数据，直接索引 Iceberg 表**
   我们直接在既有 Iceberg / Parquet 数据湖上建索引，数据生命周期、既有工具链、下游消费方全部不动；Lance 需要把数据（重新）嵌入到 Lance 格式，迁移有成本和切换风险。

2. **数据库级集成 vs 嵌入式库**
   我们的索引进入 SQL 全链路：FDW 下推、检索规划器感知、GUC 开关、**数据库权限体系**、事务语义全部复用 openGauss 既有能力，多用户 / 多租户场景权限可控；
   Lance 是嵌入式库，**无数据库级权限（仅 OS 文件权限）、无 HA / 复制、无持久性保证**（宿主应用负责），多租户与高可用场景能力缺失。

3. **混合查询的实现路径不同，且我们有量化收益**
   我们的做法是**标量条件进入检索内核**作为检索的一部分（预过滤），并配套**两阶段物化**（先读标量列→过滤→只物化存活行），同环境 A/B 实测收益 11~14×（1% 过滤档）；Lance 的预过滤是**应用层行掩码**（RowAddrMask）跳过方式，且按 Lance 公开的设计文档观察，其物化路径没有「先过滤再物化存活行」这一层优化——过滤成本与结果物化方式不同（此为基于公开文档的设计观察，非实测对比）。

4. **复合多列 BTree 标量索引**
   我们支持多列复合的标量索引并在索引内求值过滤；Lance 的标量索引族以单列加速掩码为主（BTree / Bitmap / FM 针对单列谓词，List 类针对标签列）。

5. **官方 GT 严格评测，召回可对外**
   我们用 SIFT / GIST 官方 GT 文件做真实召回验证（90.6% / 78.4%），指标有权威基准背书；Lance 默认配置召回偏低、需自行调参，公开评测体系并不内建于其工具链。

6. **标准载体：Puffin 是 Iceberg 官方规范**
   我们的索引文件是 Iceberg 标准侧车文件，随表快照 / metadata 统一管理，任何 Iceberg 生态组件按规范可读；Lance 的索引文件格式虽开源、也是普通文件，但是 Lance 自己的私有格式（与 Iceberg 无关），跨引擎互操作需对方读 Lance 格式。
   > 说明：**"索引是普通文件、可移植"这一项双方共有**（见 2.2 共有优势）；这里的相对点在于**载体是跨引擎的开放标准**，且索引生命周期跟随 Iceberg 快照。

7. **SQL 统一建索引 + 权限治理**
   一次 `create_index`（支持异步）即完成向量 + 标量索引定义与构建，走数据库权限与台账；Lance 通过 SDK 编程接口建索引，无数据库级权限 / 台账概念。

### 3.3 Lance 相对优势（诚实承认）

- **索引构建速度**：IVF-PQ 构建天然便宜（约 11×），适合"频繁重建 / 快速迭代"场景；
- **索引类型丰富度**：HNSW 图索引族、SQ / RaBitQ 多种量化、Bitmap / LabelList / FM / 全文检索，覆盖场景更广；
- **GPU 加速训练与分布式 10B 级建索引**；
- **embedded 免部署、Python 原生**：个人 / 小团队起步极快；
- **预过滤 API 成熟**（`prefilter` 开关即用）。

### 3.4 结论

两者**场景互补、各有取舍**：

- 在「AI 应用自建向量库、多模态数据、要求快速起步与高构建吞吐」的场景，Lance 有明确优势；
- 在「**既有 Iceberg 数据湖 + 数据库 SQL 体系内补齐索引能力**」的场景——数据已入湖、要复用数据库权限 / 规划器 / 事务、需要标准 Iceberg 载体与官方 GT 质量门禁——我们的路径更贴合。

我们相对 Lance 的差异化核心是三件事：**数据库内核集成（SQL 透明 + 权限 + 规划器）、标准 Iceberg 索引载体（Puffin + 快照管理）、官方 GT 质量门禁（召回可对外）**。

> 注："索引格式可独立演进""存储为标准文件"虽是双方共有的设计取向，但在我们的架构里是**被明确作为立项关键取向**落实的（索引即附属结构、Puffin 侧车文件），因此它们既属于共有优势，也是我们能力栈的设计底色，不因共有而减损其价值。

### 4.2 测试条件备注

- **我方召回率**：SIFT 90.6% / GIST 78.4%，官方 GT @10，100 条查询等距采样取均值，同环境实测；测试前清理历史检索参数残留，避免虚高。
- **我方混合查询收益**：MoReVec 真实过滤负载（电影 / 评论数据），同环境 A/B 对照（对照组 / 实验组同一流程），1% / 5% 过滤档 × K10 / K100，多查询取均值。
- **我方向量查询加速**：全表扫描 → 索引查询同环境实测；SIFT 2358ms→212ms（11×）、GIST 18883ms→1467ms（13×）。
- **我方 DOP**：分区并行 + IVF 距离计算并行，DOP 1→8 加速 4.1~4.8×，最优配置 16 分区 + DOP=8。
- **Lance 侧数字**：均来自第三方公开评测，各自测试条件与数据集不同，仅作量级参考，不与我方数字直接横比。
