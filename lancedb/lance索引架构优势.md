# Lance 索引架构优势

> 定位：单独整理 Lance 索引在**架构层面**的设计优势（能力点 / 性能表现见《Lance索引设计调研与优势分析.md》）
> 依据：Lance 官方格式规范索引章节（中译版见同目录 `lance索引.md`）+ 公开格式资料
> 说明：聚焦"架构如何设计、为什么这个架构有优势"；实验性 / 推测性内容已标注

---

## 一、架构总览：索引是独立于表布局的冗余数据结构

Lance 将索引视为**分层在表行标识符之上的独立冗余数据结构**。这个定位带来架构级的好处：

- **文件格式不被内置搜索结构约束**——表格式不需要为"支持什么索引"预留结构，索引是叠加结构；
- **索引格式独立于表布局而发展**——索引算法 / 结构升级不触及底层数据文件，两个层面各自演进。

索引体系分三类，职责清晰：

| 类型   | 作用                                  | 返回          |
| ---- | ----------------------------------- | ----------- |
| 标量索引 | 加速整数 / 时间戳 / 字符串谓词（等值、范围、集合成员、令牌匹配） | 匹配的行标识符     |
| 向量索引 | 高维嵌入上的近似最近邻检索（IVF 系 / HNSW）         | 行标识符 + 距离分数 |
| 系统索引 | 内部表维护与行标识符解析，终端用户不可见                | —           |

## 二、统一存储架构：索引即普通文件

- 每个索引的内容存放在基路径下 `_indices/{UUID}` 目录，具体内容由索引类型决定，通常是**包含索引数据结构的 Lance 文件**；
- 关键架构收益：**复用现有 Lance 文件格式的读写代码**，不必为索引另造一套 IO 层；
- 文件自描述（footer / Arrow schema metadata / 文件级 global buffer），普通文件形态 → 可移植、易管理、易备份、可随数据集共享，免重建。

## 三、元数据驱动的索引模型（manifest + IndexSection）

索引在**清单文件**里以 `IndexSection` 描述，每段一个 `IndexMetadata`：

| 字段              | 作用                                  |
| --------------- | ----------------------------------- |
| uuid            | 索引段唯一标识                             |
| name            | 索引名（并入既有索引时必须与既有段一致）                |
| fields          | 键控列 + 覆盖列（fields[0] 恒为键控列）          |
| covering_fields | 仅携带值、不被键入的列，让"只投影这些列"的查询无需读数据片段     |
| fragment_bitmap | 该段覆盖的片段 ID 集合                       |
| index_details   | protobuf any，承载类型特定的参数与配置 → 索引类型可扩展 |
| version         | 索引格式版本 → 兼容性演进依据                    |

架构特点与收益：

1. **索引段粒度**：一个索引由多个段组成，每段覆盖不相交的片段子集；
2. **索引不需要覆盖全部片段**：允许部分未索引 → 引擎把查询拆成「索引子计划 + 未索引子计划」合并结果，索引可以不完全更新仍可用；
3. **覆盖列（covering columns）**：索引除键控列外还可携带列值，只投影覆盖列的查询由索引直接回答、**无需触碰数据片段**——这是"索引服务化查询"的架构手段（注意：官方注明目前尚无构建器写入携带值，引擎须把 covering_fields 当作声明、从基表兜底服务，直至自行验证存储，此为过渡状态）；
4. **类型与版本双检查**：引擎先验索引段类型与格式版本，识别不了就**跳过该段并回退扫描** → 索引格式可随时间演进且保持向后兼容（向量索引格式已演进到 V3）。

## 四、加载与生命周期架构：按需、逐步、不可变、可合并

四条设计准则共同决定内存 / IO 效率：

1. **按需加载**：数据集可在不加载任何索引的情况下打开与读取；只有查询能从索引受益时才加载 → 最小化内存、加快数据集打开；
2. **逐步加载**：查询执行期间只加载必要部分——例如 BTree 查询先读一个小的页表确定要加载哪些页，再只加载这些页执行搜索 → **分摊冷索引查询成本**（每个查询只碰索引的一小部分）；
3. **写入后不可变**：索引文件不可原地修改，只能通过创建新文件变更 → **可安全缓存在内存或磁盘**，无一致性问题（与数据文件同准则）；
4. **段可合并**：索引远小于数据文件，合并索引段覆盖多个片段是高效的 → 减少查询执行期需打开 / 需查询的索引文件数量。

## 五、一致性与降级架构：不可变段的正确性处理

索引段不可变 → 可能引用已删除 / 已更新的行，查询期必须过滤。架构上对四种情况做了明确约定：

1. 段中有已删行 → 用删除文件中的行地址过滤结果；
2. 段覆盖的片段已被整体删除 → 检测缺失片段 ID，过滤该段所有行地址；
3. 段内某列被原地更新 → 过滤不在当前 fragment_bitmap 中的行地址（字段级计数，含覆盖列）；
4. 覆盖文件中出现更新值 → 排除受影响行并**按当前叠加值重新评估**（不重评会静默丢失命中新值的行），排除可字段感知、仅影响相关行。

压缩导致行地址变化时的三种处理策略：

| 策略     | 做法                       | 权衡                        |
| ------ | ------------------------ | ------------------------- |
| 忽略     | 索引段不再覆盖被压缩片段             | 简单，但压缩立即使索引过时，查询性能最差      |
| 立即重写   | 用重映射后的行地址重写索引段           | 索引保持最新，但压缩过程写入放大明显        |
| 片段重用索引 | 建系统索引把旧地址映射到新地址，读取期内存重映射 | 查询期增加少量 IO / 计算，避免压缩期写入放大 |

另有**稳定行 ID**（实验阶段）：逻辑标识符压缩中不随移动而变 → 压缩后无需重映射、仅字段数据变化才使索引失效；代价是查询期需额外查找把稳定 ID 转物理地址（性能权衡评估中）。

## 六、向量索引架构：三段式自由组合

向量索引统一拆成**聚类 × 子索引 × 量化**三段，可独立替换组合：

- 聚类：IVF（k-means 分区，搜索只查最相关分区）——目前唯一主聚类机制，可与任何子索引 / 量化组合；
- 子索引：FLAT（精确线性扫描）/ HNSW（分层导航小世界图）；
- 量化：PQ（乘积量化）/ SQ（标量量化）/ RaBitQ（随机旋转 + 二进制量化，极端压缩）/ FLAT（无量化）。

组合命名 `{聚类}_{子索引}_{量化}`，常用如 IVF_PQ、IVF_HNSW_SQ、IVF_SQ、IVF_RQ、IVF_FLAT。**格式版本化**：向量索引格式已 3 个版本，具体版本记录在通用索引元数据的 index_version 字段。

存储布局：每个向量索引 = **2 个标准 Lance 文件**——索引文件 `index.idx`（搜索图 / 结构，HNSW 存 `__vector_id` / `__neighbors` / `_distance`，FLAT 为空文件带 marker）+ 辅助文件（按分区排序的量化向量）。分区元数据放 Arrow schema metadata（`lance:index` / `lance:ivf` / `lance:hnsw`），IVF 质心等放文件级 global buffer。

## 七、标量索引架构：BTree 两级结构

BTree 用**两级结构**在"贵的全内存结构"与"不可有效搜索的磁盘结构"之间取得平衡：

- `page_lookup.lance`：BTree 结构，映射值范围 → 页码，设计为**可缓存在内存**；对 10 亿个值可存 256K 个 4K 叶子，BTree 元数据只需几 MiB 内存，搜索缩小到单个 4K 值页；
- `page_data.lance`：叶子子索引（当前为平面文件），存排序值 + 行 ID。

对等值 / 范围 / IN / IS NULL 四类谓词给出**精确结果**。标量索引族还有 Zone Map（主要跳过结构）、Bitmap（低基数）、LabelList（标签列）、Bloom Filter、FTS / N-gram / FM-Index（子串 / 全文）、RTree 等，按谓词类型选用。

## 八、事务化索引生命周期

索引段创建 / 更新走事务流程，**与数据写入共用同一套事务机制**：

1. 构建索引数据 → 写入新 `_indices/{UUID}` 目录（新 UUID）；
2. 准备 `IndexMetadata`（uuid / name / fields / covering_fields / fragment_bitmap / index_details / version）；
3. 提交事务：写新清单，在其 `IndexSection` 包含新索引段——**原子完成**。

原地更新列（不删行）时，引擎从含该列各索引段的 fragment_bitmap 移除受影响片段 ID → 只把片段**标记为需重索引**，不使整段失效，也不从索引读无效数据。

## 九、生态集成架构

- **Arrow 原生**：索引元数据走 Arrow schema metadata，向量 / 图数据按 Arrow 列式组织，二进制载荷走文件级 global buffer → 与 Arrow 生态零间隙；
- **查询执行引擎**：在 DataFusion 上以自定义物理算子实现索引查询（过滤读取、标量索引执行、KNN 距离计算、IVF 分区与子索引执行等），索引是执行计划的一等组成部分；
- **开放目录 / 引擎**：Polaris、Unity Catalog、Gravitino、Hive Metastore，及 Spark / Trino / DuckDB 等。

---

## 结论：架构层面的核心优势

1. **解耦**：索引独立于表布局的冗余数据结构，表格式与索引格式各自演进；
2. **统一**：索引即普通 Lance 文件 + 元数据驱动的段模型（manifest + IndexMetadata），一套 IO / 事务 / 兼容机制覆盖所有索引类型；
3. **可演进**：类型 / 版本双检查 + 回退扫描，格式升级向后兼容不破坏可用性；
4. **可降级**：索引不覆盖全部片段、识别不了的段跳过回扫，部分失效不拖垮整体查询；
5. **按需高效**：按需 / 逐步加载 + 不可变缓存 + 段合并，冷索引与大规模数据集下的内存 / IO 开销可控；
6. **正确性自洽**：不可变段 + 查询期过滤 + 压缩重映射策略 + 稳定行 ID（实验），覆盖删除 / 更新 / 压缩全链路。
