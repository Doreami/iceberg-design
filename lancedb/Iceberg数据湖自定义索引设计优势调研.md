# Iceberg 数据湖自定义索引设计优势调研

> **定位**：面向领导 / 管理层的汇报材料——论证我们在 **Iceberg 湖仓上自定义构建索引能力栈**的设计优势。
> **参照系**：以 Lance（业界代表性的向量索引 / 湖格式）作为参照，用于衬托与佐证我们的设计取舍；**Lance 是参考，不是主角**。
> **结论先行**：我们的核心优势是三件事——**数据不动、直接索引 Iceberg 表**；**与数据库内核深度集成（SQL 透明 + 权限 + 规划器）**；**标准 Iceberg 载体 + 官方 GT 质量门禁**。
> **使用说明**：**第五章为汇报素材**（可直接上 PPT）；第二~四章为背景与开发参考。

---

## 一、为什么选择"在 Iceberg 上自定义索引"

### 1.1 场景

湖仓一体趋势下，数据落在 Iceberg 表的 Parquet 文件中（对象存储 / 文件系统），具备事务与 Schema 演化能力，但**湖上数据天然没有数据库式的索引结构**——openGauss 经 FDW 访问湖数据只能全表扫描，面对百万~十亿级、128~960 维高维数据，秒级延迟无法支撑检索场景。

### 1.2 两条路径的取舍

| | 路径 A：引入现成向量库 / 格式（如 Lance） | 路径 B：在 Iceberg 表上自定义索引（**我们的选择**） |
|---|---|---|
| 数据 | 需把数据**迁移 / 重新嵌入成 Lance 格式**，脱离既有 Iceberg 生态 | **数据不动**，索引作为叠加结构直接建立在 Iceberg 表上 |
| 生态 | 独立格式，与 Iceberg 数据湖是两套体系，工具链、下游消费方需切换 | 完全兼容 Iceberg（metadata / manifest / Puffin 标准），既是"数据湖一员" |
| 数据库 | 嵌入式库，无数据库级权限 / 规划器 / 事务语义；要么额外集成、要么应用层自管 | 直接复用 openGauss 的 SQL / 权限 / 规划器 / 事务，索引对 SQL 用户透明 |
| 质量 | 召回指标需自行调参验证，无官方 GT 生态 | 以 SIFT / GIST 官方 GT 做真实召回门禁 |

结论：**在既有 Iceberg 湖仓 + 数据库 SQL 体系内补索引能力，路径 B 更贴合，这也是本项目的设计使命**——为 openGauss 补齐一套完整的数据湖索引能力栈（引擎 / 桥接 / FDW / Catalog / 内核 / 数据面）。

## 二、我们索引设计优势（核心章节）

### 2.1 架构层面

1. **数据不动，索引叠加，生态兼容**
   - 直接在既有 Iceberg / Parquet 湖上建索引，存量资产零成本接入；
   - 索引以 Iceberg 标准 Puffin 载体存储，引用链清晰（表元数据 → 索引注册表 → 算法文件），元数据轻量、不复制索引数据；
   - 不同算法可自定义 artifact 内部格式（如 BTree 用标准多 blob、IVF 用自有布局），以"实现标识 + 格式版本"选择 reader——**载体标准、内容自由**。

2. **与数据库内核一体化**
   - SQL 下推 / 规划器 / 权限 / GUC / 事务全部复用 openGauss，索引对 SQL 用户透明；
   - 索引对外**可见性由 Catalog 原子推进控制**（写入 ≠ 生效），不向查询暴露半成品 / 损坏索引；孤儿文件残留由索引维护回收；
   - **线程与调度权归宿主**：DOP / 任务 / 取消由数据库决定，索引不自建生产运行时、不抢占 worker。

3. **索引类型可扩展，新增索引容易**
   - **编排与算法分离**：运行时管计划 / 覆盖 / 合并，插件只实现算法；
   - 新增索引类型是引擎侧"局部新增"，数据格式 / ABI / 下推框架稳定不动；
   - 新插件**自带完整性保障**：必须实现 full-scan 兜底，否则查询返回 Unsupported 而非错误结果；带版本 key 保证已发布段可找回 reader，向后兼容。

4. **增量复用与正确性优先（fail-closed）**
   - 逻辑定义与物理实现分离，用字段 ID 绑定列，列名 / 表结构变化不失效；
   - 与 Iceberg 分区对齐的三层组织模型（定义 → 分区组 → 物理段），消除重复事实，非分区表统一代码路径；
   - 按目标快照存活文件计算覆盖，Append / COW 后旧段按死行比例策略部分复用，无需全量重建；
   - 构建与查询**共用同一套覆盖语义**，杜绝两套规则打架；
   - 无法证明安全复用即回退全扫描或报错，**不静默漏行**（限定在索引路径被路由后：段 / 注册表缺失或损坏即 fail-closed 报错；未建索引的表由规划器正常回退全扫）。

5. **并行构建，统一发布收口**
   - 协调者 / 执行者 / 组装者三段式：执行者只产不可变产物，协调者统一校验并组装成一张补丁，宿主统一原子发布；
   - 杜绝"部分索引提前外泄、后完成的覆盖先完成的"并发竞态；
   - 发布冲突只需基于最新元数据重新准备，**已构建产物不重做**。

6. **计算与存储解耦，核心与存储后端解耦**
   - 索引计算与索引存储分离，算法升级不改存储文件结构；
   - 核心层只依赖自有抽象（分区标识、文件引用、trait），与具体存储 / 表格式无关；运行时与算法可用内存替身聚焦测试，底层格式演进不扩散全仓。

7. **内存与 IO 可控**
   - 物化按需 / 流式：标量逐文件分批回表、向量超取有界；
   - 索引引擎内**按需读页 + LRU 页缓存**（查询只加载候选页并缓存，不全索引常驻内存），磁盘驻留、按需加载。

8. **设计过程严谨、可验证**
   - 关键决策文档化：每个设计决策记录未采用方案、演进触发条件、验收不变量；
   - 持久化格式有版本化契约 + 损坏输入 / 旧版本读取测试；
   - 性能优化有量化方法：如排序改精确的部分排序算法（召回率不变、可验证），优化结论有数据支撑。

### 2.2 设计层面

1. **索引独立演进 / 存储为标准文件**（展开见 2.1-1 与 2.4-1/2，此处不重复）：设计落点是索引作为叠加在 Parquet 数据之上的附属结构、升级不触及数据；索引**注册表与 BTree 为 Iceberg 标准 Puffin** 普通文件，可移植、易管理、易备份（IVF/IVF-PQ 算法文件为插件自有二进制格式，经标准 Puffin 注册表统一引用管理）。
2. **向量检索 + 标量过滤，一套体系打通**：IVFPQ 向量索引与 BTree 标量索引（支持多列复合）在同一套体系、一次索引定义中完成，覆盖等值 / 范围 / 最近邻检索——标量条件可直接进入检索内核预过滤，与向量检索在同一执行计划内协作。
3. **两阶段物化（scalar-first）设计**：混合查询把物化路径拆为「先读标量列 → 过滤 → 只物化存活行」，从设计上消除"大面积无效回表"这一真实瓶颈。
4. **数据湖一致性**：索引元数据进入表元数据 / manifest，随快照演进；与 Iceberg 生态（Puffin / metadata / manifest）一致，而不是数据库本地私有结构。

### 2.3 能力点层面（实测，见附录测试条件）

1. **混合查询加速**：标量条件作为检索内的输入（预过滤）+ 两阶段物化；MoReVec 真实过滤负载、同环境 A/B（相对现状后过滤构建）：1% 过滤档 K10 快 **11.2×**、K100 快 **13.8×**；5% 档 K10 快 **7.2×**；无过滤无回归。
2. **向量查询加速**：全表扫描 → 索引查询，SIFT 11×（2358ms→212ms）、GIST 13×（18883ms→1467ms）；分区并行 DOP 1→8 加速 **4.1~4.8×**。
3. **官方 GT 召回门禁**：SIFT **90.6%**、GIST **78.4%**（官方 GT @10，100 查询取均值）——召回有权威基准背书，非自洽验证。
4. **异步两步建索引 + 索引状态可查**：`create_index` 先发布索引定义、立即返回（不阻塞）；再显式触发构建完成。索引状态可查（SQL 查询台账），定义 → 构建 → 查询全生命周期可管理。（注：当前"异步"是定义与构建分离的两阶段模式；真实后台任务状态机尚未实现。）
5. **权限治理**：建表 / 建索引走数据库权限体系，多用户可控。
6. **性能优化方法论（可量化、可验证）**：优化以**精确算法**为主——如候选排序改部分排序（精确算法，召回率不变）等，实测查询延迟累计 **-84%**；优化结论均有数据支撑，且不引入召回损失。
7. **与业界实现的单点对照（参考）**：曾在 SIFT1M 上与 Lance 做同数据集单点对照——Lance 关闭 SIMD / 单线程（**非对称条件**），同等召回档下我们的查询延迟 1.71ms vs Lance 2.27ms、构建 132s vs 32s（Lance 构建更快）。**仅作参考数据点，不作为跨实现通用结论**。

### 2.4 与业界主流（Lance）共有的优势

以下优势并非我们独有，而是**行业认可的关键设计取向**，我们同样作为立项原则落实——在汇报中如实呈现，说明我们的设计"站在了正确方向"：

1. **索引格式可独立演进**：Lance 官方规范明确"使索引格式独立于表布局而发展"；我们的索引同样是叠加在数据之上的附属结构。
2. **存储为标准文件**：Lance 规范写明"所有向量索引都存储为常规 Lance 文件，使其易于移植和管理"；我们以 Iceberg 标准 Puffin 作为索引注册表载体（BTree 为标准 Puffin，向量算法文件为插件自有格式，经标准注册表统一管理）。
3. **磁盘驻留 / 按需加载**，不全索引常驻内存；索引写入后不可变，可安全缓存。
4. **索引格式带类型标识 + 版本契约**，格式演进有明确的兼容边界：Lance 遇到不兼容段会跳过并回退扫描；我们 fail-closed 报错、不猜测——两者都不让格式演进破坏可用性。
5. **向量 + 标量联合过滤**（混合查询）、**量化压缩**向量体积（PQ 系）、**列式随机访问**优于全量扫描。

## 三、对照 Lance：我们的差异化优势（参照系）

### 3.1 定位差异（一句话）

> Lance 是「为 AI 应用而生的一体化数据格式 + 嵌入式引擎」，要用它需要**把数据迁成 Lance 格式**；
> 我们是「在既有 Iceberg 湖仓上为数据库补齐索引能力」，**数据不动，索引叠加**。

### 3.2 相对优势（7 项）

| # | 维度 | 我们 | Lance | 价值点 |
|---|---|---|---|---|
| 1 | 数据迁移 | 直接索引既有 Iceberg / Parquet 表，**不搬数据** | 数据需（重新）嵌入成 Lance 格式，有迁移成本与切换风险 | 存量资产零成本接入 |
| 2 | 数据库集成 | SQL 下推 / 规划器 / 权限 / GUC / 事务全复用 openGauss | 嵌入式引擎：仅 OS 文件权限、无内置 HA / 复制 / 持久性保证（宿主负责，云托管版除外） | 多用户、多租户、高可用场景可用 |
| 3 | 混合查询实现 | 标量条件**进检索内核**预过滤 + **两阶段物化**（先读标量列 → 过滤 → 再物化存活行），实测 11~14×（1% 过滤档，相对现状后过滤构建） | 行掩码预过滤（作用于 IVF 遍历，同类避免无效物化的机制）；差异在实现层 | 我们在物化顺序与列裁剪上有量化收益 |
| 4 | 标量索引 | BTree **多列复合**，索引内求值 | 标量索引族以单列掩码加速为主 | 多条件联合过滤更强 |
| 5 | 质量门禁 | 官方 GT 真实召回验证（90.6% / 78.4%，调优配置下），指标可对外 | 默认配置召回偏低（第三方评测 0.15~0.48 档，条件不同不可与我们直接横比），无官方 GT 生态 | 我们以官方 GT 门禁保证，Lance 依赖自行调参 |
| 6 | 索引载体 | 索引注册表为 Iceberg 官方标准 Puffin（BTree 为标准 Puffin，向量算法文件为插件自有格式），跨引擎开放、随快照管理 | 开源但是 Lance 私有格式，跨引擎互操作需读 Lance 格式 | 生态互操作性强 |
| 7 | 索引管理 | SQL 统一建索引（支持异步）+ 数据库台账 / 权限 | SDK 编程接口，无数据库级台账 / 权限 | 运维友好、可管控 |

### 3.3 Lance 相对优势（诚实承认）

- **索引构建速度**：IVF-PQ 构建天然便宜（第三方对比约 11×），适合"频繁重建 / 快速迭代"；
- **索引类型丰富度**：HNSW 图索引族、多种量化（SQ / RaBitQ）、Bitmap / LabelList / FM / 全文检索，覆盖场景更广；
- **GPU 加速训练与分布式 10B 级建索引**；
- **embedded 免部署、Python 原生**：起步极快；
- **预过滤 API 成熟**。

这些是 Lance 的优势，也是我们后续规划中可吸收的方向（见第四节）。

### 3.4 关键差异化结论

我们相对 Lance 的差异化核心是三件事：**数据库内核集成（SQL 透明 + 权限 + 规划器）、标准 Iceberg 载体（Puffin + 快照管理）、官方 GT 质量门禁（召回可对外）**。

## 四、给管理层的核心信息

1. **我们做了一个"正确方向"的选择**：在既有 Iceberg 湖仓上以"数据不动、索引叠加"的方式补索引能力，既守住存量资产，又站在了业界公认的设计方向（索引独立演进、存储为标准文件）上；
2. **我们的差异化不可替代**：数据库内核一体化（SQL 透明 + 权限 + 规划器）、标准 Iceberg 载体、官方 GT 质量门禁——这些是引入外部向量库 / 格式给不了的；
3. **能力可量化、指标可对外**：混合查询最高 11~14×、向量查询 11~13×、召回率有官方 GT 背书；Lance 的长处（构建速度、索引类型、GPU / 分布式）作为后续规划方向已列入演进清单。

## 五、PPT 汇报素材（按页整理）

### 一句话定位（封面 / 定位页）

> 在 Iceberg 湖仓上以「**数据不动、索引叠加**」的方式，为数据库补齐完整索引能力栈，索引对 SQL 用户透明。

### 5.1 系统指标（一屏数字）

| 类别 | 指标 |
|---|---|
| 召回（官方 GT @10） | SIFT **90.6%**、GIST **78.4%** |
| 向量查询加速 | 全扫 → 索引：SIFT 2358→212ms（**11×**）、GIST 18883→1467ms（**13×**） |
| 混合查询（两阶段物化） | 1% 过滤档 K10 **11.2×** / K100 **13.8×**；5% 档 **7.2×**（均相对现状后过滤构建） |
| 并行查询 | DOP 1→8 加速 **4.1~4.8×**（16 分区 + DOP=8 最优） |
| 优化方法论 | 精确部分排序累计 **-84%**（召回不变）；候选串克隆 -99.7%（每查询 39K→100 次） |
| 其他优化 | vector→fixed 1.2~1.7×；jemalloc 延迟 -17~37% / 缺页 -57~62%；并行回表 GIST -79% |
| 索引构建 | SIFT 7.8min / GIST 63.2min（IVFPQ） |
| 质量 | devtest **67 通过 + 1 预期失败**；11 仓联编；10+ 篇文档、28 类踩坑沉淀 |

### 5.2 架构优势（一页 8 条，每条一句）

1. **数据不动，索引叠加** —— 直接索引既有 Iceberg / Parquet 表，存量资产零成本接入；
2. **与数据库内核一体** —— SQL 透明、规划器感知、权限与事务复用 openGauss；
3. **索引可见性由 Catalog 原子推进控制** —— 写入 ≠ 生效，不向查询暴露半成品 / 损坏索引；
4. **索引类型可扩展** —— 编排与算法分离，新增索引类型是局部新增，格式 / ABI / 下推不动；
5. **增量复用 + fail-closed** —— Append / COW 后复用旧段；无法证明安全时宁可全扫，不静默漏行；
6. **标准载体 + 内容自由** —— Puffin 标准存储、生态可互操作，算法可自定义内部格式；
7. **计算与存储解耦、核心与后端解耦** —— 算法升级不改存储，可聚焦测试；
8. **内存 / IO 可控** —— 引擎内按需读页 + LRU 页缓存、流式物化，不全索引常驻内存。

> 能力佐证（可并入脚注 / 下一页）：混合查询最高 11~14×；向量查询 11~13×、DOP 4.1~4.8×；召回经官方 GT 验证（SIFT 90.6% / GIST 78.4%）。

### 5.3 实现了哪些功能（能力全景）

**四大能力模块**

1. **向量索引 IVFPQ**：构建 / 加载 / 检索 / 全扫兜底，L2 距离，检索参数（nprobe 等）可控；
2. **标量索引 BTree**：单列 / 多列复合；等值 / 范围已端到端下推，IN / BETWEEN 引擎层支持（SQL 下推待接）；索引内精确求值；
3. **混合查询**：向量 + 标量联合检索，标量条件进检索内预过滤 + 两阶段物化；
4. **索引管理**：create_index（同步 / 异步两步：定义先行、构建随后）、同名替换、optimize（Append 增量 / Retrain 重建）、drop、索引状态可查（SQL 查询台账）、**并行构建**（协调者 / 执行者 / 组装者三段式；当前支持单分区值、worker 上限 8）。

**工程化能力**：标准 Puffin 载体 + 版本化注册表（完整性校验）、fail-closed 回退、回表物化、权限治理、索引维护（孤儿清理）、官方 GT 评测体系、多仓联编 + 全量回归。

### 5.4 索引放湖上的优势（弹性 / 计算资源）

1. **计算与存储分离 → 弹性扩展**：索引是湖上文件——**存储**容量随对象存储弹性扩展、不占数据库本地盘；索引**构建 / 查询是计算**——构建异步 + 并行（执行者可调度到多 worker）、查询 DOP 并行，计算资源按需扩缩而索引不动。
2. **数据库无状态、迁移 / 容灾友好**：索引不在数据库本地，实例重启、迁移、多实例负载均衡下索引不丢；接入同一数据湖的 openGauss 实例均可读取同一份索引。
3. **与数据同生命周期、强一致**：索引随表快照**原子发布**（写入 ≠ 生效），与数据天然一致，不会"索引悬空"。
4. **标准载体 → 生态资产**：索引以 Iceberg 标准 Puffin 注册表统一管理（BTree 为标准 Puffin，向量算法文件为插件自有格式），是数据湖资产而非数据库私有结构，可备份、可迁移、可共享。
   > 诚实标注：当前查询路径经 openGauss 栈（引擎 / 桥接 / FDW / 内核）；载体是开放标准，理论上其他按规范实现的引擎即可读，但当前 reader 仅我们实现——**"多引擎共享"是方向，不是已交付**。

### 三句话收口（演讲提示）

1. **对湖**：数据不动、生态兼容，索引作为湖上标准载体随表快照统一管理；
2. **对库**：与 openGauss 内核一体化，索引对 SQL 用户透明、权限可控；
3. **对外**：能力可量化（混合查询最高 11~14×）、召回可承诺（官方 GT 背书）。
