## 1. 模块定位与边界

### 1.1 模块职责

本模块负责**自定义索引的元数据管理和生命周期管理**。它不实现任何具体的索引数据结构（BTree、Bloom Filter、IVF 等），而是提供：

- 索引的**注册与发现**（有哪些索引、覆盖哪些文件、什么状态）
- 索引的**构建调度**（全量/增量构建、调用索引插件完成实际构建）
- 索引的**状态维护**（active → stale → remap → rebuild → GC）
- **Puffin 文件读写**（Reader/Writer，纯 C++ 实现）
- **与 Iceberg TableMetadata 的同步**（通过 JNI 桥接调用 Java SDK）

### 1.2 边界图

```
                        本模块 (索引管理)
                    ┌───────────────────────────────┐
                    │                               │
  TableMetadata ←──┤  IndexCatalog  IndexMaintainer │
  (Java SDK)       │                               │
                    │  IndexSegmentManager          │
  Manifest ←───────┤                               │
  (Java SDK)       │  PuffinReader  PuffinWriter    │
                    │                               │
                    └──────────┬────────────────────┘
                               │ IIndexPlugin 接口
                    ┌──────────▼────────────────────┐
                    │     索引具体实现 (外部)         │
                    │  BTreeIndex  BloomIndex        │
                    │  BitmapIndex IVFIndex  ...     │
                    │  (各索引独立实现)               │
                    └───────────────────────────────┘

  本模块管: 索引有哪些、状态是什么、文件在哪里、何时构建/重建
  各索引导管: 序列化格式、构建算法、值评估逻辑
```

### 1.3 语言与集成策略

| 组件                      | 语言           | 原因                 |
| ----------------------- | ------------ | ------------------ |
| Puffin 文件 I/O           | C++          | 计算不重，但需要与查询引擎零拷贝集成 |
| 索引构建与评估                 | C++          | 计算密集型              |
| TableMetadata 读写 commit | Java（JNI 桥接） | Java SDK 是唯一可靠实现   |
| Manifest 解析             | Java（JNI 桥接） | 复用 Java SDK        |

## 3. Puffin 文件格式概要

### 3.1 文件布局

```
┌─────────────────────────────┐
│  Magic (4 bytes)   "PFA1"   │
├─────────────────────────────┤
│  Blob₁                      │  索引/统计的二进制数据
│  (变长, 可压缩)              │
├─────────────────────────────┤
│  ...                        │
├─────────────────────────────┤
│  Blobₙ                      │
├─────────────────────────────┤ ← Footer 开始
│  Magic (4B)                 │
├─────────────────────────────┤
│  FooterPayload (UTF-8 JSON) │  blobs[] + 文件级 properties
│  可选 LZ4 压缩               │
├─────────────────────────────┤
│  FooterPayloadSize (i32 LE) │
├─────────────────────────────┤
│  Flags (4B, bit0=LZ4)       │
├─────────────────────────────┤
│  Magic (4B)                 │
└─────────────────────────────┘
```

### 3.2 BlobMetadata 字段

| 字段                  | 类型     | 必需  | 说明                         |
| ------------------- | ------ | --- | -------------------------- |
| `type`              | string | ✅   | Blob 类型标识符，自定义索引需定义唯一 type |
| `fields`            | int[]  | ✅   | Iceberg 字段 ID 列表           |
| `snapshot-id`       | long   | ✅   | 源快照 ID                     |
| `sequence-number`   | long   | ✅   | 源快照序列号                     |
| `offset`            | long   | ✅   | Blob 在文件中的字节偏移             |
| `length`            | long   | ✅   | 压缩后字节长度                    |
| `compression-codec` | string | ❌   | `"lz4"` / `"zstd"`，省略=不压缩  |
| `properties`        | map    | ❌   | 任意 key-value，索引参数和元数据放在此处  |

### 3.3 压缩

- FooterPayload: LZ4（可选，Flags bit0 标记）
- Blob: LZ4 或 Zstd（可选，`compression-codec` 标记）
- 整数编码：全部有符号小端序

### 3.4 TableMetadata.statistics[] 的存储策略

本模块**不将每个索引文件的条目直接放入** `TableMetadata.statistics[]`。改为：

- `statistics[]` 中只有**一条**指向 `![index_catalog]().puffin` 的指针
- 所有自定义索引的元数据集中在 `index_catalog.puffin` 内管理
- 内置 Puffin 统计（如 Theta Sketch）可以继续在 `statistics[]` 中独立存放

```
TableMetadata.statistics[]
  ├── [0]: type="apache-datasketches-theta-v1", path="...theta.puffin"  (内置)
  └── [1]: type="puffin.idx.registry-v1", path="...index_catalog.puffin"
            ↑ 自定义索引从此入口发现
```

## 4. 索引组织模型

### 4.1 核心概念

```
一个逻辑索引 (IndexGroup) = 1 个或多个物理索引段 (IndexSegment)

IndexGroup: 唯一标识一个逻辑索引
  - uuid: 全局唯一标识
  - name: 索引名称 (如 "btree_order_id")
  - type: 索引类型 (如 "puffin.idx.btree-v1")
  - field_id: 索引列

IndexSegment: 一个不可变的物理 Puffin 文件
  - uuid: 段唯一标识
  - puffin_path: 对应 .puffin 文件的路径
  - delta_from_segment: 增量链 (指向前一个 segment 的 uuid)
  - file_coverage: 覆盖哪些 Parquet 文件 (摘要)
  - status: 当前状态 (active/stale_partial/remapping/...)
```

### 4.2 增量链示例

```
IndexGroup "a1b2c3d4" (btree_order_id, field=1)
│
├── Segment[0] (uuid="s0-xxx", status=active)
│   puffin: snap-1001-2-idx1.puffin (16MB)
│   covers: files 0-499
│
├── Segment[1] (uuid="s1-yyy", status=active)
│   puffin: snap-1003-3-idx1delta.puffin (3.3MB)
│   delta_from_segment: "s0-xxx"   ← 增量, 基于 seg[0]
│   covers: files 500-999
│
└── Segment[2] (uuid="s2-zzz", status=active)
    puffin: snap-1011-6-idx1delta2.puffin (5MB)
    delta_from_segment: "s1-yyy"   ← 增量, 基于 seg[1]
    covers: files 1000-1499, spec_id=1

查询 field=1 时: 需搜索全部 3 个 segment 的 BTree
增量构建时: 只新增 Segment[3], 前 3 个 segment 的 Puffin 文件不动
```

### 4.3 文件拆分原则

- 一个 Puffin 文件 = 恰好一个 IndexSegment（大索引 >1MB 必须独立文件）
- 小统计索引（Theta + HLL <1MB）可合并，需满足相同覆盖范围 + 相同生命周期
- 增量构建只追加新 Puffin 文件，永不修改旧文件

## 5. 元数据设计：index_catalog.puffin

### 5.1 定位

`index_catalog.puffin` 是本模块的**元数据中枢**。它是一个标准 Puffin 文件，包含：

- **Blob₀ (registry-v1)**：索引注册表，描述所有 IndexGroup 和 IndexSegment 的目录、状态、文件覆盖摘要
- **Blob₁**：保留位，预留给未来的审计日志等扩展用途（当前版本不含此 Blob）

### 5.2 registry Blob 结构

```
┌──────────────────────────────────────────────────────────┐
│  Header:  magic, version, num_groups, registry_version,  │
│           updated_at_snapshot                            │
├──────────────────────────────────────────────────────────┤
│  Group Directory:                                        │
│    Group[0]: uuid, name, type, field_id, partition_spec, │
│              num_segments, segment_index_start            │
│    Group[1]: ...                                         │
│    Group[N]: ...                                         │
├──────────────────────────────────────────────────────────┤
│  Segment List:                                           │
│    Segment[0] (属于 Group[0]):  uuid, puffin_path,        │
│       delta_from_seg_uuid, deprecates_uuids,              │
│       status, staleness_ratio, built_at_snapshot,         │
│       total_rows, num_pages, puffin_file_size,            │
│       file_coverage_format, file_coverage,                │
│       partition_summary                                  │
│    Segment[1] (属于 Group[0]): ...                        │
│    Segment[K] (属于 Group[1]): ...                        │
│    ...                                                   │
└──────────────────────────────────────────────────────────┘
```

### 5.3 关键字段说明

| 字段                     | 位置              | 说明                                                                                         |
| ---------------------- | --------------- | ------------------------------------------------------------------------------------------ |
| `registry_version`     | Header          | 单调递增计数器，每次状态变更 +1。用于缓存失效检测                                                                 |
| `num_segments`         | Group Directory | 该 Group 拥有的 Segment 数量；配合 `segment_index_start` 定位到 Segment List 中的起始位置                    |
| `segment_uuid`         | Segment List    | 每个 segment 的唯一标识。被 `delta_from_seg_uuid` 和 `deprecates_uuids` 引用                           |
| `delta_from_seg_uuid`  | Segment List    | 增量链：指向基础段的 uuid                                                                            |
| `deprecates_uuids`     | Segment List    | 逗号分隔的旧 segment uuid 列表，表示新段取代了哪些旧段                                                         |
| `file_coverage_format` | Segment List    | 0=range 字符串（如 "0-499"），1=Roaring Bitmap。registry 只存摘要，完整映射在各索引 .puffin 的 filebitmap Blob 中 |
| `status`               | Segment List    | 段状态（见 §6）                                                                                  |

### 5.4 文件覆盖的完整映射

registry 中的 `file_coverage` 仅存摘要（如 `"0-499"`），用于索引发现。**完整映射**（file_index ↔ file_path_hash ↔ file_path）存储在各索引 `.puffin` 文件的 `filebitmap-v1` Blob 中。

- `file_index`：构建时对文件排序后从 0 顺序分配的稠密 u32，用于 RoaringBitmap 集合运算
- `file_path_hash`：XXH64(file_path)，用于 RowAddress 跨快照稳定寻址
- 索引 `.puffin` 内的 `filebitmap-v1` Blob 同时包含正反映射：`file_index_map_[]` 和 `hash_to_index_`

## 6. 索引状态机

### 6.1 状态定义

每个 **IndexSegment** 拥有独立的状态：

```
                    ┌─────────────┐
                    │  BUILDING   │  构建中, 查询不可用
                    └──────┬──────┘
                           │ 构建完成
                           ▼
                    ┌─────────────┐
         ┌──────────│   ACTIVE    │──────────┐
         │          └──────┬──────┘          │
         │                 │                  │
         │   文件变更        │   文件变更        │
         │   ratio<0.1      │   ratio>=0.1      │
         ▼                 ▼                  ▼
┌──────────────────┐  ┌──────────────┐  ┌──────────────┐
│  STALE_PARTIAL   │  │  REMAPPING   │  │STALE_ORPHAN  │
│ (跳过stale文件)   │  │ (Rewrite Map │  │ (等待Rebuild │
│ 查询可用 ✓        │  │  转译)       │  │ 或Rewrite Map│
│                  │  │ 查询可用 ✓    │  │ 查询不可用 ✗   │
└────────┬─────────┘  └──────┬───────┘  └──────┬───────┘
         │                   │                  │
         ▼                   ▼                  ▼
         REBUILDING     REBUILDING          REMAPPING
              │              │
              ▼              ▼
           ACTIVE         ACTIVE
         (新segment)    (旧→DEPRECATED)

    DEPRECATED → DELETED (GC)
```

### 6.2 状态速查

| 状态              | 查询可用? | 说明                              |
| --------------- | ----- | ------------------------------- |
| `building`      | ❌     | 构建中，数据不完整                       |
| `active`        | ✅     | staleness_ratio = 0             |
| `stale_partial` | ✅     | ratio < 0.1，跳过少量 stale 文件即可     |
| `remapping`     | ✅     | 有 Rewrite Map，查询时自动转译行地址        |
| `stale_orphan`  | ❌     | ratio ≥ 0.3 或无 Rewrite Map，等待重建 |
| `rebuilding`    | ❌     | 正在重建                            |
| `deprecated`    | ❌     | 已被新 segment 替代                  |
| `deleted`       | ❌     | 可 GC                            |

### 6.3 状态存储

- **权威源**：`index_catalog.puffin` 的 registry Blob
- **交叉验证**：各索引 `.puffin` Footer 中也可存 status（但可能过时）
- 状态变更**只重写** `index_catalog.puffin`（~10KB），不重写索引 `.puffin` 文件

## 7. 需要调用的 Java SDK 接口

本模块通过 JNI 桥接调用 Java Iceberg SDK 完成以下操作。C++ 侧不自行实现 TableMetadata 读写或 Manifest 解析。

### 7.1 TableMetadata 操作

| 接口                                            | 用途                                                                | 调用时机                           |
| --------------------------------------------- | ----------------------------------------------------------------- | ------------------------------ |
| `loadTableMetadata(tablePath)`                | 加载当前表的 metadata（含 snapshots、statistics[]、schemas、partition-specs） | 查询规划、索引构建、维护操作                 |
| `commitStatisticsFile(tablePath, json, mode)` | 提交统计文件注册，原子 commit TableMetadata                                  | 索引构建完成、index_catalog.puffin 更新 |
| `updateIndexStatuses(tablePath, json)`        | 原子更新多个索引 segment 的状态                                              | CoW UPDATE / Compaction 回调时    |

### 7.2 Snapshot / Manifest 操作

| 接口                                       | 用途                                | 调用时机      |
| ---------------------------------------- | --------------------------------- | --------- |
| `getDataFiles(tablePath, snapshotId)`    | 获取 snapshot 下所有 DataFile 列表（含列统计） | 索引构建、查询规划 |
| `diffSnapshots(tablePath, fromId, toId)` | 比较两个 snapshot 的新增/删除文件            | 增量构建差异检测  |

### 7.3 不需要调用的接口

| 不调用                  | 原因                         |
| -------------------- | -------------------------- |
| Java PuffinWriter    | C++ 自行实现，性能更优且避免 JNI 大数据拷贝 |
| Java PuffinReader    | 同上                         |
| Java BlobMetadata 解析 | C++ 自解析 Footer JSON        |

### 7.4 bridge 接口定义

C++ 侧封装的桥接接口：

```cpp
namespace puffin::bridge {

class JavaBridge {
public:
    // 表元数据
    std::optional<TableMeta> load_table_meta(const std::string& path);

    // 提交统计文件 (mode: "append"|"replace"|"update_status")

                                    const StatisticsFileMeta& sfm,
                                    const std::string& mode);

    // 原子更新索引状态
    int64_t update_index_statuses(const std::string& path,
                                   const std::vector<IndexStatusUpdate>&);

    // 数据文件列表
    std::vector<DataFileInfo> get_data_files(const std::string& path,
                                              int64_t snap);

    // 快照差异
    SnapshotDiff diff_snapshots(const std::string& path,
                                 int64_t from, int64_t to);
};

} // namespace puffin::bridge
```

## 9. 索引实现接口（IIndexPlugin）

### 9.1 接口定义

各具体索引（BTree、Bloom、Bitmap、IVF 等）实现此接口，被索引管理模块通过 `IndexRegistry` 工厂调用：

```cpp
class IIndexPlugin {
public:
    virtual ~IIndexPlugin() = default;

    // ====== 标识 ======
    virtual const char* blob_type() const = 0;       // Puffin Blob type 字符串

    // ====== 序列化 (Puffin blob ↔ 内存对象) ======
    virtual bool deserialize(std::span<const uint8_t> data) = 0;
    virtual std::vector<uint8_t> serialize() const = 0;

    // ====== 构建 ======
    virtual void begin_build() {}                    // 重置
    virtual void add_row(const IcebergValue& value,   // 添加一行数据
                         const RowAddress& row_addr) = 0;
    virtual void end_build() {}                      // 最终化
    virtual bool merge(const IIndexPlugin& other)     // 合并 (增量构建)
        { return false; }

    // ====== 查询 ======
    virtual IndexEvalResult evaluate(
        const Expression& expr,
        const RowFilter* filter = nullptr) const = 0;

    // ====== 元数据 ======
    virtual size_t memory_bytes() const = 0;
    virtual size_t estimated_serialized_bytes() const = 0;
};
```

### 9.3 索引实现方的交付物

每个自定义索引类型需要提供：

1. 唯一的 `blob_type` 字符串（如 `"puffin.idx.btree-v1"`）
2. `IIndexPlugin` 子类实现
3. 工厂函数注册到 `IndexRegistry`
4. Blob 序列化格式规范（供跨语言读取）

| Blob Type                        | 粒度          | 用途                         |

### 10.1 被动维护（数据变更触发）

```cpp
class IndexMaintainer {

```

### 10.2 主动维护（后台任务）

```cpp
class IndexMaintainer {
public:
    // 生成 Rewrite Map (异步, 后台)
    void generate_rewrite_maps(const std::string& table_path);

    // 重建 stale segment (异步, ratio >= 0.3 触发)
    void rebuild_stale_indexes(const std::string& table_path);

    // 合并过于分散的增量链 (segments >= 10)
    void defragment_index_group(const std::string& group_uuid);

    // 垃圾回收 deprecated/deleted segment
    void garbage_collect(const std::string& table_path);

    // 删除整个索引组
    void drop_index(const std::string& group_uuid, const std::string& table_path);

    // 强制全量重建
    std::string rebuild_index(const std::string& group_uuid,
                              const std::string& table_path);

    // 校验索引完整性
    struct ValidationReport {
        std::string segment_uuid, status;
        double staleness_ratio;
        size_t total_files, stale_files, active_files;
        bool has_rewrite_map;
    };
    std::vector<ValidationReport> validate_index(const std::string& group_uuid,
                                                   const std::string& table_path);
};
```

### 10.3 维护操作触发条件

| 操作                    | 触发条件                           | 同步/异步    |
| --------------------- | ------------------------------ | -------- |
| mark_files_stale      | CoW UPDATE / Compaction commit | 同步       |
| generate_rewrite_map  | staleness_ratio ≥ 0.1          | 异步       |
| rebuild_stale_indexes | staleness_ratio ≥ 0.3          | 异步       |
| defragment            | delta-from 链长度 ≥ 10            | 异步（低优先级） |
| garbage_collect       | deprecated 超过 TTL              | 异步（低优先级） |
| validate_index        | 运维主动调用                         | 同步       |

### 10.4 MoR DELETE 特别说明

Merge-on-Read DELETE **不触发任何索引维护**。原因：MoR DELETE 只写 delete file，不重写 DataFile。索引返回的 row_addr 在查询引擎读取时会被 delete file 过滤（引擎层行为，索引无需感知）。

## 11. 查询流程

### 11.1 查询时索引使用流程

```
查询: SELECT * FROM t WHERE col = value

1. 分区裁剪 (Manifest List) → 保留相关 Manifest
2. 文件裁剪 (Manifest Entry stats) → 保留候选文件
3. 索引发现:
   → 读 TableMetadata.statistics[] → 找到 index_catalog.puffin
   → 读 index_catalog.puffin Footer + registry Blob (~10KB)
   → 找到 field 匹配的 IndexGroup, 获取其所有 segment 的摘要
4. 安全校验:
   → 对每个 segment, check_index_usability(seg, active_files)
   → SKIP 的 segment 回退全扫描
5. 索引搜索:
   → 对可用 segment, 加载对应 .puffin 中的索引 Blob
   → 调用 IIndexPlugin::evaluate(expr)
6. 结果验证:
   → SAFE_WITH_STALE_SKIP: 过滤掉来自 stale 文件的行
   → USE_WITH_REMAP: Rewrite Map 转译行地址
7. 回表:
   → RowAddress → FileRegistry → Parquet 文件 → Page 定位 → 读数据
8. 合并: 索引命中 ∪ 全扫描回退 → 去重 → 返回
```

### 11.2 查询时索引缓存

索引发现层缓存 `registry_version`，后续查询若版本未变则直接使用内存缓存。索引数据层 LRU 缓存已反序列化的 `IIndexPlugin` 对象（最大 128MB / 1000 条目）。

## 12. 文件覆盖与部分失效

### 12.1 两层文件标识

|      | file_index (u32)   | file_path_hash (u64)   |
| ---- | ------------------ | ---------------------- |
| 作用域  | segment 内部         | 跨 segment / 跨 snapshot |
| 产生方式 | 构建时排序后顺序分配         | XXH64(file_path)       |
| 用途   | RoaringBitmap 集合运算 | RowAddress 寻址          |
| 稳定性  | 同 segment 内稳定      | 跨快照永久稳定                |

### 12.2 部分失效流程

```
CoW UPDATE 重写 part-00001.parquet → part-01000.parquet

1. 文件路径 → XXH64 → hash
2. seg->hash_to_index_[hash] → file_index = 0
3. seg->stale_files.add(0)          ← RoaringBitmap 操作
4. staleness_ratio = 1/500 = 0.002  (< 0.1 → stale_partial)
5. 更新 index_catalog.puffin registry: segment.status = "stale_partial"
6. 查询时: BTree 返回 row_addr 后, 检查 hash→file_index→stale_files.contains()
   → stale 行丢弃, 其余正常使用
```

### 12.3 Rewrite Map

当 staleness 超过阈值（≥ 0.1）时，异步生成 Rewrite Map。它是一个独立的 `.puffin` 文件，记录 `old_file_hash → new_file_hash` 的行范围映射。查询时 BTree 返回的旧地址通过 Rewrite Map 转译为当前快照中的有效地址。
