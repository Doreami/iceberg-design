# Puffin文件介绍

https://github.com/apache/iceberg/blob/main/format/puffin-spec.md



## 是什么

Puffin 是 Apache Iceberg 的配套统计与索引文件格式，用于存储无法放入 Manifest 中的辅助信息。

```
                   Iceberg Table Metadata
                  ┌──────────────────────────┐
                  │  Snapshots               │
                  │  ├── s0                  │
                  │  ├── s1                  │
                  │  │   ├── manifest-list   │──→ ManifestList (Avro)
                  │  │   ├── manifest        │──→ ManifestFile (Avro) ──→ DataFile (Parquet)
                  │  │   └── statistics[]    │──→ Puffin ←── 本文核心
                  │  └── s2                  │
                  └──────────────────────────┘
```

核心设计原则：分离关注点（Manifest 管操作元数据，Puffin 管优化元数据）；可选消费（Reader 忽略 Puffin 不影响正确性）；可扩展（通过 type 字符串标识 Blob 类型）。



## Puffin 文件格式规范

#### 文件布局

```
Offset 0    ┌──────────────────┐
            │  Magic (4 bytes) │  0x50 0x46 0x41 0x31  ("PFA1")
Offset 4    ├──────────────────┤
            │  Blob₁           │  原始索引/统计二进制数据 (变长, 可压缩)
            ├──────────────────┤
            │  Blob₂           │
            ├──────────────────┤
            │  ...             │
            ├──────────────────┤
            │  Blobₙ           │
            ├──────────────────┤ ← Footer 开始
            │  Magic (4B)      │
            ├──────────────────┤
            │  FooterPayload   │  UTF-8 JSON, 可选 LZ4 压缩
            ├──────────────────┤
            │  FooterPayloadSize│ i32 LE (已压缩后长度)
            ├──────────────────┤
            │  Flags (4 bytes) │  bit 0 = Footer LZ4 压缩标志
            ├──────────────────┤
            │  Magic (4B)      │
            └──────────────────┘
```



### Magic Number

```
字节:  0x50 0x46 0x41 0x31
u32 LE: 0x31414650
含义:  "Puffin Fratercula arctica, version 1"
```

### BlobMetadata 字段

| 字段                  | JSON 类型 | 必需  | 说明                          |
| ------------------- | ------- | --- | --------------------------- |
| `type`              | string  | ✅   | Blob 类型标识符                  |
| `fields`            | int[]   | ✅   | Iceberg 字段 ID 列表            |
| `snapshot-id`       | long    | ✅   | 源快照 ID                      |
| `sequence-number`   | long    | ✅   | 源快照序列号                      |
| `offset`            | long    | ✅   | Blob 数据在文件中的起始字节偏移          |
| `length`            | long    | ✅   | Blob 数据字节长度（压缩后）            |
| `compression-codec` | string  | ❌   | `"lz4"` / `"zstd"`；省略 = 不压缩 |
| `properties`        | map     | ❌   | 任意 key-value 元数据            |



## metadata.json对应puffin文件列表

如果 `statisticsFiles` 存在，它通常被序列化为 `statistics` 列表，保存在 `metadata.json` 根级别的 `statistics` 字段中。

- **结构**：根级别的 `statistics` 字段是一个数组，包含一个或多个 `StatisticsFile` 对象。

- **字段**：一个 `StatisticsFile` 对象通常包含以下信息：

- 

| 字段名                         | 类型     | 描述                                                                                    |
| --------------------------- | ------ | ------------------------------------------------------------------------------------- |
| `snapshot-id`               | long   | 关联的快照ID                                                                               |
| `statistics-path`           | string | Puffin文件的存储路径                                                                         |
| `file-size-in-bytes`        | int    | 文件总大小（字节）                                                                             |
| `file-footer-size-in-bytes` | int    | Puffin文件尾（footer）的大小（字节）                                                              |
| `key-metadata`              | string | 加密相关的元数据 (可选)                                                                         |
| `blob-metadata`             | array  | 一个 `BlobMetadata` 对象数组，描述 Puffin 文件内包含的统计信息 Blob 列表，如`type`、`fields`、`snapshot-id`等信息 |



**json示例**

```json
{
  "statistics": [
    {
      "snapshot-id": 1234567890123456789,
      "statistics-path": "s3://my-bucket/my_table/metadata/stats-456.puffin",
      "file-size-in-bytes": 4096,
      "file-footer-size-in-bytes": 1024,
      "blob-metadata": [
        {
          "type": "apache-datasketches-theta-v1",
          "fields": [ 4 ],
          "snapshot-id": 1234567890123456789
        }
      ]
    }
  ]
}

```

## statistics[] 结构

每条自定义索引在 `statistics[]` 中占一条记录。**不压缩、不间接引用**。

Json示例如下：

```json
      "file-footer-size-in-bytes": 512,

        "type": "apache-datasketches-theta-v1",
        "fields": [1],
        "properties": { "ndv": "5000000" }

    // 自定义索引 1: BTree on order_id
```

## properties 字段说明

### 通用字段（所有索引类型）

| 字段                  | 类型     | 必需  | 说明                                                                                                        |
| ------------------- | ------ | --- | --------------------------------------------------------------------------------------------------------- |
| `index-name`        | string | ✅   | 索引名称，唯一标识一个索引。多次 rebuild 保持不变                                                                             |
| `status`            | string | ✅   | `"building"` / `"active"` / `"invalid"`。查询时根据此字段决定是否使用索引                                                  |
| `built-at-snapshot` | long   | ✅   | 构建时的 Iceberg snapshot ID。用于判断索引版本与数据的新旧关系                                                                 |
| `puffin-version`    | string | ✅   | Puffin 文件版本号，从 1 开始每次 rebuild +1。用于生成文件名                                                                  |
| `file-count`        | string | ✅   | 覆盖的 Parquet 文件数量。用于快速判断覆盖范围                                                                               |
| `file-list-hash`    | string | ✅   | 构建时所有覆盖文件路径拼接后的 XXH64 值。查询时对比此值与当前文件列表的 hash，判断文件集是否变更。**hash 计算规则**: 将所有文件路径按字典序排序后拼接(无分隔符)，对拼接结果做 XXH64 |
| `total-rows`        | string | ❌   | 索引覆盖的总行数                                                                                                  |
| `partition-spec-id` | string | ❌   | Iceberg 分区 spec ID。用于分区感知索引                                                                               |

### BTree 索引额外字段

| 字段          | 类型     | 必需  | 说明                                                      |
| ----------- | ------ | --- | ------------------------------------------------------- |
| `num-pages` | string | ❌   | BTree 数据页总数。用于估算搜索代价                                    |
| `key-type`  | string | ❌   | 索引键的类型：`"INT32"` / `"INT64"` / `"STRING"` / `"FLOAT64"` |

### IVF 向量索引额外字段

| 字段          | 类型     | 必需  | 说明                                           |
| ----------- | ------ | --- | -------------------------------------------- |
| `dimension` | string | ✅   | 向量维度，如 `"768"`                               |
| `nlist`     | string | ✅   | K-Means 聚类中心数量                               |
| `nprobe`    | string | ❌   | 查询时探测的聚类数，默认 `sqrt(nlist)`                   |
| `distance`  | string | ✅   | 距离度量：`"l2"` / `"cosine"` / `"inner_product"` |



## 文件变更检测

使用 `file-list-hash` 快速判断索引是否仍然有效：

```
查询时:
  当前 snapshot 的文件列表 → 计算 XXH64
  与 statistics[] 中的 file-list-hash 比较:
    相同 → ACTIVE, 索引可用
    不同 → INVALID, 需要更新 status 并跳过
```

这是一个轻量级的"文件集校验"，不需要加载索引的 Puffin 文件就能判断有效性。

# 索引puffin结构

每个索引的 `.puffin` 文件包含以下 Blob：

```
idx_btree_order_id.puffin
┌──────────────────────────────────────────────┐
│  Blob₀: btree-v1                             │
│    主索引数据 (BTree Page Table + Data Pages)  │
│    Zstd 压缩                                  │
│    大小: 约 16MB (500 文件 × 2048 行 × 12B)   │
├──────────────────────────────────────────────┤
│  Blob₁: filebitmap-v1                        │
│    文件覆盖位图 + file_index 映射表            │
│    包含: original_files (RoaringBitmap)       │
│          file_index_map_[] (每项: hash+path)  │
│    未压缩                                     │
│    大小: 约 60KB                              │
├──────────────────────────────────────────────┤
│  Blob₂: partition-bitmap-v1  (可选)           │
│    分区值 → Page 范围映射                      │
│    大小: 约 9KB (365 分区)                    │
├──────────────────────────────────────────────┤ ← Footer
│  Footer JSON                                  │
└──────────────────────────────────────────────┘
```

```
Blob₁: filebitmap-v1 (同 BTree 索引, ~60KB)
  └── 与上文 BTree 索引的 filebitmap-v1 完全一致

查询流程:
  SELECT * FROM orders ORDER BY embedding <-> query_vector LIMIT 10;

  1. 加载 ivf-flat-v1 Blob → 反序列化 IVF 索引
  2. query_vector → 计算到 1024 个聚类中心的距离
     → 选择最近 nprobe=32 个聚类
  3. 只扫描这 32 个倒排列表中的向量 (~32 × 1000 = 32000 个候选)
     vs 全扫描 1,024,000 个向量 → 缩小 32×
  4. 精确计算 top-10 → 返回 vector_id
  5. vector_id → RowAddress → filebitmap → 回表读 Parquet
```

# Java SDK优先策略

为了快速跑通全流程，**能调用 Java Iceberg SDK 的地方优先使用 Java SDK**：

| 能力                   | 实现方式                                           | 说明                                        |
| -------------------- | ---------------------------------------------- | ----------------------------------------- |
| **Puffin 文件读写**      | **Java SDK** (org.apache.iceberg.puffin) → JNI | 成熟的 PuffinReader/PuffinWriter，避免 C 侧重新实现  |
| **TableMetadata 读写** | **Java SDK** (TableMetadataParser) → JNI       | Iceberg 元数据的唯一可靠操作方式                      |
| **Manifest 解析**      | **Java SDK** → JNI                             | 获取 DataFile 列表、列统计、分区信息                   |
| **Blob 序列化/反序列化**    | **Java SDK** → JNI                             | Puffin Blob 的 add/read 由 Java SDK 处理      |
| **索引构建编排**           | C (openGauss 侧)                                | 轻量编排：获取文件列表 → 读 Parquet → 喂入 IIndexPlugin |
| **索引查询编排**           | C (openGauss 侧)                                | 轻量编排：发现索引 → 加载 → evaluate → 回表            |
| **IIndexPlugin 实现**  | C (openGauss 内核内)                              | 索引计算需与查询引擎零拷贝集成，不能走 JNI                   |
| **openGauss 集成**     | C                                              | ANALYZE hook、系统表缓存                        |

```
                 ┌─────────────────────────────────┐
                 │  Java 虚拟机 (JNI 内嵌)           │
                 │  Iceberg SDK                     │
                 │  • PuffinReader/PuffinWriter     │
                 │  • TableMetadata 读写 commit     │
                 │  • Manifest 解析                 │
                 │  • StatisticsFile 管理           │
                 └──────────────┬──────────────────┘
                                │ JNI
                 ┌──────────────▼──────────────────┐
                 │  openGauss 内核 (C)              │
                 │  • 索引管理编排 (构建/发现/维护) │
                 │  • IIndexPlugin (BTree/IVF/..)   │
                 │  • 查询引擎集成                   │
                 │  • ANALYZE hook / 系统表          │
                 └─────────────────────────────────┘
```

C 侧通过 JNI 直接调用 Java SDK：

```
  puffin_read(file_path)  →  JNI  →  Java: new PuffinReader(path).readBlob(...)
  puffin_write(file_path) →  JNI  →  Java: new PuffinWriter(path).addBlob(...)
  meta_load(table_path)   →  JNI  →  Java: TableMetadataParser.read(...)
  meta_commit(json)       →  JNI  →  Java: UpdateStatistics.commit(...)
  manifest_files(snap_id) →  JNI  →  Java: snapshot.dataFiles()...
```

**后续优化**：当 Puffin 读写成为瓶颈时，可考虑替换为 C 实现（对外接口相同，互换透明）。





# 核心数据结构

```c
/* ====== 索引描述符 ====== */
typedef struct PuffinIndex {
    char        name[128];            /* 索引名称 */
    char        blob_type[128];       /* 索引类型 */
    int32_t     field_id;             /* Iceberg 字段 ID */
    int32_t     partition_spec_id;    /* 分区 spec */

    char       *puffin_path;          /* .puffin 文件路径, malloc'd */
    uint8_t     status;              /* 0=building, 1=active, 2=invalid */
    int64_t     built_at_snapshot;
    int64_t     status_updated_at;

    /* 构建统计 */
    int64_t     total_rows;
    int32_t     num_pages;
    int64_t     puffin_file_size;
    int32_t     puffin_footer_size;

    /* 文件覆盖 (从 .puffin 的 filebitmap Blob 加载) */
    int32_t     file_count;           /* 覆盖的文件数 */
    struct FileMapEntry *file_map;    /* 文件列表, calloc'd */
    uint64_t    file_list_hash;       /* 文件列表的 XXH64 校验 */

    /* 运行时 (非持久化) */
    struct RoaringBitmap *file_bitmap;       /* file_index 位图, 集合运算用 */
} PuffinIndex;

/* ====== 文件映射条目 ====== */
typedef struct FileMapEntry {
    uint64_t    path_hash;            /* XXH64(file_path) */
    char       *file_path;            /* 文件相对路径, malloc'd */
    int64_t     record_count;         /* 文件行数 */
} FileMapEntry;

/* ====== 行地址 ====== */
typedef struct RowAddress {
    uint64_t high;   /* [file_path_hash:48 | rg_index:16] */
    uint64_t low;    /* [row_in_rg:16 | reserved:48] */
} RowAddress;

/* ====== 索引可用性 (简化) ====== */
typedef enum {
    IDX_USABILITY_SAFE   = 0,   /* 可用, 所有文件有效 */
    IDX_USABILITY_SKIP   = 1,   /* 不可用, 回退全扫描 */
} IndexUsability;

/* ====== 索引评估结果 ====== */
typedef enum {
    INDEX_CANNOT_DECIDE = 0,
    INDEX_CAN_SKIP      = 1,
    INDEX_CAN_MATCH     = 2,
    INDEX_EXACT_MATCH   = 3,
} IndexVerdict;

typedef struct IndexEvalResult {
    IndexVerdict verdict;
    char        *reason;
    RowAddress  *exact_rows;
    size_t       exact_row_count;
} IndexEvalResult;

typedef struct RowFilter {
    struct RoaringBitmap *allowed_file_indices;
} RowFilter;
```



## 类型字段说明

**PuffinIndex**

| 字段                   | 持久化位置                                  | 说明                                             |
| -------------------- | -------------------------------------- | ---------------------------------------------- |
| `name`               | statistics[].properties["index-name"]  | 索引名称, 唯一标识。rebuild 时不变, 用于匹配 statistics[] 条目   |
| `blob_type`          | statistics[].blob-metadata[].type      | 决定使用哪个 IIndexPlugin, 如 `"puffin.idx.btree-v1"` |
| `field_id`           | statistics[].blob-metadata[].fields[]  | Iceberg 字段 ID (不是列名)                           |
| `partition_spec_id`  | statistics[].properties                | 分区 spec, 0=非分区                                 |
| `puffin_path`        | statistics[].statistics-path           | Puffin 文件路径, rebuild 后指向新版本                    |
| `status`             | statistics[].properties["status"]      | building / active / invalid                    |
| `built_at_snapshot`  | statistics[].properties                | 构建时的 snapshot ID                               |
| `status_updated_at`  | statistics[].properties                | 最后状态变更时间 (epoch ms)                            |
| `total_rows`         | Puffin Footer properties               | 索引覆盖总行数                                        |
| `num_pages`          | Puffin Footer properties               | BTree 数据页数                                     |
| `puffin_file_size`   | statistics[].file-size-in-bytes        | Puffin 文件大小                                    |
| `puffin_footer_size` | statistics[].file-footer-size-in-bytes | Footer 大小                                      |
| `file_count`         | 运行时 (从 filebitmap Blob 加载)             | 覆盖文件总数                                         |
| `file_map`           | 运行时 (从 filebitmap Blob 加载)             | 文件映射表, 按 file_index 索引                         |
| `file_list_hash`     | statistics[].properties                | 文件列表 XXH64 校验值, 查询时对比判断是否变更                    |
| `file_bitmap`        | 运行时 (从 filebitmap Blob 加载)             | RoaringBitmap, file_index 集合运算用                |

**FileMapEntry**

| 字段             | 说明                                        |
| -------------- | ----------------------------------------- |
| `path_hash`    | XXH64(file_path), 用于 RowAddress 寻址, 跨快照稳定 |
| `file_path`    | 文件相对路径 (含分区目录)                            |
| `record_count` | 该文件总行数                                    |

**RowAddress** — 128-bit 统一行地址, Parquet 版本无关

| 组件             | 位宽      | 说明                             |
| -------------- | ------- | ------------------------------ |
| file_path_hash | 48 bits | XXH64(file_path) 的低 48 位, 标识文件 |
| rg_index       | 16 bits | Parquet Row Group 序号 (0-based) |
| row_in_rg      | 16 bits | Row Group 内的行偏移 (0-based)      |
| reserved       | 48 bits | 保留                             |

**IndexVerdict** — 索引评估结论

| 值             | 含义                 | 查询引擎行为                          |
| ------------- | ------------------ | ------------------------------- |
| CANNOT_DECIDE | 索引无法判断 (如表达式类型不支持) | 回退全扫描该文件                        |
| CAN_SKIP      | 确定文件不包含目标值         | 跳过该文件, 不读取                      |
| CAN_MATCH     | 文件可能包含目标值          | 读取文件, 上层精确过滤                    |
| EXACT_MATCH   | 精确定位到具体行           | 仅读取 exact_rows 指向的 Parquet Page |

**RowFilter** — 搜索范围约束

| 字段                     | 说明                                                                                      |
| ---------------------- | --------------------------------------------------------------------------------------- |
| `allowed_file_indices` | RoaringBitmap (u32), 仅搜索这些 file_index 对应的数据页。对 BTree 可缩小 page_range; Bloom/IVF 可能不使用此参数 |

# 索引实现接口

使用 C vtable pattern。

```c
typedef struct IIndexPlugin IIndexPlugin;

typedef struct {
    // ====== 标识 ======
    const char* (*blob_type)(void);

    // ====== 序列化 (Puffin Blob ↔ 内存对象) ======
    int (*deserialize)(IIndexPlugin *idx, const uint8_t *data, size_t len);
    int (*serialize)(const IIndexPlugin *idx, uint8_t **out_data, size_t *out_len);

    // ====== 构建 (框架调用顺序: begin → add_row × N → end) ======
    void (*begin_build)(IIndexPlugin *idx);
    void (*add_row)(IIndexPlugin *idx, const IcebergValue *value,
                    RowAddress row_addr);
    void (*end_build)(IIndexPlugin *idx);

    // ====== 查询 ======
    IndexEvalResult (*evaluate)(const IIndexPlugin *idx,
                                 const Expression *expr,
                                 const RowFilter *filter);

    // ====== 配置与生命周期 ======
    void   (*configure)(IIndexPlugin *idx, int n_keys,
                        const char **keys, const char **values);
    size_t (*memory_bytes)(const IIndexPlugin *idx);
    void   (*destroy)(IIndexPlugin *idx);
} IIndexPluginVtable;

struct IIndexPlugin {
    const IIndexPluginVtable *vtable;
    void                     *internal;
};
```

#### 接口说明

| 方法                            | 调用阶段     | 说明                                                                                                                             |
| ----------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `blob_type()`                 | 注册时      | 返回 Puffin Blob type 字符串，如 `"puffin.idx.btree-v1"`。框架用此值匹配 Puffin 文件中的 Blob                                                     |
| `deserialize(idx, data, len)` | 查询时      | 将已解压的 Blob 二进制反序列化为内存索引对象。`data` 是解压后的完整 Blob body。成功返回 0。多次调用应覆盖旧状态                                                           |
| `serialize(idx, out, len)`    | 构建完成后    | 将内存索引序列化为 Blob 二进制。`*out` 由实现方 malloc，调用方 free。需与 deserialize 完全互逆                                                             |
| `begin_build(idx)`            | 构建开始     | 重置内部状态，准备接收新数据。之后会连续调用 `add_row`                                                                                               |
| `add_row(idx, value, addr)`   | 构建中 ★热路径 | 喂入一行数据。**全流程最热路径**（百万级调用），应极致优化：无 malloc、无锁。BTree 追加到数组；Bloom 置位；IVF 追加向量                                                      |
| `end_build(idx)`              | 构建结束     | 所有行已喂入，执行最终化。BTree 排序分页；IVF 训练 K-Means。释放构建临时缓冲区                                                                               |
| `evaluate(idx, expr, filter)` | 查询时 ★核心  | 根据谓词评估索引。`filter` 可选约束搜索范围。返回 CAN_SKIP / CAN_MATCH / EXACT_MATCH。`exact_rows` 由实现方 malloc，调用方通过 `puffin_eval_result_free()` 释放 |
| `configure(idx, n, k, v)`     | 构建前（可选）  | 传递索引类型特定参数，如 `"btree.page_size"→"4096"`。不支持的 key 静默忽略                                                                          |
| `memory_bytes(idx)`           | 缓存管理     | 返回当前内存占用字节数，用于 LRU 淘汰决策                                                                                                        |
| `destroy(idx)`                | 生命周期结束   | 释放 `idx->internal` 和 `idx` 本身占用的所有资源                                                                                           |

**注册与创建**：

# 全量构建流程（异步）

```
puffin_index_build_async("s3://bucket/db/orders", 1, "puffin.idx.btree-v1",
                          "btree_order_id")

Phase 1: 注册 (同步, 快速返回)
  ├── 通过 Java SDK 获取当前 snapshot
  ├── 生成唯一 index_name (如果同名索引已存在 → 版本递增重建, 旧版本保留)
  └── 写入 TableMetadata: statistics[] 新增或更新条目, status="building"
      → commit TableMetadata → 立即返回
      → 此时查询看到 status="building" → 跳过该索引, 回退全扫描

Phase 2: 后台构建 (异步, Java 进程或 openGauss bgworker)
  ├── 获取 DataFile 列表 + 列统计
  ├── 按文件路径排序 → 分配 file_index (稠密 u32)
  ├── for each file in files (可并行):
  │     ├── ColumnReader → 批量读取列数据 Page
  │     ├── IIndexPlugin::add_row(value, row_addr) ← 热路径
  │     └── 进度上报
  ├── plugin->end_build()
  └── plugin->serialize() → blob_data

Phase 3: 写入 + 激活 (异步完成)
  ├── Java SDK PuffinWriter:
  │     add_blob(BTREE, blob_data, Zstd)
  │     add_blob(FILEBITMAP, file_bitmap + file_map, none)
  │     (可选) add_blob(PARTITION_BITMAP, ..., none)
  │     finish() → idx_btree_order_id.puffin 写入完成
  ├── 更新 TableMetadata statistics[]:
  │     status: "building" → "active"
  │     file-size-in-bytes, file-list-hash, total-rows 等
  └── commit TableMetadata
      → 查询看到 status="active" → 开始使用索引 ✓
```

**异步构建期间的行为**：

```
ANALYZE TABLE orders COMPUTE STATISTICS FOR COLUMNS order_id;
  → 立即返回 (Phase 1 完成, ~100ms)
  → 索引处于 BUILDING 状态

查询 SELECT * FROM orders WHERE order_id = 42:
  → 遍历 statistics[] → 找到 field=1 的条目 → status="building"
  → 跳过 → 全扫描回退 → 数据正确 ✓
  → 性能暂时未加速（构建完成前）

... 几分钟后 ...

后台构建完成 (Phase 2-3):
  → statistics[] 更新 → status="active"

查询 SELECT * FROM orders WHERE order_id = 42:
  → 遍历 statistics[] → status="active" + file-list-hash 匹配
  → 使用索引 → 加速 ✓
```

**重建**（已有索引，重新构建）：

```
puffin_index_rebuild("btree_order_id"):

  1. 更新 statistics[]: status: "active" → "building" (立即返回)
  2. 后台构建新 Puffin 文件 (新文件名, 带版本后缀)
  3. 构建完成后:
     statistics[] 更新:
       statistics-path → 新文件路径 (带版本号)
       status: "building" → "active"
       file-list-hash → 新文件列表 hash
     → commit TableMetadata
  4. 旧 Puffin 文件不再被当前 statistics[] 引用
     但仍被旧 snapshot 的 metadata.json 引用 → 不能删除!
     等旧 snapshot 过期后 GC 清理

  如果构建失败 (Phase 2-3 失败):
     status 从 "building" 恢复为 "active" (保留旧索引)
     或恢复为 "invalid" (旧索引已不可靠)
     新文件 (未完成) → 加入 orphan 列表 → 立即可删
```

# 查询流程

```
查询: SELECT * FROM orders WHERE order_id = 42

1. 分区裁剪 (Manifest List) → 保留相关 Manifest
2. 文件裁剪 (Manifest Entry stats) → 保留候选文件
3. 索引发现:
   → 遍历 TableMetadata.statistics[]
   → 找到 field=1, status="active" 的条目
4. 有效性检查:
   → 计算当前 snapshot 文件列表的 XXH64
   → 与 file-list-hash 比较:
     一致 → 索引可用 ✓
     不一致 → 更新 status 为 "invalid" → 回退全扫描
5. 加载索引:
   → PuffinReader 打开 statistic-path 指向的 .puffin
   → 加载 btree-v1 Blob → deserialize → BTree 对象
6. 搜索:
   → BTree.search(42)
   → 返回 row_addr = (file_hash, rg, row)
7. 回表:
   → file_hash → filebitmap 中查找 file_index → file_path
   → ParquetPageLocator → 读 Page → 返回数据
8. 如果无可用索引 → 全扫描回退
```

# 索引维护

## 文件变更处理

```
CoW UPDATE / Compaction 重写文件:
  1. 遍历 statistics[] 中所有自定义索引
  2. 对每个索引:
     计算当前 snapshot 文件列表 hash → 与 file-list-hash 比较
     如果不同 → status = "invalid"
  3. 更新 TableMetadata
  4. commit

注意: 简易方案中不区分"哪一个文件变了"。
      任何文件变更 → 整个索引失效 → 用户手动 REBUILD。
      这是故意为之的简化——避免了部分失效和 Rewrite Map 的复杂度。
```

## 增量数据

```
INSERT 新数据:
  不做任何操作。新文件无索引覆盖 → 查询时回退全扫描。
  用户需要时手动执行 puffin_index_rebuild() 全量重建。
```

## MoR DELETE

```
Delete file 在引擎读取层过滤, 索引无感知。
```

## 维护操作触发

| 操作         | 触发条件                           | 同步/异步            | 说明                                         |
| ---------- | ------------------------------ | ---------------- | ------------------------------------------ |
| 标记 invalid | CoW UPDATE / Compaction commit | **同步**（commit 前） | 必须同步：commit 之后查询才能读到正确的 status             |
| 全量构建       | ANALYZE 命令                     | **异步**           | Phase1 同步注册(building) → 立即返回；Phase2-3 后台执行 |
| 全量重建       | 用户手动 / invalid 后触发             | **异步**           | 同上，旧索引保持 active 直到新构建成功                    |
| GC 清理      | 定时 / snapshot 过期回调             | **异步**           | 延迟删除 orphan 文件，不阻塞任何操作                     |

# Puffin 文件生命周期与旧文件清理

## Puffin 文件何时产生、何时过时

```
Snapshot S1: ANALYZE → build → idx_btree_order_id_v1.puffin 写入
  → statistics[] 指向: idx_btree_order_id_v1.puffin
  → S1 的 metadata.json 持久化此引用

Snapshot S2: INSERT 新数据
  → idx_btree_order_id_v1.puffin 不变
  → statistics[] 仍指向它, status 仍为 "active"
  → 但 file-list-hash 已不匹配 (文件列表变了)

Snapshot S3: ANALYZE → rebuild → idx_btree_order_id_v2.puffin 写入 (新文件!)
  → statistics[] 指向 v2, status="active"
  → v1 不再被当前 statistics[] 引用
  → 但 S1 的 metadata.json 仍然引用 v1 → v1 不能删除
  → v1 随 S1 过期 (snapshot TTL) 后 GC 清理
```

## 孤儿文件清理策略

| 策略                | 做法                                                                          | 适用场景                                             |
| ----------------- | --------------------------------------------------------------------------- | ------------------------------------------------ |
| **立即删除**          | rebuild 后直接在 commit 前删除旧文件                                                  | 简单粗暴，但如果在删除和 commit 之间 crash，旧文件已丢、新指针未提交 → 数据丢失 |
| **延迟删除 (推荐)**     | rebuild 后保留旧文件 N 个 snapshot，超过 TTL 后删除                                      | 安全，与 Iceberg snapshot 过期策略一致                     |
| **依赖 Iceberg GC** | 完全不主动删除，依赖 Iceberg metadata 文件过期时连带清理（如果 orphan .puffin 和 metadata 文件在同一目录） | 最简单但有隐患：orphan .puffin 数量可能很大                    |

**推荐策略：延迟删除**

**关键认识**：一个 .puffin 文件可能被多个 snapshot 的 metadata.json 引用。当前 statistics[] 不再引用 ≠ 没有 snapshot 引用它。

```
实现:
  1. rebuild 完成 → 旧 .puffin 文件不再被当前 statistics[] 引用
     但它仍被之前 snapshot 的 metadata.json 引用 → 不能删!

  2. 删除条件 (全部满足):
     a) 不被当前 statistics[] 引用
     b) 不被任何未过期 snapshot 的 metadata.json 引用
     c) 产生它的 snapshot 已过期 (超过 TTL)

  3. 简化实现: 文件名带 snapshot_id
     idx_btree_order_id_snap1005_v3.puffin
     snapshot 1005 过期 → 文件可直接删除
     (无需遍历历史 metadata.json 检查引用)

  4. openGauss restart 后:
     读当前 TableMetadata → 收集活跃文件列表 A
     列出 metadata/ 下 *.puffin → 列表 B
     B 中文件: 提取 snapshot_id → 检查是否过期 → 是 → 可删
     (不依赖内存中的 orphan 列表, 完全从磁盘恢复)
```

## Rebuild 时的原子性保证

rebuild 操作的时序必须保证：**先写新文件，再更新指针，最后删旧文件**。

```
puffin_index_rebuild("btree_order_id"):

  1. 构建新索引 → 写入新 Puffin 文件
     新文件: idx_btree_order_id_v3.puffin  ← 版本号递增
     (旧文件 v1, v2 仍存在于磁盘上)

  2. 更新 TableMetadata:
     statistics[] 中 status 改为 "building"
     statistics-path 改为新文件路径
     ↓
     commit TableMetadata
     ↓
     更新 statistics[]:
       statistics-path: idx_btree_order_id_v3.puffin
       status: "active"
       file-list-hash: (新文件列表的 hash)
     ↓
     commit TableMetadata

  3. 旧文件处理:
     v2 (之前活跃的) → 不再被当前 statistics[] 引用
       → 但被上一个 snapshot 的 metadata.json 引用 → 不能删
       → 等对应 snapshot 过期后 GC 清理
     v1 (更早的) → 如果其 snapshot 已过期 → GC 可删

  如果在步骤 1-2 之间 crash:
    → 新 Puffin 文件已写入但未引用 → 孤儿 → 后续 GC 清理
    → 旧 Puffin 文件仍在 statistics[] 中 → 查询不受影响 ✓

  如果在步骤 2-3 之间 crash:
    → 新 Puffin 已引用, 旧 Puffin 未删除
    → 两个文件都在磁盘上 → 查询用新的, 旧的是孤儿
    → 后续 GC 清理孤儿 ✓
```

## 文件命名与版本管理

**唯一方案: 带版本后缀, 永不覆盖。**

Iceberg 的核心原则是所有文件写入后不可变。覆盖已存在的 Puffin 文件会导致旧 snapshot 的时间旅行查询读到损坏的索引数据。

```
Snapshot S1: ANALYZE → idx_btree_order_id_v1.puffin
  → statistics[] 指向 v1

Snapshot S3: INSERT (无 ANALYZE) → 无新索引文件

Snapshot S5: ANALYZE → rebuild → idx_btree_order_id_v2.puffin (新文件!)
  → statistics[] 指向 v2
  → v1 不再被当前 statistics[] 引用
  → 但 S1 的 metadata.json 仍引用 v1 → v1 不能删!

Snapshot S10 (S1 已过期): GC 检查
  → v1 在过期 snapshot S1 中 → 无活跃 snapshot 引用 → 可安全删除

文件命名规则:
  idx_{index_name}_v{version}.puffin

  version: 从 1 开始单调递增, 每次 rebuild +1
  记录在 statistics[].properties["puffin-version"] 中

覆盖的风险 (不可接受):
  S1 引用了 idx.puffin → rebuild 覆盖了它
  → S1 时间旅行查询: 读 idx.puffin
  → 内容是为 S5 构建的, 与 S1 的文件集不匹配
  → BTree 返回的 row_addr 指向 S1 不存在或不同的文件
  → 查询结果错误或崩溃 ✗
```

## Snapshot 过期时的联动

```
Iceberg snapshot 过期流程:
  1. Iceberg 引擎标记 snapshot S1, S2, S3 过期
  2. 相关 Manifest 和 DataFile 标记可删除
  3. 本模块收到 snapshot 过期通知:
     → 扫描 orphan_puffin 列表
     → 检查: 该 orphan 是在 snapshot S1 时产生的吗?
       如果是 → 且 S1 已过期 → 可以安全删除
       如果否 → 且产生它的 snapshot 还未过期 → 保留

不主动联动的情况:
  如果无法收到 snapshot 过期通知 (没有 hook):
    → GC 基于时间: orphan 产生超过 N 天后删除
    → N = snapshot TTL + 安全窗口期 (如 TTL=7天, 安全窗口=3天 → 10天)
    → 这是保守估计, 确保没有活跃查询引用它
```
