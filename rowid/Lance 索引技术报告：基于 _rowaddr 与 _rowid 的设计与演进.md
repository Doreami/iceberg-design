# Lance 索引技术报告：基于 `_rowaddr` 与 `_rowid` 的设计与演进

## 1. 引言

Lance 是一个专为高性能数据湖和 AI 工作负载设计的列式存储格式。其索引系统在设计上具有鲜明的特点：它将**数据存储**与**索引结构**解耦，使得索引可以独立于表格式进行演进。

在 Lance 中，标识一行数据存在两种形式：**物理地址（`_rowaddr`）** 和**逻辑 ID（`_rowid`）**[reference](http://lance.org/format/table/row_id_lineage/#__codelineno-14-5)。理解这两者的区别与联系，是理解 Lance 索引设计哲学的关键。

## 2. Lance 的行标识符体系

### 2.1 物理地址：`_rowaddr`

`_rowaddr` 代表一行数据在表中的**物理位置**。它是一个 64 位整数，编码了两个 32 位值)：

- **`fragment_id`**：数据所在的片段（Fragment）ID。

- **`local_row_offset`**：该行在片段内的偏移量。

公式为：`row_address = (fragment_id << 32) | local_row_offset`。

`_rowaddr` 的主要特点是：

- **高效随机访问**：通过位运算即可提取出 `fragment_id` 和 `offset`，实现快速定位。

- **非永久稳定**：当数据因压缩（Compaction）或更新（Update）而重组时，行的物理地址会发生变化。

### 2.2 逻辑 ID：`_rowid`

`_rowid` 是一行数据的**逻辑标识符**。它的核心特性是**稳定性**。

- **稳定行 ID（Stable Row ID）**：当数据集创建时启用稳定行 ID 功能后，每一行都会被分配一个**唯一的、自动递增的 `u64` 标识符**。这个 ID 在行的整个生命周期内都保持不变，**即使其物理位置（`_rowaddr`）因压缩等操作而改变**。

- **默认行为**：如果未启用稳定行 ID，`_rowid` 列（如果请求）则**不稳定**，不应作为持久标识符使用。在默认模式下，`_rowid` 实际上等于 `_rowaddr`。

### 2.3 两种标识符的对比

| 特性       | `_rowaddr` (物理地址) | `_rowid` (逻辑 ID) |
| -------- | ----------------- | ---------------- |
| **本质**   | 物理位置              | 逻辑标识符            |
| **稳定性**  | 不稳定，随数据重组而变化      | 稳定，行生命周期内不变      |
| **用途**   | 索引的**主要**指针       | 提供稳定的行引用         |
| **是否暴露** | 是，作为系统列           | 是，作为系统列          |
| **可变性**  | 数据变更时改变           | 数据变更时保持不变        |

## 3. Lance 索引的现状：基于 `_rowaddr`

### 3.1 索引设计原则

Lance 的索引被设计为独立于数据文件的可选冗余结构)。它们具有以下特点：

- **按需加载**：数据集打开时不会加载任何索引，仅在查询需要时才加载。

- **渐进式加载**：查询时只加载索引的必要部分，例如 B-Tree 索引只加载相关的页。

- **不可变性**：索引文件一旦写入就不可变，更新通过创建新文件实现。

### 3.2 索引分类

Lance 支持三大类索引：

1. **标量索引（Scalar Indices）**：加速对整数、时间戳、字符串等标量数据的查询，包括 Zone Map、B-Tree、Bitmap 和全文搜索索引。

2. **向量索引（Vector Indices）**：专门用于高维向量的近似最近邻（ANN）搜索，支持 IVF、HNSW 等算法。

3. **系统索引（System Indices）**：辅助内部表维护和行标识符解析，如 `Fragment Reuse Index`，用于压缩后的高效重映射。

### 3.3 当前的指针机制

**目前，Lance 的所有二级索引（包括标量索引、向量索引、全文搜索索引）都使用 `_rowaddr` 来引用数据行**。

这意味着：

- 索引的叶子节点存储的是 `_rowaddr` 值。

- 查询时，索引返回一组 `_rowaddr`，Lance 引擎可以利用 `_rowaddr` 直接定位并读取数据行。

Lance 官方文档明确指出，存在一个专门的 **`RowIdIndex`** 结构，用于将 `_rowid` 映射到对应的 `_rowaddr`。`RowIdIndex` 存储了不相交的 `_rowid` 范围到 `_rowaddr` 范围的映射，并提供 `get(row_id) -> Option<RowAddress>` 方法来进行查询。

## 4. 未来演进：索引指向 `_rowid`

### 4.1 演进方向

Lance 官方路线图明确指出，**正在推进让索引支持稳定的 `_rowid`**。这一工作已在官方文档中被明确标注为“**进行中（in progress）**”。

### 4.2 目标与优势

这一演进的核心目标是解决当前基于 `_rowaddr` 的索引在数据重组时面临的**维护难题**。

- **当前痛点**：当发生 Compaction 时，数据行物理位置（`_rowaddr`）改变，所有指向这些行的索引（标量、向量等）都需要**重映射（remap）或完全重建**。

- **未来方案**：让索引指向稳定的 `_rowid`。Compaction 后，只需维护一个轻量级的 **`_rowid` 到 `_rowaddr` 的映射**即可。这可以极大地降低索引的维护成本。

### 4.3 关键支撑技术

为了实现这一演进，Lance 已经或正在构建以下关键组件：

- **`RowIdIndex` (行 ID 索引)**：这是一个系统索引，用于将 `_rowid` 映射到 `_rowaddr`。它将是未来所有索引实现稳定引用的基础。

- **`Fragment Reuse Index` (片段重用索引)**：这是一个系统索引，支持压缩后的高效重映射。

- **稳定行 ID 分配协议**：Lance 使用单调递增的 `next_row_id` 计数器来分配稳定行 ID，并采用类似乐观锁的协议来处理冲突。

## 5. 总结

Lance 的索引系统正处在一个关键的演进阶段。

- **当前状态**：所有索引均基于**物理地址（`_rowaddr`）**，这提供了极致的查询性能，但带来了索引在数据重组后的维护成本。

- **未来方向**：索引将逐步迁移到基于**逻辑 ID（`_rowid`）**，通过一个轻量级的映射层（`RowIdIndex`）来实现逻辑到物理的转换，从而在保持高性能的同时，大幅降低索引的维护复杂度。

这一演进体现了 Lance 在设计上的前瞻性：通过引入稳定的逻辑标识符，解决了高性能列式存储中索引维护的根本性难题，为构建大规模、高吞吐的数据系统奠定了更坚实的基础。





# Lance 索引维护与增量构建机制

## 一、Lance 的写入模型：一切操作都是“新增”

理解索引变化的前提，是理解 Lance 的底层写入模型。

> 和传统数据库不同，Lance 不直接在原文件上修改数据，而是通过**新增文件**和**更新元数据**来产生新的表版本。

无论是 `INSERT`、`UPDATE`、`DELETE` 还是 `MERGE`，所有修改数据的操作都会**创建新文件**，而不是原地修改。

这意味着：

- 每次 DML 都会生成一个新的 **表版本（Version）**

- 旧版本的数据文件**不会被删除**，以支持时间旅行（Time Travel）

- 每个版本通过 **Manifest** 描述当前表的完整状态

---

## 二、各 DML/DDL 操作对索引的影响

### 2.1 INSERT（新增数据）

| 维度           | 说明                                         |
| ------------ | ------------------------------------------ |
| **数据变化**     | 写入新的数据文件（Fragment）                         |
| **索引变化（当前）** | 新数据**不会自动加入**现有索引                          |
| **查询影响**     | 未索引的新数据会触发**暴力扫描（exhaustive search）**，影响延迟 |
| **处理策略**     | 需要手动触发增量索引构建（`optimize()`）                 |

**增量索引**：LanceDB 支持**增量索引（Incremental Reindexing）**，无需删除旧索引从零重建，只需将新增数据加入索引即可。

### 2.2 DELETE（删除数据）

| 维度           | 说明                                                 |
| ------------ | -------------------------------------------------- |
| **数据变化**     | **不重写数据文件**，而是写入 **Deletion Vector（删除向量）** 标记被删除的行 |
| **索引变化（当前）** | 索引条目**不会自动删除**，仍指向已被标记删除的行地址                       |
| **查询影响**     | 查询时，读取层会过滤 Deletion Vector 中标记的行，但索引仍可能返回已删除行的地址   |
| **处理策略**     | 需要重建索引以清理已删除行的条目，或依赖 `RowIdIndex` 仅返回存活行的映射        |

**Deletion Vector 存储**：Deletion Vector 持久化为 **DeletionFile**，记录 fragment 内被删除的 local row offsets。

### 2.3 UPDATE（更新数据）

| 维度           | 说明                                            |
| ------------ | --------------------------------------------- |
| **数据变化**     | **删除 + 插入**的组合：旧行写入 Deletion Vector，新行写入新数据文件 |
| **索引变化（当前）** | 旧行的索引条目失效（指向已删除行）；新行未索引                       |
| **查询影响**     | 更新后的行在索引中**不可搜索**，查询会退化到暴力扫描                  |
| **处理策略**     | 大批量更新后应**重建索引**                               |

### 2.4 Compaction（文件合并）

| 维度           | 说明                                              |
| ------------ | ----------------------------------------------- |
| **数据变化**     | 读取旧 Fragments 中的存活行，写入新的 Fragment               |
| **索引变化（当前）** | **旧 row address 全部失效**——这是 Compaction 对索引最严重的影响 |
| **查询影响**     | 所有索引（向量索引、标量索引、全文索引）都可能指向无效地址                   |
| **处理策略**     | 索引需要 remap（重映射）或完全重建                            |

Compaction 会合并小文件以提升读写性能，但由于所有修改数据的操作都会创建新文件，如果这些操作频繁，Compaction 也需要频繁运行。

---

## 三、当前索引机制（基于 `_rowaddr`）的维护挑战

### 3.1 问题根源

当前，**所有二级索引（向量索引、标量索引、全文索引）都通过 `_rowaddr` 引用数据行**。而 `_rowaddr` 在 Compaction 或 Update 后会改变。

这意味着：

| 操作             | 索引失效范围            | 修复代价          |
| -------------- | ----------------- | ------------- |
| **INSERT**     | 新数据未索引            | 增量加入即可        |
| **DELETE**     | 已删除行的索引条目残留       | 需清理或重建        |
| **UPDATE**     | 旧条目失效 + 新条目缺失     | 需清理并重建        |
| **Compaction** | **全量失效**（所有旧地址无效） | 需 remap 或全量重建 |

### 3.2 Compaction 后的索引 remap

Lance 在 Compaction 时支持 **索引重映射（Index Remapping）**：

- 通过 `optimize()` 的 `remap_options` 参数控制

- 本质是将旧 `_rowaddr` 映射到新的 `_rowaddr`

- 但 remap 的成本随索引规模和 Compaction 数据量增长

> Compaction 如何挑选 fragment，以及为什么需要 index remap。

---

## 四、未来索引机制（基于 `_rowid`）的演进

Lance 官方正在推进让索引支持稳定的 `_rowid`。

### 4.1 演进后的维护对比

| 操作             | 当前（基于 `_rowaddr`） | 未来（基于 `_rowid`）                    |
| -------------- | ----------------- | ---------------------------------- |
| **INSERT**     | 新数据未索引，需增量构建      | 新数据获得新 `_rowid`，增量加入索引             |
| **DELETE**     | 索引条目残留，需清理        | 通过 `RowIdIndex` 过滤，仅返回存活行          |
| **UPDATE**     | 旧条目失效 + 新条目缺失     | 旧 `_rowid` 不变（逻辑删除），新行获得新 `_rowid` |
| **Compaction** | **全量 remap 或重建**  | **只需更新 `_rowid → _rowaddr` 映射**    |

> Stable Row ID：让索引指向稳定逻辑行 ID → compaction 后只需要维护 row_id → row_address 映射 → **降低索引 remap 成本**

---

## 五、增量索引构建流程

### 5.1 触发方式

LanceDB 提供 `optimize()` 方法触发索引维护：

```python
table.optimize()  # 执行 Compaction + 索引更新 + 清理
```

`optimize()` 执行三种维护操作：

1. **Compaction**：合并小 Fragment

2. **Pruning/Cleanup**：清理超过保留期限（默认 7 天）的旧版本文件

3. **Index Update**：将新增数据加入现有索引

### 5.2 增量索引的工作原理

当新数据被添加时，查询会**结合现有索引与对新数据的暴力扫描：

- 已索引数据：通过索引快速检索

- 未索引数据：通过暴力扫描（exhaustive/flat search）兜底

这种设计确保了**查询结果的完整性**，但代价是未索引数据越多，查询延迟越高。

### 5.3 监控与调优

| 工具                 | 用途                     |
| ------------------ | ---------------------- |
| `index_stats()`    | 查看未索引行数，为 0 时表示索引完全最新  |
| `fast_search=True` | 强制只搜索已索引数据，避免暴力扫描的延迟波动 |
| `wait_for_index()` | 等待异步索引构建完成             |

### 5.4 增量 vs 全量重建

| 方式       | 适用场景             | 优缺点             |
| -------- | ---------------- | --------------- |
| **增量索引** | 常规数据追加           | 无需删除旧索引，只处理新增数据 |
| **全量重建** | 大批量更新后、数据分布剧烈变化后 | 代价高但能彻底清理失效条目   |

---

## 六、总结

| 操作             | 当前索引影响（基于 `_rowaddr`） | 未来索引影响（基于 `_rowid`）   | 维护策略                             |
| -------------- | --------------------- | --------------------- | -------------------------------- |
| **INSERT**     | 新数据未索引                | 新 `_rowid` 加入索引       | 定期执行 `optimize()` 增量构建           |
| **DELETE**     | 条目残留                  | 通过 `RowIdIndex` 过滤    | 重建索引或依赖映射过滤                      |
| **UPDATE**     | 旧条目失效 + 新条目缺失         | 旧 `_rowid` 保留，新行获新 ID | 大批量更新后重建索引                       |
| **Compaction** | **全量 remap 或重建**      | **仅更新映射**             | 使用 `optimize(remap_options=...)` |

**核心结论**：

1. **当前 Lance 索引基于 `_rowaddr`**，Compaction 是全量失效的最大风险点，需要 remap 或重建

2. **未来 Lance 索引将基于 `_rowid`**，Compaction 后只需维护轻量级映射，索引维护成本大幅降低

3. **增量索引构建**通过 `optimize()` 触发，新增数据会先通过暴力扫描兜底，再逐步加入索引
