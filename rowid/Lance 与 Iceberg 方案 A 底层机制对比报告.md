# Lance 与 Iceberg 方案 A 底层机制对比报告

## 1. 概述：两种实现，同一机制

本报告对比两种存储系统的底层实现机制：

- **Lance**：将 `_rowid` 作为系统列物理存储，并内置 `RowIdIndex` 自动维护映射

- **Iceberg + 用户自建（方案A）**：用户自行扩展实现，将 `_row_id` 作为物理列写入，并自行维护外部映射

**核心观点**：两者在机制设计上**本质相同**——都是物理存储 `_row_id`，并通过一个映射层将逻辑ID转换为物理地址。唯一的区别在于“谁来实现这个机制”。

---

## 2. 机制层面的完整对比

| 机制维度                    | Lance                                          | Iceberg + 用户自建（方案A）                                    |
| ----------------------- | ---------------------------------------------- | ------------------------------------------------------ |
| **`_row_id` 是否物理存储**    | ✅ 是，作为系统列存储                                    | ✅ 是，用户扩展 Writer 作为普通列写入                                |
| **`_row_id` 分配机制**      | 系统维护单调递增计数器，原子分配                               | 用户自行维护全局计数器（需保证并发安全）                                   |
| **`_row_id` 唯一性保证**     | 系统保证全局唯一                                       | 用户自行保证（需处理并发冲突）                                        |
| **`_row_id` 稳定性**       | 开启稳定行ID后，行生命周期内不变                              | 用户需自行保证（写入后不再修改）                                       |
| **二级索引指向**              | `_rowid`                                       | `_row_id`                                              |
| **映射层是否存在**             | ✅ 存在：`RowIdIndex` 将 `_rowid` 映射到 `_rowaddr`    | ✅ 存在：用户自行维护外部映射表 `(_row_id → file_path, row_position)` |
| **映射层粒度**               | `_rowid → (fragment_id, local_row_offset)`     | `_row_id → (file_path, row_position)`                  |
| **映射层存储**               | 系统内置，存储在 Lance 数据集元数据中                         | 用户自行选择存储（RocksDB、TiKV等）                                |
| **映射层更新**               | 系统在 Compaction 时自动更新                           | 用户需在 Compaction 后自行感知并更新                               |
| **索引在 Compaction 后的状态** | 索引完全不受影响（指向的 `_rowid` 不变）                      | 索引完全失效，除非映射层及时更新                                       |
| **数据读取路径**              | 索引 → `_rowid` → `RowIdIndex` → `_rowaddr` → 数据 | 索引 → `_row_id` → 外部映射 → `(file_path, row_pos)` → 数据    |
| **ACID 保证**             | 系统事务机制原生保证                                     | 用户需自行实现（与 Iceberg 事务绑定）                                |
| **与社区/生态兼容性**           | 完全兼容，是 Lance 官方设计                              | 极易与社区未来实现冲突                                            |

## 3. 存储层实现对比

| 存储维度              | Lance                              | Iceberg + 用户自建（方案A）               |
| ----------------- | ---------------------------------- | --------------------------------- |
| **`_rowid` 存储位置** | Lance 数据文件的系统列                     | Iceberg Parquet/ORC 文件的用户列        |
| **`_rowid` 编码**   | 专用编码（如 `RowIdSequence`），高效存储单调递增序列 | 作为普通 `BIGINT` 列存储，无特殊优化           |
| **映射层存储位置**       | Lance 数据集内部，作为系统索引                 | 用户自行选择的外部存储系统                     |
| **存储开销**          | `_rowid` 列 + `RowIdIndex`（系统级优化）   | `_row_id` 列 + 外部映射表（用户级管理）        |
| **写入流程**          | Lance Writer 原生写入 `_rowid` 列       | 用户扩展 Writer，在写入时计算并写入 `_row_id` 列 |
| **读取流程**          | Lance Reader 原生读取 `_rowid` 列       | 用户需扩展 Reader 才能读取 `_row_id` 列     |

## 4. 各场景下的行为对比

### 4.1 INSERT 场景

| 场景              | Lance                           | Iceberg + 用户自建（方案A）        |
| --------------- | ------------------------------- | -------------------------- |
| **`_rowid` 分配** | 系统原子分配新的 `_rowid`               | 用户需从全局计数器获取并分配新的 `_row_id` |
| **`_rowid` 存储** | 系统自动写入数据文件                      | 用户需在 Writer 中手动写入          |
| **映射层更新**       | 系统自动插入 `(_rowid → _rowaddr)` 映射 | 用户需同步或异步写入外部映射表            |
| **索引更新**        | 增量索引构建自动处理新数据                   | 用户需自行将新 `_row_id` 加入索引     |

### 4.2 DELETE 场景

| 场景              | Lance                                    | Iceberg + 用户自建（方案A）       |
| --------------- | ---------------------------------------- | ------------------------- |
| **数据变化**        | 写入 Deletion Vector                       | 写入删除文件（Delete File），标记行删除 |
| **`_rowid` 状态** | 逻辑删除，`_rowid` 保持不变                       | `_row_id` 保持不变            |
| **映射层**         | `RowIdIndex` 不删除映射，查询时过滤 Deletion Vector | 用户需自行决定如何处理外部映射表中的已删除行    |
| **索引影响**        | 索引条目残留，但查询时通过 Deletion Vector 过滤         | 索引条目残留，需用户自行清理            |

### 4.3 UPDATE 场景

| 场景             | Lance                        | Iceberg + 用户自建（方案A） |
| -------------- | ---------------------------- | ------------------- |
| **实现方式**       | DELETE + INSERT（逻辑删除旧行，写入新行） | 同左（DELETE + INSERT） |
| **旧 `_rowid`** | 保持不变，标记删除                    | `_row_id` 保持不变，标记删除 |
| **新 `_rowid`** | 新行分配新的 `_rowid`              | 新行分配新的 `_row_id`    |
| **映射层**        | 系统自动插入新行映射                   | 用户需为新行插入映射，并清理旧行映射  |
| **索引影响**       | 旧条目失效（指向已删除行），新行未索引          | 同左                  |

### 4.4 Compaction 场景

| 场景              | Lance                                             | Iceberg + 用户自建（方案A）              |
| --------------- | ------------------------------------------------- | -------------------------------- |
| **实现方式**        | 读取存活行，写入新 Fragment                                | 读取存活行，写入新数据文件                    |
| **`_rowid` 状态** | **保持不变**（这就是稳定 `_rowid` 的核心价值）                    | `_row_id` **保持不变**               |
| **物理地址变化**      | `_rowaddr` 彻底改变                                   | `(file_path, row_position)` 彻底改变 |
| **映射层处理**       | **系统自动更新** `RowIdIndex` 中的 `_rowid → _rowaddr` 映射 | **用户需自行处理**：删除旧文件的所有映射，插入新文件的映射  |
| **索引影响**        | **索引完全不受影响**（指向的 `_rowid` 没变）                     | **索引完全失效**，除非用户及时更新映射层           |
| **维护难度**        | 系统自动，用户无感知                                        | 极高，需精确追踪 Compaction 涉及的文件范围      |

## 5. 数据流对比图

### Lance 的数据流

```textile
写入路径：
数据 → Lance Writer → 分配 _rowid → 写入数据文件（含 _rowid 列）
                                    → 更新 RowIdIndex（_rowid → _rowaddr）

查询路径（通过索引）：
WHERE name = 'Alice' → 索引检索 → 得到 _rowid=12345
                    → 查询 RowIdIndex → 得到 _rowaddr=0x5002A
                    → 解析 _rowaddr → fragment_id=5, offset=42
                    → 直接读取数据

Compaction 后：
索引仍指向 _rowid=12345 → RowIdIndex 已自动更新为 0x8003B → 数据读取不受影响
```

### Iceberg + 用户自建（方案A）的数据流

```textile
写入路径：
数据 → 用户扩展 Writer → 分配 _row_id → 写入数据文件（含 _row_id 列）
                                      → 用户写入外部映射表（_row_id → file_path, row_pos）

查询路径（通过索引）：
WHERE name = 'Alice' → 索引检索 → 得到 _row_id=12345
                    → 查询用户维护的外部映射表 → 得到 (file_path, row_pos)
                    → 读取数据文件对应行

Compaction 后：
索引仍指向 _row_id=12345 → 映射表未更新（file_path 已无效）→ 查询失败/读到错误数据
用户需自行：识别 Compaction → 找出新旧文件 → 删除旧条目 → 扫描新文件插入新条目
```

## 6. 本质一致性总结

| 对比维度               | Lance                 | Iceberg + 用户自建（方案A）    |
| ------------------ | --------------------- | ---------------------- |
| **机制本质**           | 物理存储 `_rowid` + 映射层转换 | 物理存储 `_row_id` + 映射层转换 |
| **机制是否相同**         | **是**（逻辑架构完全一致）       | **是**（逻辑架构完全一致）        |
| **谁来实现**           | Lance 系统              | 用户自己                   |
| **谁维护映射**          | Lance 系统              | 用户自己                   |
| **谁处理 Compaction** | Lance 系统              | 用户自己                   |
| **谁保证 ACID**       | Lance 系统              | 用户自己                   |

**核心结论**：

1. Lance 和用户自建的方案A，在**机制设计层面完全相同**——都是物理存储 `_row_id`，并通过映射层将逻辑 ID 转换为物理地址。

2. 唯一的区别是**实现主体**：
   
   - Lance：系统内置，自动处理分配、存储、映射维护、Compaction 联动
   
   - 用户自建：需要用户自己实现所有这些逻辑

3. 用户自建方案A 的风险来源于“实现复杂度”，而非“机制不可行”。如果用户能够完整实现所有子模块（`_row_id` 分配、物理存储、外部映射、Compaction 联动、ACID 保证），其机制与 Lance 完全对等。

4. Lance 的本质是把方案A 从“需要用户自建的复杂模块”变成了“系统内置的标准能力”。
