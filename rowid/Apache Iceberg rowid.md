# Apache Iceberg `_row_id` 详细报告

## 一、引言

Apache Iceberg 在 V3 版本中引入了一项重要的数据管理能力——**行级血缘（Row Lineage）**，其核心就是 `_row_id` 字段。`_row_id` 是一个**稳定、唯一的行标识符**，为每一行数据赋予了“身份证”，使得数据湖具备了传统数据库中才有的精确行级操作和追踪能力。

本报告将系统性地阐述 `_row_id` 的定义、工作原理、核心作用及应用场景。

## 二、核心概念

### 2.1 什么是 `_row_id`

`_row_id` 是 Iceberg V3 表中的一个**元数据列（Metadata Column）**，类型为 `BIGINT`。当一行数据被插入到 Iceberg V3 表时，它会被分配一个**在整个表生命周期内保持不变的唯一标识符**。

> **关键特性**：`_row_id` 一旦分配，即使该行被更新多次，其 `_row_id` 也**永远不会改变**。这使其成为追踪行数据全生命周期变更历史的理想锚点。

### 2.2 配套字段：`_last_updated_sequence_number`

与 `_row_id` 协同工作的还有一个重要字段——`_last_updated_sequence_number`（最后更新序列号）。它记录了该行最后一次被修改时所对应的 Iceberg 快照序列号。

这两个字段共同构成了行级血缘的基础：

- **`_row_id`**：回答“这是哪一行？”

- **`_last_updated_sequence_number`**：回答“这行最后被谁、在什么时候修改过？”

## 三、工作原理

### 3.1 `_row_id` 的分配机制

当新数据写入 Iceberg V3 表时，每个数据文件都会被分配一个**起始行 ID（`first_row_id`）**。该文件中每一行的 `_row_id` 通过以下公式计算：

text

_row_id = first_row_id + row_position

其中 `row_position` 是该行在数据文件中的位置偏移量。事务会追踪下一个可用的 `_row_id`，并为每个文件分配连续的 `_row_id` 范围。

### 3.2 `_row_id` 的读取方式

在扫描数据时，`_row_id` 可以通过以下方式获取：

| 优先级 | 来源                             | 说明             |
| --- | ------------------------------ | -------------- |
| 1   | 数据文件中的物理 `_row_id` 列           | 如果文件已物化该列，直接读取 |
| 2   | `first_row_id + FILE_POSITION` | 如果文件仅有元数据，动态计算 |

对于升级到 V3 的表（原 V2 表），`_row_id` 可能尚未物化到所有数据文件中，此时引擎会通过 `first_row_id + row_position` 动态计算。

### 3.3 快照级别的 `first_row_id`

每个快照（Snapshot）都会记录其 `first_row_id` 和新增行总数。这使得查询引擎可以快速判断：

- 某个快照包含的 `_row_id` 范围

- 哪些快照可能包含目标行

## 四、核心作用

### 4.1 行级血缘追踪（Row Lineage）

这是 `_row_id` 最核心的价值。传统的表级或列级血缘只能回答“哪个任务写入了这张表”，而**行级血缘**可以精确回答：

- 哪些**具体的行**被影响了？

- 被**哪个操作**影响的？

- 在**什么时间**影响的？

> **实际场景**：金融公司每日对账时发现结算表出现差异。通过查询 `_row_id` 和 `_last_updated_sequence_number`，可以精确定位哪些行在哪个批次中被修改，以及这些行在批次运行前是否已被修改过。

### 4.2 增量读取（Incremental Read）

`_row_id` 使得精确的增量读取成为可能。通过追踪快照的 `first_row_id`，引擎可以：

- 只读取特定快照之后**新增**的数据行

- 结合 `_last_updated_sequence_number`，读取**发生变更**的数据行

这使得 CDC（变更数据捕获）管道可以高效地只拉取变化的数据，而非全表扫描。

### 4.3 数据合规与审计

在 GDPR 等数据隐私法规的背景下，`_row_id` 提供了关键的合规能力：

- **删除确认**：当收到用户的数据删除请求时，可以通过 `_row_id` 确认相关行已被彻底删除，且未被后续的 MERGE 或重处理任务重新引入

- **审计追溯**：可以精确追踪某一行数据从插入到当前状态的全部变更历史

### 4.4 精确的行级操作

`_row_id` 为精确的行级 UPDATE、DELETE、MERGE 操作提供了基础。传统数据湖的更新操作往往需要重写整个文件或分区，而有了 `_row_id`，引擎可以精确定位到需要操作的具体行，大幅减少不必要的 I/O。

### 4.5 二级索引的基础

如之前讨论的，`_row_id` 的稳定性和唯一性使其成为构建二级索引的理想基础：

- 索引可以存储 `(索引键 → _row_id)` 的映射

- 查询时通过索引找到 `_row_id`，再回表读取完整数据

- 由于 `_row_id` 稳定，索引在数据更新时无需重建

## 五、应用场景

### 5.1 实时 CDC 管道

```textile
源系统 → 变更数据 → Iceberg V3 表（带 _row_id）
                              ↓
                   增量扫描（基于 _row_id 和快照）
                              ↓
                   下游消费（只处理新增/变更的行）
```

### 5.2 数据对账与差异分析

通过比较两个快照之间 `_row_id` 的变化，可以精确识别：

- 哪些行是新增的

- 哪些行被修改了（`_last_updated_sequence_number` 变化）

- 哪些行被删除了

### 5.3 数据版本回滚与回溯

由于每一行都带有 `_last_updated_sequence_number`，可以回溯该行在任意历史快照中的状态，实现“时间旅行”到行级别。

### 5.4 数据质量监控

监控特定 `_row_id` 范围的数据变更频率，识别异常的数据更新模式（如某行被过于频繁地修改）。

## 六、限制与注意事项

### 6.1 仅支持 V3 表

`_row_id` 是 Iceberg **V3** 格式的特性，V1 和 V2 表不支持。升级 V2 表到 V3 时，`_row_id` 的分配需要特殊处理。

### 6.2 数据文件需包含 `first_row_id` 元数据

查询 `_row_id` 列要求数据文件包含 `first_row_id` 元数据。如果缺失，查询将报错。

### 6.3 压缩（Compaction）需保留行级元数据

执行 `OPTIMIZE` 或 `rewriteDataFiles` 等压缩操作时，写入的新数据文件必须保留 `_row_id` 和 `_last_updated_sequence_number` 的值，否则行级血缘将失效。

### 6.4 `_row_id` 的唯一性保证

Iceberg 保证在**表级别** `_row_id` 是唯一的。但在以下情况需注意：

- 升级 V2→V3 时，需小心处理 `_row_id` 的分配以避免重复

- 分支（Branch）和标签（Tag）场景下的 `_row_id` 管理仍需关注

### 6.5 引擎支持差异

不同的计算引擎对 `_row_id` 的支持程度不同：

- **Spark 4.1+**：完整支持

- **StarRocks v4.1+**：支持查询 `_row_id` 和 `_last_updated_sequence_number`

- **Impala**：通过隐藏列支持

- **Dremio**：完整支持

建议在使用前确认目标引擎的兼容性。

## 七、总结

| 维度       | 说明                                         |
| -------- | ------------------------------------------ |
| **本质**   | Iceberg V3 表的行级唯一标识符（BIGINT）               |
| **计算方式** | `first_row_id + row_position`              |
| **核心特性** | 一旦分配，永不改变                                  |
| **主要用途** | 行级血缘追踪、增量读取、数据合规、精确行级操作                    |
| **适用版本** | Iceberg V3 及以上                             |
| **生态支持** | Spark 4.1+、StarRocks v4.1+、Impala、Dremio 等 |

`_row_id` 代表了数据湖从“粗粒度文件管理”向“细粒度行级管理”演进的关键一步。它为数据工程师提供了传统数据库才有的行级追踪能力，使得数据湖在**数据质量、合规审计、实时数据处理**等场景下具备了更强的竞争力。对于构建下一代数据湖仓一体架构，理解和善用 `_row_id` 将成为一项核心能力。
