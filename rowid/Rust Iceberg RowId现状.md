## Rust Iceberg SDK `_row_id` 支持现状总结

### 一、核心问题：元数据就绪，数据操作缺失

Rust Iceberg SDK 对 `_row_id` 的支持处于一个**中间态**：

| 层面        | 支持状态  | 说明                                            |
| --------- | ----- | --------------------------------------------- |
| **元数据读取** | ✅ 已支持 | 可解析 V3 表的 `firstRowId`、`row_id_field()` 定义等   |
| **数据写入**  | ❌ 未实现 | Writer 不会自动将 `_row_id` 写入 Parquet 文件          |
| **数据读取**  | ❌ 未实现 | Reader 不会计算 `firstRowId + row_position` 返回给用户 |

### 二、根本原因

按 Iceberg V3 Spec，`_row_id` 是**元数据列（Metadata Column）**，其值应由 Reader 动态计算：

```textile
_row_id = DataFile.firstRowId() + 文件内行位置
```

但 **Rust SDK 0.9.1 在读写两侧均未实现此逻辑**：

- Writer 不写入 `_row_id` 物理列

- Reader 也不动态计算

相比之下，Java SDK 已在读写两侧完整实现（Writer 将 `_row_id` 作为物理列写入，Reader 可直接读取）。

### 三、社区进展

- **元数据层**：自 0.8.0 已就绪，`Snapshot.first_row_id()` 等 API 可用

- **数据层**：完整读写支持仍在开发中，暂无明确发布时间表

- **社区状态**：基础已打好，但完整功能尚待贡献者推动

### 四、自行实现的挑战

1. **写入侧**：需扩展 `ParquetWriter`，在快照提交时获取 `firstRowId`，为每行计算并写入 `_row_id` 列

2. **读取侧**：需扩展 `ArrowReader`，在投影阶段识别 `_row_id` 请求，动态计算并填充该列

3. **额外风险**：即使手动将 `_row_id` 写入 Parquet 文件，SDK 的 Reader 也**无法自动识别和读取**，因为缺少字段 ID 映射逻辑

### 五、结论与建议

| 维度              | 结论                                      |
| --------------- | --------------------------------------- |
| **当前 Rust SDK** | 可操作 V3 表元数据，但 **无法通过查询获得 `_row_id` 列值** |
| **是否可自行实现**     | 技术上可行，但需深度改造 Writer 和 Reader，投入较大       |
| **最佳策略**        | 关注社区进展，等待官方完整支持，暂缓自行实现                  |

> **一句话总结**：Rust SDK 能读 `_row_id` 的“说明书”（元数据），但还不能真的“拿到”它（数据值）。



# 自定义实现`rowid`方案

目前，Rust SDK 在 `_row_id` 支持上仍处于早期阶段。官方提供了识别 `_row_id` 的基础“零件”，如 `RESERVED_FIELD_ID_ROW_ID` 常量和 `row_id_field()` 函数，但数据层面的完整读写实现仍需社区推动。

在 Rust SDK 中自行实现 `_row_id` 支持，主要可以归纳为两种方案。它们的核心区别在于 **`_row_id` 的值的产生和获取时机**。

这两种方案并非互斥，在社区的未来实现中，很可能会结合使用。

### 方案对比：物理存储 vs 动态计算

| 特性               | 方案一：物理存储 (Physical Storage)                     | 方案二：动态计算 (Dynamic Computation)         |
| ---------------- | ----------------------------------------------- | -------------------------------------- |
| **核心思路**         | 写入时，将 `_row_id` 作为一个普通列**直接写入**数据文件（如 Parquet）。 | 读取时，不读取物理列，而是根据元数据**现场计算**出 `_row_id`。 |
| **实现位置**         | 主要在 **写入器 (Writer)**                            | 主要在 **读取器 (Reader)**                   |
| **`_row_id` 来源** | 数据文件中的一个**物理列**                                 | `first_row_id` + `row_position`        |
| **优点**           | **查询效率高**，无需计算；逻辑直观，与普通列无异。                     | **存储成本低**，无需额外列；**实现更灵活**，不依赖写入侧改造。    |
| **缺点**           | **存储成本增加**；需要深度改造写入器。                           | **查询有额外计算开销**；读取器需处理元数据与行号。            |

## 方案一：物理存储 (Physical Storage)

此方案最接近 Java SDK 的实现方式。核心是在数据写入阶段就将 `_row_id` 持久化。

### 实现要点

1. **扩展 Writer**：在 `ParquetWriter` 或其他格式的写入逻辑中，增加一个 `_row_id` 列。

2. **分配 ID**：写入时，从 Iceberg 表的元数据（如 `TableMetadata`）获取或维护一个全局的 `next_row_id`，为每个批次的数据分配连续的 `_row_id`。

3. **写入文件**：将计算好的 `_row_id` 作为数据的一列，写入 Parquet 等数据文件。

### 物理存储方案的风险

此方案的核心是在写入数据文件时，将 `_row_id` 作为一个物理列直接存储。

- **与社区路线图偏离的风险**：这是最核心的风险。一旦社区官方实现了 `_row_id`，其内部实现逻辑、字段处理方式可能与你的自实现不同。届时，你的自实现表可能无法直接使用社区新特性，甚至可能因元数据不兼容而无法被社区版 SDK 读取，导致技术栈被“锁定”。

- **破坏 ACID 事务语义的风险**：`_row_id` 的分配必须与 Iceberg 的事务提交原子性地发生。在并发写入场景下，如果自实现的 ID 生成与分配逻辑有误，可能导致 ID 冲突或空洞，破坏表的数据一致性。

- **破坏 `_row_id` 稳定性的风险**：Iceberg 规范要求 `_row_id` 在行的整个生命周期内保持不变。自实现必须确保在 `UPDATE`、`MERGE`、`OPTIMIZE` 等所有操作下，`_row_id` 都不变。这需要深入理解并正确实现所有数据重写场景，否则行级追踪将不可靠。

- **存储与性能开销**：增加一个 `_row_id` 列会带来额外的存储成本（尤其是大数据量下），并在写入时引入额外的计算和 I/O 开销。

- **维护与升级负担**：自实现的代码需要与 Rust SDK 的未来版本保持兼容，升级 SDK 时可能需要反复修改和测试你的定制代码，维护成本高。

### 指定field id的风险

虽然在自实现时，你可以强行将列的 `field_id` 设置为 `RESERVED_FIELD_ID_ROW_ID`（`2147483540`），但Rust SDK并不会将其识别为官方的 `_row_id` 元数据列。

根据Iceberg规范，元数据列的值要么存储在数据文件中，要么在读取时动态计算。`RESERVED_FIELD_ID` 的作用是在**读取时**触发SDK的内置计算逻辑，而不是赋予一个普通列特殊身份。

**为什么不建议这样做？强行指定会导致一系列严重问题：**

- **Schema校验失败**：Iceberg在写入时会校验Schema，不允许用户列使用系统保留的ID。你可能会被强制绕过校验，为后续使用埋下隐患。

- **SDK处理逻辑冲突**：读取时，SDK看到这个保留ID，会尝试**动态计算** `_row_id` 的值。这会导致你存储在文件中的物理值被**覆盖或忽略**，你写入的数据永远无法被正确读取。

- **数据不一致**：同一个表里，部分文件有物理 `_row_id` 列，部分没有，会造成数据分裂和不一致。

- **生态兼容性灾难**：任何遵循Iceberg规范的工具（如Spark、Flink）在读取这张表时，都会因Schema冲突而报错，导致表无法被其他生态工具使用。

**总结**

强行将自实现的 `rowid` 列设置为保留ID，结果是 **“写进去了，但读不出来”**。这种做法不仅无法实现预期功能，还会破坏表的元数据一致性，使其与整个Iceberg生态不兼容。

这再次印证了之前讨论的结论：**自行实现 `_row_id` 的方案风险极高，强烈不建议采用**。最稳妥的方式仍是等待官方实现。

### 不指定field id的风险

如果你不指定 `field_id` 为系统保留的 `RESERVED_FIELD_ID_ROW_ID`（即 `2147483540`），而是使用一个普通的用户字段 ID（例如 `1`、`2` 或 `100`），那么对于 Iceberg SDK、Rust SDK 以及所有上层计算引擎（Spark、Flink、DataFusion 等）来说，**这仅仅是一列由用户自行定义的、名为 `row_id`（或任意名字）的普通 BIGINT 列。**

它和 `_row_id` 虽然名字可能相似，但在系统层面有着本质的区别。具体表现如下：

#### 1. SDK 层面的表现（普通列）

- **读写方式**：SDK 会按照处理普通列的标准流程来处理它。写入时，它会被作为 Parquet 文件中的一个普通列存储；读取时，它会作为 `RecordBatch` 或 DataFusion `DataFrame` 中的一个普通数字列返回。

- **Schema 解析**：只要 `field_id` 不在保留范围内，Iceberg 的 Schema 校验就会认为这是一个合法的用户列，不会触发任何关于“系统列”的特殊处理逻辑。

#### 2. 计算引擎层面的表现（用户数据）

- **查询**：在 DataFusion 或 Spark SQL 中，你可以使用 `SELECT my_row_id FROM table` 来查询它，也可以对它进行 `WHERE my_row_id > 100` 的过滤或 `GROUP BY` 聚合。

- **优化器**：引擎会将这列当成普通数据，并根据列的值进行谓词下推（例如，如果将其设为排序列，可能会利用 Parquet 的元数据过滤），但这**完全取决于列值和文件统计信息**，与 Iceberg 的行级血缘（Row Lineage）机制无关。

#### 3. 核心区别：Iceberg 内部机制无视该列

这是最关键的一点。即使你在文件中写入了自增的 `my_row_id`，Iceberg 的**核心 V3 特性（如增量扫描、行级血缘、`_last_updated_sequence_number` 联动）依然不会生效**。

- **增量扫描**：增量扫描依赖的是快照的 `first_row_id` 元数据，而不是数据文件里的普通列。因此，**你的这一列对于区分“哪个是新增数据”毫无作用**。

- **稳定性**：Iceberg 不会保证这列的值在 `UPDATE`、`MERGE` 或 `OPTIMIZE`（压缩）后保持不变。当数据文件被重写时，如果你没有在业务逻辑中显式维护该列，它的值可能会丢失、重复或错乱。

#### 总结

这就像一个“**自定义的业务主键**”：

| 特性         | 官方 `_row_id`                  | 自实现的普通 `row_id` 列 |
| ---------- | ----------------------------- | ----------------- |
| **系统身份**   | 系统列，受 Iceberg 规范保护            | 用户列，系统不关心其语义      |
| **存储方式**   | 物理存储或动态计算（由引擎决定）              | 物理存储（由用户写入）       |
| **唯一性保证**  | 由 Iceberg 全局 `next-row-id` 保证 | 由用户业务逻辑保证         |
| **增量扫描支持** | ✅ 内部通过元数据 `first_row_id` 支持   | ❌ 无关，无法用于增量范围剪枝   |
| **稳定性**    | 随行生命周期稳定（规范保证）                | 用户需自行维护（重写时极易失效）  |

**结论**：这样做虽然不会破坏表的元数据，解决了“数据冲突”的问题，但它**实际上只是一个带自增属性的业务字段**，并没有将 Iceberg 的 `_row_id` 能力带到 Rust 生态中。如果你需要的是真正的 `_row_id` 语义（增量 CDC、行级追踪），这种自实现方式依然无法满足需求。

## 方案二：动态计算 (Dynamic Computation)

此方案更符合 Iceberg V3 规范中 `_row_id` 作为“元数据列”的原始定义。它要求在读取数据时，根据文件的元数据动态计算出 `_row_id`。

### 实现要点

1. **扩展 Reader**：在 `ArrowReader` 或类似的读取逻辑中，增加对 `_row_id` 这个“虚拟列”的处理。

2. **获取元数据**：在读取 `FileScanTask` 时，获取其对应数据文件的 `first_row_id`。

3. **动态计算**：在将数据转换为 `RecordBatch` 的过程中，对于每一行，根据其在文件中的位置 `row_position`，实时计算出 `_row_id = first_row_id + row_position`。

### 动态计算方案的风险

此方案的核心是在读取数据时，根据 `first_row_id` 和行号动态计算出 `_row_id`。

- **破坏 `_row_id` 稳定性的风险（同样存在）**：动态计算方案同样需要面对 `_row_id` 稳定性的挑战。虽然你不需要在写入时存储它，但在 `UPDATE` 等操作后，旧行被标记删除、新行写入，如何保证“逻辑上同一行”的 `_row_id` 不变，依然是一个需要正确处理的复杂问题。

- **高昂的查询性能开销**：每次查询都需要为每一行执行一次加法和可能的元数据查找，这会显著增加查询的 CPU 时间，并降低整体吞吐量。

- **与计算引擎的兼容性问题**：如果上层查询引擎（如 DataFusion）期望 `_row_id` 是一个普通列，而你的实现是动态计算的，可能导致接口不匹配或优化器无法下推谓词，影响查询性能。

- **实现复杂度高**：需要在 Rust SDK 的读取路径（`ArrowReader`）上进行深度定制，处理 `FileScanTask`、`first_row_id` 的传递和行号的计算，实现难度高且容易出错。

- **维护与升级负担（同样存在）**：动态计算方案的代码侵入性同样很强，升级 SDK 时需要反复适配，维护成本高。

## 两种方案的通用风险

除了各自特有的风险，两种方案还面临一些共性问题：

- **表升级（V1/V2 → V3）的兼容性风险**：自实现需要处理从旧版本升级上来的表，这些表的历史数据可能没有 `_row_id`。如何为这些历史数据分配或计算 `_row_id`，是一个需要谨慎处理的难题。

- **生态工具兼容性风险**：你的自实现表可能无法被其他期望标准 `_row_id` 行为的 Iceberg 生态工具（如 Spark、Flink）正确识别和处理。

### 总结与建议

| 风险维度      | 物理存储方案          | 动态计算方案        |
| --------- | --------------- | ------------- |
| **核心风险**  | 存储成本增加，写入性能开销   | 查询性能严重下降      |
| **实现难度**  | 高（需改造写入路径）      | 高（需改造读取路径）    |
| **稳定性风险** | 高（需保证所有场景下ID不变） | 高（同上）         |
| **社区兼容性** | 差（极易与官方实现冲突）    | 差（实现路径可能完全不同） |
| **维护成本**  | 高               | 高             |

**总体建议**：除非有无法妥协的极端性能要求，否则**强烈不建议自行实现 `_row_id`**。两种方案都伴随着巨大的技术债务和不确定性。最稳妥的方式是**等待 Apache Iceberg Rust 官方团队实现此功能**，并在此期间积极关注社区动态。如果情况紧急，可以考虑在 Java/Scala 生态中使用成熟的 Iceberg 实现（如 Spark）作为过渡。

## 混合方案

一个更完善的实现可能是**混合方案**：

- **写入时**：仍然物理写入 `_row_id` 列，以提升查询性能。

- **读取时**：优先读取物理列；如果物理列不存在（例如，处理历史数据时），则回退到动态计算的方式。Impala 等引擎的实现思路与此类似。

## 总结与建议

| 维度        | 方案一：物理存储        | 方案二：动态计算      |
| --------- | --------------- | ------------- |
| **实现难度**  | 较高，需改动写入核心逻辑    | 中等，需改动读取核心逻辑  |
| **性能影响**  | 写入略慢，读取很快       | 写入无影响，读取有计算开销 |
| **存储成本**  | 增加一列存储          | 无额外存储         |
| **规范符合度** | 更贴近 Java SDK 实现 | 更贴近 V3 规范定义   |

**选择建议**：

- 如果**查询性能是首要目标**，且能接受存储成本的增加，**方案一（物理存储）** 是更直接的选择。

- 如果希望**最小化对现有写入流程的改动**，并愿意在读取时付出一些计算代价，**方案二（动态计算）** 是一个不错的起点。

- 最理想的长期方案是**混合模式**，这也是社区未来可能演进的方向。

建议持续关注 [Apache Iceberg Rust 项目](https://github.com/apache/iceberg-rust) 的进展，以便在官方实现相关功能时，能平滑地迁移到标准方案。

# 社区现状

目前，Rust SDK 在 `_row_id` 支持上仍处于早期阶段。官方提供了识别 `_row_id` 的基础“零件”，如 `RESERVED_FIELD_ID_ROW_ID` 常量和 `row_id_field()` 函数，但数据层面的完整读写实现仍需社区推动。

根据目前能查阅到的官方资料，**Apache Iceberg Rust SDK 项目组尚未就 `_row_id` 的具体实现方案发布公开的路线图或倾向性说明**。

不过，我们可以从 Rust SDK 的现状、Iceberg 社区的整体讨论以及 Iceberg 规范本身，来推断其未来的可能路径。

### 📜 现状与规范：奠定基础

Rust SDK 目前仅停留在元数据层面，例如定义了 `RESERVED_FIELD_ID_ROW_ID` 常量，但尚未实现 `_row_id` 的读写功能。未来的实现一定会遵循 Iceberg V3 规范，该规范明确了 `_row_id` 的核心机制。近期社区也通过投票明确了表升级时 `_row_id` 的分配策略，以确保其可靠性。

### 🔮 两种方案的权衡与推测

虽然官方未明确表态，但我们可以分析两种方案的利弊，以及哪种更可能成为首选。

**1. 物理存储方案：性能优先**

- **思路**：写入时直接将 `_row_id` 作为一列存入 Parquet 文件。

- **优势**：查询时**无需计算，性能最好**，逻辑也最直观。

- **推测**：Java SDK 采用的就是这种“存储”方式。作为参考实现，这很可能是 Rust SDK 未来会遵循的方向。

**2. 动态计算方案：存储优先**

- **思路**：读取时根据 `first_row_id + row_position` 动态计算。

- **优势**：**不占用额外存储空间**，实现也相对轻量。

- **劣势**：每次查询都有**额外的计算开销**。

### 🚀 最终推测：混合模式或是终点

一个更成熟的实现，很可能是**混合模式**：

- **写入时物理存储**：保证最优的查询性能。

- **读取时兼容计算**：作为保底方案，确保那些因历史原因没有物理存储 `_row_id` 的老数据也能被正确读取。

这个模式能兼顾性能与兼容性，也可能是社区未来的最终目标。

### 💎 总结

总而言之，官方目前尚未明确选边站队。但基于 Iceberg 生态的惯例（如 Java SDK）和规范的发展，**Rust SDK 最终很可能优先采用“物理存储”方案**，并可能在此基础上发展出兼具两种方案优势的**混合模式**。
