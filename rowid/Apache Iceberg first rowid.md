# firstRowId

`firstRowId` 是 Apache Iceberg 表格式中**行级血缘（Row Lineage）** 功能的基石。它是一个**元数据（Metadata）属性**，本身不存储在数据文件中，而是为 Iceberg v3 表的每一行数据分配一个**稳定、唯一**的标识符（`_row_id`）提供了基础。`

### 🧬 定义：`firstRowId` 是什么？

`firstRowId` 是一个长整型（Long）数值，表示**一个数据文件或一个快照中，第一条新写入数据行所被分配到的 `_row_id` 值**。

- **在数据文件（Data File）层面**：它记录了该文件中第一条数据的 `_row_id`。

- **在快照（Snapshot）层面**：它记录了该快照中，第一个被提交的数据文件里第一条数据的 `_row_id`。

### ⚙️ 工作原理：`firstRowId` 如何运作？

Iceberg 依赖 `firstRowId` 这个元数据来为每一行数据生成唯一的 `_row_id`，其核心计算公式为：

> **`_row_id` = `firstRowId` + `row_position`**

- **`firstRowId`**：从数据文件或快照的元数据中获取。

- **`row_position`**：该行在数据文件内部从 0 开始的位置偏移量。

### 📍 存储位置：`firstRowId` 在哪？

`firstRowId` 存储于 Iceberg 表的元数据（Metadata）中，主要有两个位置：

1. **清单文件（Manifest File）**：每个清单文件都会记录其包含的数据文件的 `firstRowId` 信息。

2. **表快照（Table Snapshot）**：每个快照的元数据中，会记录其 `first-row-id`。

### 💡 关键应用场景

#### 1. 查询 `_row_id` 列

查询引擎（如 StarRocks）在解析对 `_row_id` 的查询时，会读取数据文件的 `firstRowId` 元数据，并结合行号动态计算出每一行的 `_row_id。如果数据文件缺失 `firstRowId` 元数据，查询将会失败。

#### 2. 数据重写（Compaction）时保留行ID

在进行 `OPTIMIZE` 或 `rewriteDataFiles` 等数据重写操作时，Iceberg v3 规范要求将 `_row_id` 写入新数据文件的**物理列**中。这样，新文件在重写后可以直接读取物理列中的 `_row_id`，而无需依赖 `firstRowId` 元数据，从而保证了行ID的稳定性和查询效率。

### ⚠️ 注意事项：表升级与 `firstRowId`

将一个现有的 v1 或 v2 表升级到 v3 格式时，已存在的旧行**不会立即获得** `_row_id` 和 `firstRowId`。这些旧行的行ID会保持为 `null`，直到它们因数据重写（Rewrite）操作被重新写入时，才会被分配新的 `_row_id`。

### 💎 总结

`firstRowId` 是 Iceberg v3 实现行级追踪的关键元数据，它为每一行数据分配唯一 ID（`_row_id`）提供了基础。它存储在元数据而非数据文件中，并在数据重写等场景下需要特殊处理以保证行ID的稳定性。

# 补充问题

## 快照级firstRowId在什么场景下会发生变更.

快照级（Snapshot-level）的 `firstRowId` **一旦被创建，其值本身就不会再发生变更**。

它就像一个历史快照的“身份证号”，一旦生成就固定下来，用于唯一定义该快照内新增数据的 `_row_id` 起始范围。

不过，在以下几种场景下，与 `firstRowId` 相关的行为或状态会发生变化：

### 1. 创建新快照时：分配新的 `firstRowId`

这是最核心的场景。每当有新的数据写入（如执行 `INSERT`、`MERGE` 等操作）并生成一个新的快照（Snapshot）时，系统就会为这个**新快照**分配一个全新的 `firstRowId`。

- **分配机制**：系统会维护一个全局的 `next_row_id`（下一个可用的行ID）。创建新快照时，当前的 `next_row_id` 值就会被用作新快照的 `firstRowId`。

- **ID范围**：该快照内所有新增数据行的 `_row_id` 都将从这个 `firstRowId` 开始，连续分配。

### 2. 表升级（V1/V2 → V3）时：`firstRowId` 的分配策略

这是社区正在演进的一个重要场景。将一张现有的 V1 或 V2 表升级到 V3 时，历史数据原本没有 `_row_id`。

- **旧方案（存在缺陷）**：最初的规定是，旧数据行只有在被**重写（Rewrite）** 时才会被分配 `_row_id`，这导致在新旧数据并存期间，行ID功能不可靠。

- **新方案（社区投票通过）**：为了解决这个问题，社区已投票通过一个新方案：
  
  1. **首次写入时分配**：表升级后，发生的**第一次写入操作**（即使是向空表写入），就会为**所有现存的历史数据行**分配 `_row_id`。
  
  2. **继承机制**：任何新增的或已存在但没有 `first_row_id` 的数据文件，都应通过“继承”等方式被分配一个。任何没有 `first_row_id` 的清单文件（Manifest），在写入清单列表（Manifest List）时也必须被分配一个。

- **核心思想**：这个变化的核心是确保 `firstRowId` 在表升级后能尽快、尽可能完整地覆盖所有数据，让行级追踪功能变得更可靠。

### 3. 数据重写（Rewrite）时：保留与继承

当执行 `OPTIMIZE` 或 `rewriteDataFiles` 等操作时，会生成包含重新组织后数据的新文件，并创建一个新的快照。

- **新快照**：这个新快照会拥有自己的 `firstRowId`。

- **数据继承**：新文件中的数据行会**继承并保留它们原有的 `_row_id`**，以确保行ID的稳定性。

- **元数据更新**：新文件的 `first_row_id` 元数据会被正确设置，以反映其包含的行的起始ID。

### 4. 快照过期（Expire）时：移除旧的 `firstRowId`

当执行 `expire_snapshots` 操作清理过期快照时，被删除的旧快照及其对应的 `firstRowId` 记录也会被一同移除。这虽然不改变现存快照的 `firstRowId`，但会改变表的元数据历史。

### 💎 总结

可以把 `firstRowId` 想象成快照的“出生证明”：

- **一旦“出生”（快照被创建），其 `firstRowId` 就终身不变**。

- 它本身是一个**只读的历史标记**，用于定义该快照中数据的行ID范围。

- 相关的变化主要体现在**新快照的创建**、**表升级时对历史数据的补分配**，以及**数据重写时的继承与保留**上。

## INSERT语句`firstRowId`的变化情况

示例为：初始状态有数据的rowid为1-10共10行，执行insert插入5行数据后`firstRowId`的变化情况。

### 说明

**快照级 `firstRowId` 并不代表该快照下所有数据的最小 `rowId`，而是专指该快照中“新增数据”的起始 `rowId`**

### 结合示例理解

- **初始状态**：表中有10行数据，`rowId` 为 1 到 10。当前快照 `S1` 的 `firstRowId` 为 **1**。

- **执行 INSERT**：你执行了一条 `INSERT` 语句，向表中添加了5行新数据（`rowId` 11 到 15）。

- **关键变化**：这个 `INSERT` 操作会创建一个**新的快照**，我们称之为 `S2`。

- **新快照的 `firstRowId`**：`S2` 的 `firstRowId` **不会是 1**。根据定义，它记录的是这个新快照中**第一条新增数据**的 `rowId`。因此，`S2` 的 `firstRowId` 应该是 **11**。

### 总结

所以，快照级 `firstRowId` 的变更逻辑如下：

1. **它从不“回溯”**：`firstRowId` 不会去记录快照中已存在的老数据的最小ID。

2. **它只“向前看”**：它记录的是**本次操作新增数据**的起始ID。

3. **核心机制**：系统内部维护着一个 `next-row-id`。每当有新数据加入，系统就会从 `next-row-id` 开始分配 `rowId`，并将这个起始值作为新快照的 `firstRowId`，同时更新 `next-row-id`。

因此，在 `INSERT` 之后：

- 快照 `S1` 的 `firstRowId` 仍为 **1**（代表它新增了 rowId 1-10）。

- 新快照 `S2` 的 `firstRowId` 为 **11**（代表它新增了 rowId 11-15）。

## UPDATE流程

在 Iceberg 内部，`UPDATE` 是一个组合操作，本质上是先“标记删除”旧行，再“插入”新行。

1. **标记删除（逻辑删除）**：
   
   - 找到满足条件的旧行（比如 `row_id = 5`）。
   
   - 生成一个**删除文件（Delete File）**，记录下该行的位置。
   
   - 这**不会**改变旧行原有的 `_row_id`。

2. **插入新行（新数据）**：
   
   - 将更新后的新行数据写入**新的数据文件（Data File）**。
   
   - 系统会为这个新行分配一个**全新的 `_row_id`**（比如从全局的 `next-row-id` 中获取，假设为 `16`）。

3. **提交快照（Snapshot）**：
   
   - 这个“标记删除”和“写入新数据”的组合操作，会作为一个整体提交，并生成**一个新的快照**（我们称之为 `S3`）。

### 新快照 `S3` 的 `firstRowId`

现在，我们来看新快照 `S3` 的 `firstRowId` 是什么：

- **定义回顾**：快照级的 `firstRowId`，记录的是**该快照中新增数据**的起始 `rowId`。

- **应用于 `S3`**：在 `S3` 中，确实**有新增的数据**（即更新后的新行），它的 `_row_id` 是 `16`。

- **结论**：因此，快照 `S3` 的 `firstRowId` **就是 `16`**。

### 总结：分清“行”和“快照”

为了彻底解决矛盾，我们可以这样区分：

- **对于被更新的旧行**：它的 `_row_id` **保持不变**（依然是 `5`），只是被标记为已删除。它不会获得新的 `_row_id`。

- **对于 UPDATE 操作本身**：因为它包含“插入新行”的动作，所以在它生成的**新快照**中，`firstRowId` **会被分配一个新的数值**（即新插入行的起始ID）。

所以，结论是：**`UPDATE` 操作会为它产生的新快照分配一个新的 `firstRowId`**。

## DELETE 操作：逻辑删除，无新ID

`DELETE` 操作不会物理移除数据，而是进行逻辑删除。

- **操作方式**：执行 `DELETE` 时，Iceberg 不会去修改原有的数据文件。相反，它会生成一个新的 **"删除文件"（Delete File）**，这个文件记录了被删除行的位置信息。这个删除文件会被关联到一个**新的快照（Snapshot中)**。

- **`firstRowId` 逻辑**：由于这个新快照**没有新增任何数据行**（`addedRows` 为 0），它的 `firstRowId` 字段为 **`null`**，或者不设置具体的值。快照的 `operation` 类型会被标记为 `delete`。

简单来说，`DELETE` 是“标记删除”，新快照只记录“哪些行被删了”，没有新数据加入，所以没有 `firstRowId`。

## FirstRowId分配逻辑

> 下一个快照的 `firstRowId` **并不是**通过上一个快照的 `firstRowId + addedRows` 计算得来的。

### 核心机制：从全局的 `next-row-id` 分配

`firstRowId` 的分配遵循一个更直接的机制：**系统会维护一个全局的、不断递增的“下一个可用行ID”（`next-row-id`）**。

当一个新快照因数据写入操作（如 `INSERT` 或 `UPDATE`）而被创建时，系统会：

1. **取出**当前全局的 `next-row-id` 值。

2. **分配**这个值作为新快照的 `firstRowId`。

3. **更新**全局的 `next-row-id`，将其增加该快照新增的行数（`addedRows`）。

### 为什么不是简单的加法？

你提出的公式 `上一个快照的 firstRowId + 上一个快照的 addedRows` 在**大多数情况下**确实等于下一个快照的 `firstRowId`，但这只是一个**巧合**，而非其定义的**原因**。

关键在于，`firstRowId` 的分配是基于一个**全局的、独立的状态（`next-row-id`）**，而不是依赖对上一个快照的简单计算。

用你之前的例子来说明会更清晰：

1. **初始状态**：全局 `next-row-id` 为 `1`。

2. **创建快照 S1（INSERT 10行）**：
   
   - `S1.firstRowId` = 当前 `next-row-id` = **1**。
   
   - 更新全局 `next-row-id`：`1 + 10 = 11`。

3. **创建快照 S2（INSERT 5行）**：
   
   - `S2.firstRowId` = 当前 `next-row-id` = **11**。
   
   - 更新全局 `next-row-id`：`11 + 5 = 16`。

在这个场景中，`S2.firstRowId (11)` 确实等于 `S1.firstRowId (1) + S1.addedRows (10)`。但我们要注意，这个计算**描述的是结果，而不是过程**。真正的过程是系统去查询了那个全局的 `next-row-id`。

### 总结

- **计算方式**：新快照的 `firstRowId` = 全局 `next-row-id` 的当前值。

- **更新方式**：全局 `next-row-id` += 新快照的 `addedRows`。

因此，`firstRowId` 的分配是一个**基于状态的“取值”过程**，而非一个基于历史的“计算”过程。



## 快照级别的first rowid与数据文件级别的first rowid的作用

这个问题问得非常敏锐，直击了 Iceberg 设计的层次感。你的感觉——“文件级 `first_row_id` 已经够用了，快照级似乎多余”，在**逐行读取（Execution）**这个微观层面是完全正确的。

但是，**快照级的 `first_row_id` 并非用于“逐行计算”，而是用于“宏观决策”**。它的作用主要体现在**写入规划、查询优化和事务审计**这三个更高维度上。如果只有文件级元数据，很多全局操作将变得极其低效甚至不可行。

### 1. 表级 ID 分配的“锚点”（写入侧）

当一个新快照被创建时，系统需要一个全局的“下一个可用 ID”来分配新文件的 `first_row_id`。

- **快照级 `first_row_id`** 就是这个分配过程的**原子记录**。它记录了该事务开始时的起始 ID。

- **作用**：它确保了整个表内 `_row_id` 的全局单调递增。如果没有这个快照级记录，多个并发写入事务将无法协调出一个不冲突的、唯一的 ID 范围。

### 2. 查询规划和元数据“剪枝”（读取侧优化）

这是快照级元数据最重要的性能价值。当执行一个按 `_row_id` 范围过滤的查询（如 `WHERE _row_id BETWEEN 100 AND 200`）时，系统无需读取所有文件的元数据。

- **优化流程**：查询规划器可以先查看快照列表。因为每个快照都记录了其 ID 范围（`first_row_id` 到 `first_row_id + added_rows`），规划器可以**瞬间跳过**那些 ID 范围与查询条件完全无关的快照。

- **作用**：在拥有成千上万个小文件的表中，这能节省大量的元数据读取和文件扫描开销。**文件级 `first_row_id` 告诉你怎么读，快照级告诉你要不要读这个快照下的所有文件**。

### 3. 行级血缘的事务边界（审计与 CDC）

对于 CDC 或数据对账，我们不仅要知道某行存在，更想知道它是在**哪个事务（快照）**中被创建的。

- **场景**：如果行 ID 为 15，你可以确定它属于快照 S2（范围 11-15）。如果行 ID 为 25，它属于另一个快照。

- **作用**：快照级 `first_row_id` 为每一行提供了**创建时间戳的事务上下文**，而文件级元数据只提供了存储位置。这对于审计、增量消费时的断点续传（根据快照 ID 拉取）至关重要。

### 4. 数据重写（Compaction）时的验证

当执行 `OPTIMIZE` 合并多个小文件时，新生成的大文件会包含来自不同原始文件的分散 `_row_id`。

- **作用**：系统需要确保新文件的 `first_row_id` 设置正确（应等于其中最小行的 ID）。快照级元数据记录了表整体的 ID 连续性，可以作为验证重写后数据分布是否合理、是否出现 ID 断裂的重要参照。

### 💎 总结：分层设计

| 层级                     | 存储位置           | 核心作用                          | 类比                         |
| ---------------------- | -------------- | ----------------------------- | -------------------------- |
| **文件级** `first_row_id` | 数据文件（Manifest） | **执行层**：用于逐行计算 `_row_id` 的具体值 | 每本书的**页码**（内部计数）           |
| **快照级** `first_row_id` | 表元数据（Metadata） | **管理层**：用于全局 ID 分配、查询规划、事务溯源  | 图书馆的**采购批次号**（确定书籍来源和入库时间） |

所以，文件级 `first_row_id` 解决了“**怎么算**”的问题，而快照级 `first_row_id` 解决了“**从哪来、要不要读**”的问题。两者分工明确，后者是前者在全局规划和事务管理层面的必要延伸。
