# 向量 + 标量混合查询索引加速设计方案

> 最后更新: 2026-08-19
> 状态: 待评审
> 前置依赖: 标量多列 BTree 索引（多候选择优已合入）、向量 IVFPQ 索引、混合任务组数据面

## 一、背景与问题

### 1.1 混合查询形态

实际业务里最常见的是「相似度 + 属性/时间/分类约束」的组合查询：

```sql
-- 场景1：分类 + 相似度
SELECT * FROM tab
WHERE category = 'electronics'
ORDER BY vector <-> '[0.1, 0.2, ...]'
LIMIT 10;

-- 场景2：时间范围 + 相似度
SELECT * FROM tab
WHERE created_at > '2024-01-01'
ORDER BY vector <-> '[0.1, 0.2, ...]'
LIMIT 10;

-- 场景3：多标量条件 + 相似度
SELECT * FROM tab
WHERE user_id = 123 AND status = 'active'
ORDER BY vector <-> '[0.1, 0.2, ...]'
LIMIT 10;
```

这类查询同时具备向量相似度条件和标量过滤条件，是向量检索与关系过滤的交集场景。

### 1.2 现状行为（基线）

当前一条混合查询的执行链路：

1. **内核识别**：`ORDER BY vector <-> q LIMIT K` 被识别为向量检索请求，得到 Top-K 与 `FetchK`。
2. **FetchK 放大**：`FetchK = TopK × 5`，夹在 [50, 10000]。放大倍数用于缓解「向量检索后过滤」带来的召回损失。
3. **向量索引搜索**：FDW 走向量索引路径（仅此一条），索引引擎对覆盖文件做近似最近邻检索，返回最多 FetchK 个候选。
4. **标量过滤是事后发生的**：标量谓词不进向量检索，只以两种形式兜底——
   - **文件级**：作为表扫描的文件级谓词下推（Iceberg 谓词裁剪），排除不可能匹配标量的数据文件；
   - **行级**：作为 FDW 本地 recheck，在候选行物化后逐行校验。
5. **内核精确重排**：对 FetchK 候选做精确距离计算 + 全局 Top-K。

### 1.3 现状的两个硬伤

**硬伤一：高选择率标量下召回无保证。**

当标量条件很选择性（如 1000 万行里只有 100 行匹配 `category='rare'`），向量检索返回的 FetchK 个最近邻（上限 10000）里可能几乎不含这 100 行中的任何一行——于是最终结果为空或严重漏行，即便数据里明明存在匹配的最近邻。5 倍 overscan 对宽过滤够用，对高选择率过滤完全兜不住。业界对此有明确结论：**post-filter 只适用于宽过滤，高选择率过滤必须预过滤**。

**硬伤二：全部候选行都要物化。**

性能剖析显示查询耗时的主要部分在候选行物化（Parquet 读取 + Arrow 解码）。高选择率标量若能把候选行在物化前大幅收窄，直接命中最大瓶颈。

## 二、方案对比

### 2.1 方案 1：融合索引（索引同时存储向量 + 标量）

**做法**：新建/扩展一种索引，在向量索引的存储里同时带上若干标量列（构建时指定）。查询时向量检索内核对候选向量直接按「随向量存储的标量值」过滤。

**优点**：
- 单索引，检索一次完成，无两阶段；
- 宽过滤也高效：检索时逐向量跳过不匹配向量，不需要物化标量匹配集合；
- 过滤随索引走，无二次索引加载。

**代价**：
- **必须改向量索引的构建、存储格式与序列化**（当前向量索引只存向量 + 数据文件路径 + 行号，不存任何标量列）；
- 标量列在向量索引里冗余一份 → 存储放大，且大表重建成本高；
- 标量列在建索引时固化，想对新的标量列过滤必须重建索引，灵活性差；
- 改动面横跨构建、格式、加载、检索、桥接，工作量最大。

### 2.2 方案 2：双索引 + 标量预过滤（标量索引先出候选行，向量索引只搜候选）

**做法**：复用现有两个独立索引。先跑标量 BTree 索引得到匹配行的候选集合，再让向量检索只在候选集合内出候选。

**优点**：
- **零索引格式改动**：标量索引本来就精确返回匹配行集合（文件路径 + 行号，精确标记）；向量索引本来就以「文件路径 + 行号」标识向量——两者天然可对上；
- **高选择率下可以直接精确**：候选行很少时，无需近似检索，对候选行全量算精确距离即可，召回完美；
- 复用已合入的多候选索引择优，标量侧能力现成；
- 灵活：任意有标量索引的列都能参与，不重建索引。

**代价**：
- 两阶段：先标量、后向量，两次索引访问；
- **候选集合过大的场景（宽过滤）受限检索无收益**，需要回退策略；
- 候选集合需要在引擎内表达并传递。

### 2.3 方案 3（推荐）：标量预过滤内嵌向量检索 —— 按候选集规模三级路由

**核心思想**：不新建索引类型，把「标量预过滤」表达为**一个候选行集合，内嵌进同一次向量检索**；引擎按候选集规模在三种执行形态间自动路由。它是方案 2 的引擎化 + 路由补强，兼顾了方案 1 的「一次检索」和方案 2 的「零格式改动」。

**三级路由**：

| 候选集规模（相对总量） | 执行形态 | 召回语义 | 场景 |
|---|---|---|---|
| **小**（高选择率） | **精确扫描**：对候选行全量算精确距离，取全局 Top-K | **精确**（保证返回标量匹配集内真正最近的 K 行） | `category='rare'`、租户过滤 |
| **中**（中等选择率） | **受限近似检索**：IVF 探测若干簇，簇内逐向量按候选集过滤后入候选堆 | 近似，recall 由探测簇数控制 | `status='active'` 等常见过滤 |
| **大**（低选择率） | **现状**：纯近似检索 + 事后过滤，保留 FetchK 放大兜底 | 近似 | 宽过滤（过滤几乎不裁剪） |

路由依据：标量检索返回的候选行数（精确可得）。候选数少 → 精确；适中 → 受限检索；过大（过滤无收益）→ 回退现状。

**为什么它是「更好的方案」**：

1. **相对方案 1**：不动索引构建/存储格式，无存储放大、无重建成本；高选择率反而更优（精确 vs 近似）。
2. **相对方案 2 字面实现**：不是「先标量、后向量」两个独立阶段，而是**同一次检索内按候选集过滤**，避免候选行集合的中间物化与两次索引加载；且用三级路由解决「候选集过大时受限检索退化」这一方案 2 的固有缺陷。
3. **相对现状**：高选择率场景从「可能空结果」质变为「保证正确」；所有场景候选行都在物化前收窄，命中最大性能瓶颈。
4. **业界验证**：过滤选择率决定策略是生产向量数据库的共识——post-filter 只适合宽过滤；高选择率必须预过滤（否则静默返回空）；中等选择率采用「检索遍历时内联过滤」。本方案的三级路由正是这一共识的工程化落地。

### 2.4 方案对比总表

| 维度 | 方案1 融合索引 | 方案2 双索引预过滤 | 方案3 内嵌过滤+三级路由（推荐） |
|---|---|---|---|
| 索引格式改动 | 大（存储+构建+序列化） | 无 | 无 |
| 高选择率标量 | 近似（探测簇内过滤） | **精确**（候选全量） | **精确**（候选全量） |
| 中等选择率 | 高效 | 受限检索 | 受限检索（同一次检索） |
| 宽过滤 | 高效 | 退化（候选集过大） | 回退现状（无退化） |
| 存储放大 | 有 | 无 | 无 |
| 标量列灵活性 | 差（构建时固化） | 好（任意有索引的列） | 好 |
| 实现工作量 | 最大 | 中 | 中 |
| 与现有组件复用度 | 低 | 高（两索引现成） | 高 |

**结论**：方案 3 为主推方向；方案 2 是它的第一阶段形态（打通受限检索）；方案 1 作为远期演进（服务宽过滤的高效内联过滤，需解决存储放大）。

## 三、推荐方案详细设计

### 3.1 两级裁剪架构

混合查询的标量裁剪分两层，互为补充：

- **第一级 · 文件级（现状，保留）**：标量谓词作为表扫描文件级谓词下推（Iceberg 谓词裁剪），排除不可能匹配标量的数据文件。对向量检索、兜底扫描两条路径都生效，先于行级裁剪把数据文件数量缩小。
- **第二级 · 行级（本次新增）**：标量 BTree 索引在**剩余文件**内精确找出匹配行集合，向量检索只在该集合内出候选。

两级叠加的效果：文件级先砍文件，行级再砍文件内的行。候选行（最终要物化的行）被双重收窄——正是对准「物化是最大耗时」这一瓶颈。

### 3.2 执行流程（引擎内一次检索完成）

```
请求（混合检索配置）
  ├─ 向量侧：向量索引名、查询向量、Top-K / FetchK、探测簇数等参数
  └─ 标量侧：标量索引名、标量表达式（列 / 算子 / 值）
                  │
                  ▼
① 标量检索（精确）
  BTree 索引按表达式精确返回匹配行集合（文件路径 + 行号，精确标记）
                  │
                  ▼
② 按候选集规模路由
  ├─ 小  → ③精确：对候选行全量计算精确距离 → 全局 Top-K
  ├─ 中  → ④受限：IVF 探测若干簇，簇内逐向量按候选集过滤后入候选堆
  └─ 大  → ⑤现状：忽略候选集，纯近似检索 + 事后过滤
                  │
                  ▼
⑥ 与未覆盖文件兜底合并（覆盖段走索引、未覆盖文件走全扫，并入同一结果流）
```

要点：

- **一次引擎调用内完成**：标量检索 → 路由 → 向量检索的编排发生在索引引擎内，FDW 只需在规划期组装混合检索配置，执行期一次调用。避免「FDW 先调标量、再调向量」的两次往返。
- **候选集合的传递**：标量检索产出的匹配行集合（可能很大）在引擎内不落中间存储，直接作为向量检索的过滤条件。
- **正确性兜底不变**：FDW 仍把标量谓词保留为本地 recheck；向量侧输出的 `_distance` 列继续供内核做精确距离 + 全局 Top-K。

### 3.3 三级路由的语义

**精确语义**：混合查询 `WHERE 标量条件 ORDER BY vector <-> q LIMIT K` 的「正确答案」定义为——标量匹配的行中按向量距离最近的 K 行。三级路由中：

- **精确路径（候选集小）保证达到该语义**。这是相对现状的质变：现状在任何选择率下都是近似，且高选择率时连近似都谈不上（可能空结果）。
- **受限路径（候选集中等）**：近似语义，召回由探测簇数与 FetchK 控制；本地 recheck 保证返回的行都满足标量条件（无假阳性），但可能漏真最近邻（假阴性）。
- **现状路径（候选集大）**：维持现有近似语义与兜底。

**路由阈值**：小/中/大的分界由候选行数与探测能力的比值决定（候选行数 ≤ 某阈值 → 精确；候选行数 × 精确距离单位成本 ≥ 受限检索成本 → 受限；候选集占总量比例过高 → 现状）。具体阈值用参数化配置，避免拍脑袋，需基准标定。

### 3.4 与内核向量检索的交互

- 内核侧 **无需改动**。`FetchK` 机制对「受限 / 现状」两条近似路径继续兜底；对「精确路径」，引擎直接返回精确 Top-K，FetchK 放大不再需要（数量上少于 FetchK 也无妨）。
- FDW 在规划期把向量检索与标量预过滤信息合并进同一个混合检索配置，标量谓词同时进文件级谓词与行级预过滤两处。

### 3.5 标量表达式范围

行级预过滤复用现有标量检索的表达式能力（等值 / 范围 / 多列组合），不新增算子。不支持的算子（如空值判断）不进预过滤，留在文件级裁剪 + 本地 recheck。

## 四、分层实现计划

### Phase 1：打通「标量预过滤 → 受限向量检索」主路径

目标：混合查询走上行级预过滤，中等选择率场景正确加速。

1. **引擎**：向量检索请求增加可选的「候选行集合」；IVF / IVFPQ 检索内层循环按候选行集合成员过滤（判断命中后再算距离入堆）；全扫兜底同样过滤。标量检索先行、产出候选集合。
2. **桥接**：混合检索配置从「向量 / 标量二选一」扩展为「向量检索 + 可选标量预过滤」组合表达；标量检索与向量检索在桥接层编排为一次调用。
3. **FDW**：规划期识别混合查询（向量 Top-K 与可下推标量谓词同时存在），并行匹配标量与向量索引，组装混合检索配置；标量谓词同时进文件级谓词与行级预过滤。
4. **验证**：回归测试新增混合查询用例（选择率 × K × 谓词顺序矩阵）；端到端性能基准（同环境 A/B，冷/热分别测）。

### Phase 2：路由增强（精确 + 自适应）

目标：高选择率场景变精确，路由自动。

1. **精确扫描路径**：候选集小 → 对候选行全量精确距离 + 全局 Top-K（引擎需支持「按行号集合取向量并算距离」）。
2. **自适应参数**：受限路径按候选集规模动态放大探测簇数 / FetchK，稳定召回。
3. **路由判定落地**：候选行数由标量检索精确返回，判定逻辑参数化 + 基准标定阈值。

### Phase 3（远期演进）：融合索引

服务宽过滤的高效内联过滤。在向量索引构建时可选携带标量属性列（构建 / 格式 / 序列化扩展），检索内核对候选向量按随索引存储的标量值过滤。需权衡存储放大与重建成本，与 Phase 2 的精确路径互补。**仅当 Phase 1/2 的宽过滤回退现状成为实测瓶颈后再启动**。

## 五、正确性与测试

### 5.1 正确性分层

| 层 | 机制 | 保证 |
|---|---|---|
| 索引检索 | 候选集过滤 / 精确距离 | 不产生假阳性（返回的行必满足标量条件） |
| 本地 recheck | FDW 保留原始谓词 | 最终语义正确性的最后防线 |
| 内核精确重排 | 精确距离 + 全局 Top-K | 排序正确 |

### 5.2 测试场景

回归测试覆盖（选择率 × 组合）：
- 高选择率：匹配行极少，验证**精确路径**返回正确 Top-K（相对「标量匹配集内的真实最近邻」）。
- 中等选择率：验证受限检索召回（对照精确 Top-K 的 recall@K）。
- 低选择率：验证回退现状、结果与纯 post-filter 一致。
- 谓词顺序 / 建索引顺序 / 多候选并存（与多候选择优叠加）下的路由确定性。
- 边界：候选集为空（返回空）、候选集恰为 Top-K、单文件 vs 多文件、部分覆盖（未覆盖文件兜底）。

### 5.3 性能基准方法

- 同环境 A/B：现状（post-filter）vs 预过滤路径，固定索引类型、探测簇数、DOP、数据规模。
- 冷/热分别测：冷启动（重启 + 清缓存 + 单次执行）、热查询（预热后计时），避免预热掩盖差异。
- 结果正确性用查询向量来源 + 基准答案（GT）校验 recall。
- 指标注明测试条件（规模、维数、选择率、K、探测簇数）。

## 六、风险与对策

| 风险 | 描述 | 对策 |
|---|---|---|
| 候选集过大 | 宽过滤下受限检索退化 | 三级路由回退现状（Phase 1 即可带回退） |
| 受限检索召回不稳 | 匹配行在探测簇内稀疏时漏检 | 自适应放大探测簇数 / FetchK；高选择率直接走精确路径 |
| 双索引一致性 | 标量与向量索引覆盖不同快照 | 沿用现有覆盖规划与兜底机制，未覆盖文件全扫兜底 |
| 计划期开销 | 规划期同时匹配两个索引 | 复用既有索引发现（一次匹配返回全量），不逐谓词 I/O |
| 阈值拍脑袋 | 路由阈值无依据 | 参数化 + 基准标定，默认保守（宁走受限不走精确回退） |

## 七、与既有设计文档的关系

本方案取代目录下既有的两份混合查询文档（「方案 A（Pre-filter）」「统一方案」）。它们的方向正确（行级候选集过滤），但存在与当前实现不一致之处：

- 描述的检索编排接口形态基于已退役的旧直连架构，与当前「索引发现 + 混合任务组数据面」不一致；
- 部分接口与检索入口为假想形态，与现有引擎的实际接口（向量检索请求不含过滤字段、向量/标量在桥接层二选一）对不上；
- 查询语法示例与内核实际识别形态（`ORDER BY vector <-> q LIMIT K`）不符；
- 未覆盖「选择率决定策略」这一核心路由语义，仅提到「候选集过大回退」。

本文档以当前架构为准，给出可落地的三级路由设计。既有文档可作为方案 1（融合索引）演进的素材。
