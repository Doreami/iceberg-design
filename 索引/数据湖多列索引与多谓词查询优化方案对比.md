## 〇、结论先行：四条技术路线一图速览

多谓词查询（`WHERE a = 1 AND b > 2`）的优化，业界可归为**四条路线**：

| 路线                 | 代表                           | 复合索引     | 前缀限制  | 裁剪粒度   |
| ------------------ | ---------------------------- | -------- | ----- | ------ |
| **A 文件级剪枝**        | Hudi / Delta / Iceberg / Doris / StarRocks / ClickHouse / CarbonData | ⚠️ 部分/规划 | 无（Hudi 部分） | 文件/块级 |
| **B 独立列索引 + 集合运算** | LanceDB / Paimon(生产) / Databend | ❌(独立列)   | 无     | 行级     |
| **C 字典序复合索引 + 前缀** | **本仓库**（gaussdb + Iceberg）；CarbonData MDK 为文件内变体 | ✅        | **有** | 行级     |
| **D 空间索引 / 布局**    | Qbeast OTree / Delta Z-Order | ⚠️（Qbeast ✅；Z-Order 是布局非索引） | 无 | 数据块/文件 |

各路线核心思想与关键代价见 §一（A=文件统计跳过无关文件、B=行号集求交/并集、C=复合键最左前缀定位、D=空间曲线物理相邻）。

**核心判断（贯穿全文）**：

1. **前缀复合索引不是过时方案**——"字典序复合 + 最左前缀"是关系型数据库（PostgreSQL/SQL Server/Oracle）在**本地表存储**上验证几十年的标准设计；但这些库**没有湖表索引能力**（不索引 Iceberg/Parquet 这类数据湖表）。本仓库是把同一**设计原则**移植到 **Iceberg 湖表场景**（gaussdb FDW + 自研索引引擎），而非对标任何产品的索引能力。本文对比的**数据湖产品**（LanceDB / Hudi / Iceberg 社区 / Delta / Paimon / Qbeast）里"看起来都是独立索引"，是因为它们**大多还没做行级复合索引**（LanceDB 规划中、Hudi 文件级为主、Iceberg 在讨论）——我们虽是 Iceberg 湖表实现，却证明了这并非必然：**行级复合索引在湖表上完全可以落地**（§2.7）。
2. **复合索引与"两个单列索引 + 求交"互补，不是替代**——复合赢在"复合谓词单趟裁剪、不受单列选择率拖累"；单列求交赢在"任意列组合、无前缀限制"。关系型数据库两种都要（设计原则），我们应同样两者支持、规划器择优（详见 §四）。

## 一、问题背景：多谓词查询要解决什么

`WHERE a = 1 AND b > 2` 的加速难点：

- 单列索引只能命中一个谓词，另一谓词要引擎外逐行 recheck；
- 复合索引（若支持）可对 `(a, b)` 键区间一次裁剪；
- 独立多索引则要查多个索引再求交。

四条路线是在"裁剪粒度 / 是否需预测查询 / 写路径代价 / 前缀限制"四个维度上的不同取舍。

### 路线 A：文件级剪枝（严格说不是"索引"）

不建任何索引结构，靠**每数据文件每列的 min/max/null 统计**（manifest 元数据，或布隆过滤），查询逐谓词跳过不含目标值的文件；多谓词 = 各谓词剪出的文件集合取交集。

> **同类代表**：Hudi / Delta / Iceberg 社区 / **Doris、StarRocks（ZoneMap，文件/页 min/max）、ClickHouse（跳过索引 minmax/bloom）、CarbonData（min/max，blocklet 级）**——都是文件/块级跳过，无独立索引结构；其中 Doris/StarRocks 还在其上叠加了二级索引（倒排/位图/Bloom），属"路线 A 第一层 + 精确索引第二层"的组合。

> **澄清**：这本质是**元数据级文件跳过（data skipping）**，不是传统意义的索引——没有独立索引结构，只决定"读哪些文件"，存活文件内部仍全扫；不提供行级定位。但它是天然免费、对所有列生效的第一层裁剪（写路径近零侵入），代价是粒度粗。有些产品在它之上还叠加真索引（Hudi 的 Record/Secondary/Bloom 即行/值级索引）。

**多谓词执行（以 `WHERE a=1 AND b>2` 为例）**：

- 每个文件 F 都带**所有列**的统计，如 F：`a∈[0,100], b∈[1,50]`。
- 逐谓词对 F 检查：`a=1 ∈ [0,100]`？是；`b>2 ∩ [1,50]`？是 → F 存活；**任一谓词排除 F** → 直接跳过。
- AND = 各谓词存活文件集的**交集**；OR = **并集**。
- 存活文件**全扫**，谓词作为过滤条件逐行应用——文件级检查只是"读不读"的决策，没有行级候选集合，也无"索引返回超集再过滤"这回事。
- 效果取决于文件分布：文件多且范围紧（配合 Z-Order/列式聚类）→ 剪得准；文件大且范围松 → 近乎全扫。

- 优点：引擎无关、开放格式、写路径近零侵入、任意列可剪（不需预测查询）。
- 缺点：文件级粒度，文件内大量不命中行仍要读。

### 路线 B：独立列索引 + 集合运算

为每个过滤列建**独立行级索引**，查询各列索引分别得到行号集合，再做 **AND（交集）/ OR（并集）**。

> **同类代表**：LanceDB（BTree/Bitmap/LabelList）、Paimon 生产（每列独立 BTree）、**Databend（Inverted Index，Lucene 类）**——都是每列独立索引 + 集合运算。

**多谓词执行（以 `WHERE a=1 AND b=2` 为例）**：

- 分别查索引 (a) 得行号集 A，索引 (b) 得行号集 B。
- AND → `A ∩ B`；OR → `A ∪ B`；范围谓词（`b>2`）照常走单列索引得到范围行号集。
- **代价 ∝ 两个集合的大小 × 求交成本**：低选择率列（如 `a=1` 命中 50% 行）会返回巨大集合，求交开销随集合规模上升——这是它相对复合索引的核心短板。
- 无前缀限制：任意列组合都能查（每列都有自己的索引）。

- 优点：任意列组合可走索引（无前缀限制）；索引类型可按列特征选。
- 缺点：大结果集求交/并集开销；复合范围（`a=1 AND b>2`）无法单趟定位，要分别查再相交。

### 路线 C：字典序复合索引 + 前缀匹配

复合键 `(a,b,c)` 按字典序排序，查询利用**最左前缀**：连续等值列 + 首个范围列用于定位，其余列页内过滤。

> **同类代表**：本仓库（gaussdb + Iceberg 行级复合 BTree，§2.7）。**文件内复合键变体**：**CarbonData 的 MDK（多维键）** 是文件内复合排序键 + min/max 统计（blocklet 级跳过）——但它作用于文件内排序/统计，**非行级精确定位**，与我们的行级复合索引不同层次。

**多谓词执行（以 `WHERE a=1 AND b>2` 为例，索引 (a,b)）**：

- **前缀定位**：`a=1` → 等值列 `lo = hi = 1`；`b>2` → 首个非等值列，收拢 b 的下界 → 得到复合键区间 `[(1, 2⁺), (1, +∞)]`。
- **二分页面**：页面按复合键 `max_key` 单调排序，二分定位到该区间覆盖的页面范围。
- **页内过滤**：对页面逐行做多列 mask（`a=1 AND b>2`），输出命中的行地址。
- 复合谓词**一次扫描**完成裁剪；**非前缀**（`WHERE b=2`）在路由期即被拒绝、退化为全扫描（字典序复合索引的固有性质）。
- 正确性由"引擎返回保守超集 + 调用方本地过滤"两层保证。

- 优点：复合谓词**单趟范围裁剪**；一次排序一次扫描。
- 缺点：非前缀谓词（`WHERE b=2`）退全扫描；键列需按查询模式设计。

### 路线 D：多维空间索引 / 数据布局

把多列值映射空间曲线（OTree 递归划分 / Z-order），相近值物理相邻，查询裁剪空间子树/文件，**无前缀限制**。

**多谓词执行（以 `WHERE a=1 AND b>2` 为例，OTree(a,b)）**：

- 把 `a=1`、`b>2` 映射到 (a, b) 二维空间，成为一组约束超平面。
- 从 OTree 根递归裁剪：跳过与约束不相交的空间子树/Cube，只读相交 Cube 中的数据。
- **无前缀限制**：任意列组合的谓词都能参与空间裁剪（不依赖列顺序）。
- 粒度是"空间块/Cube"，块内仍要读；配合 Z-Order/布局能让文件范围更紧、文件级跳过更准。

- 优点：任意列组合受益，布局一次生效。
- 缺点：写入/重写成本（递归划分、OPTIMIZE）；块/文件级，非行级精确。

## 二、各产品详解

### 2.1 LanceDB — 独立索引 + 集合运算（路线 B）

**索引哲学**：向量优先的嵌入式数据库，标量过滤服务于向量检索。

**实现方案**：

- 标量索引：**BTREE**（高基数列）、**BITMAP**（低基数列）、**LABEL_LIST**（数组列），每列独立。
- 多谓词处理：每个过滤列各自走索引得行号集合，再做交集/并集。
- 混合查询：标量索引可与向量/全文组合，支持**预过滤**（先标量后向量）与**后过滤**（先向量后标量）。

**物理存储**：Lance 列式格式，数据分段，段内列式，配套列统计元数据；MVCC；后台 Compaction。

**多列索引支持**：

| 维度                  | 说明                                                                                         |
| ------------------- | ------------------------------------------------------------------------------------------ |
| 复合索引                | ❌ **不支持**。官方文档：索引 `columns` "currently always an array of size 1…future there may be more" |
| "composite index"一词 | ⚠️ 在 LanceDB 指 **IVF-PQ**（单列向量 = IVF 分桶 + PQ 量化），**不是多列**                                  |
| 多索引创建               | ✅ 不同列可建不同类型索引                                                                              |

**优劣势**：

| 优势              | 劣势                       |
| --------------- | ------------------------ |
| 实现简单直接，易理解易用    | 不支持真复合索引，多条件需多次索引查找      |
| 索引类型丰富，可按列特征选   | **多谓词求交开销**：两个结果集都大时交集昂贵 |
| 与列式存储深度集成、零拷贝   | 复合索引仍在规划，方向不确定           |
| 向量检索标量预/后过滤场景成熟 | 主要面向向量场景，复杂分析能力有限        |

**小结**：路线 B 代表，用"多索引 + 求交"规避复合索引复杂度，代价是求交开销与无单趟复合裁剪。

### 2.2 Apache Hudi — 多模式索引子系统（路线 A + 少量行级）

**索引哲学**：多模式索引（Multi-Modal Index）子系统，索引作为元数据表（Metadata Table）的分区独立存储。

**索引类型体系**：

| 类型                | 适用场景   | 原理                       |
| ----------------- | ------ | ------------------------ |
| 文件索引（Files）       | 基础文件裁剪 | 文件列表 + 分区映射              |
| 列统计（Column Stats） | 范围谓词   | 每文件每列 min/max/null count |
| 布隆过滤器（Bloom）      | 高基数列等值 | 判断"不可能存在"，跳过文件           |
| 记录索引（Record）      | 主键等值   | record key → 文件位置        |
| 二级索引（Secondary）   | 非主键等值  | 列值 → record key → 文件位置   |
| 表达式索引（Functional） | 函数变换谓词 | 对变换列建索引                  |

**多谓词执行**：谓词下推，各索引分别**文件级裁剪**，文件列表取交集，仅扫命中文件。

**物理存储**：元数据表为 MOR Hudi 表（HFile 格式），每索引类型一个分区；数据为 Parquet，更新追加日志。

**多列索引支持**：⚠️ 部分——`CREATE INDEX` 可为多列建索引但每列独立配类型；记录索引支持多主键复合；复合记录索引"不要对第一个键做前缀查找"。

**优劣势**：

| 优势             | 劣势                |
| -------------- | ----------------- |
| 索引体系最丰富（8+ 类型） | 子系统复杂，运维理解成本高     |
| 文件级裁剪对任意谓词生效   | 行级复合能力弱，多列仍是多单列组合 |
| 异步/同步构建，事务性更新  | 元数据表本身也是表，有存储开销   |
| 宣称最高 30× 提升    | 行级精确定位有限          |

**小结**：路线 A 集大成者，覆盖广但行级复合弱。

### 2.3 Apache Iceberg（社区）— 元数据剪枝 + 规划中 Puffin（路线 A）

**索引哲学**：开放格式、引擎无关，当前靠元数据剪枝 + 数据布局；二级索引尚在社区讨论。

**现有优化手段**：分区剪枝（按分区列跳过分区）、清单文件过滤（每文件统计）、列统计剪枝（min/max 跳文件）、Z-Order（空间曲线物理排序）。

**多谓词执行**：一条三级裁剪链——先按分区谓词跳过分区，再在清单层用每文件统计逐谓词检查（任一谓词排除即跳过文件），最后对存活文件做列统计/布隆再剪一次；存活文件全扫逐行过滤（同路线 A 机制，文件层 AND）。

**规划中的二级索引**：Phase 1 单列布隆过滤器（存 Puffin 文件，零修改写入、快照作用域、建议性）；Phase 2+ 探索 B-Tree/全文/向量。另有一个 **B-Tree/Covering Index 提案**（[Iceberg 社区索引讨论](https://dev.to/morningman/how-hard-is-it-to-add-an-index-to-an-open-format-lessons-from-the-apache-iceberg-community-5gcf)）——目标是直接定位行（跳过主表访问），存储建议用物化视图表或专用结构（而非 Puffin），**与我们的行级复合 BTree 思路一致，但仍在提案阶段未落地**。

**物理存储**：三层元数据（元数据文件 → 清单列表 → 清单文件每文件 min/max/行数）；Puffin 为容器文件（任意 Blob + LZ4 JSON Footer），GreptimeDB 已用它存倒排索引。

**多列索引支持**：⚠️ 规划中——Phase 1 仅单列布隆，多列复合后续讨论。

**优劣势**：

| 优势               | 劣势                       |
| ---------------- | ------------------------ |
| 开放标准、引擎无关、设计审慎   | 二级索引讨论/规划阶段，生产可用性有限      |
| Puffin 灵活，可存任意索引 | Phase 1 仅单列布隆，多列待定       |
| 快照隔离 + 时间旅行完备    | 当前多列优化靠 Z-Order + 统计，非行级 |
| 社区活跃、未来可期        | 索引生态成熟度低于 Hudi           |

**小结**：路线 A"元数据剪枝派"，二级索引早期；与本仓库已落地的行级复合索引相比尚在探索。

### 2.4 Delta Lake — Data Skipping + 数据布局（路线 A + D）

**索引哲学**：不建传统索引，用自动列统计 + 数据布局优化文件裁剪。

**实现方案**：

- **Data Skipping**：写入自动收集每文件每列 min/max/null count，查询超范围跳过文件。
- **Z-Ordering**：`OPTIMIZE ... ZORDER BY (col1, col2, …)` 编码 Morton 空间曲线并物理排序，收紧文件统计。
- **Liquid Clustering**：Databricks 新一代布局，灵活列选择、增量优化、免全表重写。

**物理存储**：事务日志 `_delta_log/`（每 commit 一个 JSON）+ Parquet 数据文件 + 每文件统计。

**多谓词执行**：与路线 A 一致——对每个谓词查文件统计（min/max/null），任一谓词排除即跳过；Z-Order/Liquid Clustering 让文件范围更紧、跳过更准；存活文件全扫逐行过滤。

**多列索引支持**：❌ 不支持传统复合索引（Z-Order/Liquid Clustering 替代）；`DataSkippingNumIndexedCols` 控制统计列数；Z-Order 不受前缀限制。

**优劣势**：

| 优势                      | 劣势                   |
| ----------------------- | -------------------- |
| 自动化高、运维简单、写路径近零侵入       | 没有传统行级复合索引           |
| 统计对任意列生效（不需预测查询）        | 文件级裁剪，粒度粗            |
| Z-Order 对多种查询模式有帮助      | Z-Order 需定期 OPTIMIZE |
| Liquid Clustering 灵活、增量 | 开源版功能不及商业版           |

**小结**：路线 A+D，用"布局 + 统计"让文件尽量小、统计尽量紧，绕过索引复杂度。

### 2.5 Apache Paimon — 文件 + 全局两级索引

**索引哲学**：文件索引 + 全局索引两级，全局索引支持行级精确过滤。

**文件索引**：每数据文件一个索引文件，可含 BloomFilter/Bitmap/B-Tree 等，支持多列配置。

**全局索引（Data Evolution 表）**：BTree（标量）、Bitmap（枚举）、Vector（ANN）、Full-Text（Lucene）、Hybrid Search（多路由融合）。

**多列复合索引**：

| 维度    | 说明                                                                                                                                                           |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 生产多列  | ⚠️ **每列独立 BTree，非复合**。`global-index.btree.index-column='id,name'` = 每列各建一个单列 BTree（官方："each column gets an independent BTree index — not a composite index"） |
| 真复合框架 | ⚠️ **开发中（PR #7933）**：multi-column GlobalIndex SPI，"主-辅字段"概念，未发布                                                                                              |
| 多谓词执行 | 每字段 BTree 查询独立执行（PR #7951 并行线程池），再 AND/OR 集合运算                                                                                                               |
| 前缀限制  | ❌ 无——**因为它没有字典序复合键**（每列独立可查），本质是路线 B                                                                                                                         |

**优劣势**：

| 优势                | 劣势                                  |
| ----------------- | ----------------------------------- |
| 文件 + 全局两级，体系灵活    | 真复合（Lucene 多字段）仍在开发                 |
| 全局 BTree 行级精确，类型多 | 配置复杂，学习曲线陡                          |
| 任意列组合可走索引（无前缀限制）  | **多谓词靠求交**：大结果集相交贵，复合范围无法单趟         |
| 支持全文 + 向量混合       | 全局索引仅限 Data Evolution（Append-Only）表 |

**小结**：生产 = 路线 B（独立列 + 集合运算）；真复合还在开发。**"非前缀也能走索引"正是因为它没有复合键**——与我们的字典序复合是不同架构。

---

### 2.6 Qbeast — OTree 多维空间索引（路线 D）

**索引哲学**：多列视为多维空间，OTree 递归空间划分组织数据，查询裁剪空间子树。

**实现方案**：

1. 数据归一化：索引列值映射 [0,1]（数值 linear、字符串 hash）。
2. 空间映射：每行 = n 维空间一个点。
3. 递归划分：n 维空间递归分为 **2^n 个等大小不重叠 Cube**，超容量（`desiredCubeSize`）继续对半切。
4. 树形组织：Cube 构成 OTree，每 Cube 存实际数据。
5. 自动列选择：`columnsToIndex.auto=true` 时算相关性矩阵，选**平均相关性最低的 top N 列**。

**多谓词执行**：把各谓词映射到 n 维空间约束 → 从 OTree 根递归裁剪不相交的空间子树 → 只读相交 Cube 内的数据；无前缀限制、任意列组合（详见路线 D 执行细节）。`columnsToIndex` 决定维度数；"2–5 维"是软性建议非硬限制。

**物理存储**：OTree 元数据作为 Delta Log 扩展（Revision 记录空间划分），数据按空间划分物理分布；底层可用 Delta/Iceberg。

**多列索引支持**：✅ 原生多维（`columnsToIndex`）；多索引创建 ✅；无前缀限制。

**优劣势**：

| 优势                    | 劣势         |
| --------------------- | ---------- |
| 专门为多维过滤设计，理念独特        | 社区小、生态不成熟  |
| 任意列组合受益，无前缀限制         | 主要面向 Spark |
| 可插拔在 Delta/Iceberg 之上 | 维护更新开销需评估  |
| 支持高效数据采样              | 块级裁剪，非行级精确 |

**小结**：路线 D 代表，用空间划分换"无前缀 + 任意列组合"，代价是写放大与生态局限。

### 2.7 本仓库实现：gaussdb + Iceberg 前缀复合 BTree 索引（路线 C）

> 选型参考 [多列BTree索引设计方案.md](多列BTree索引设计方案.md)。

**索引哲学**：**字典序复合索引**（关系型数据库经典设计）——`CREATE INDEX (a,b,c)`，键按复合键字典序排序，查询利用**最左前缀**。本实现是 gaussdb 上为 Iceberg 数据湖自研的行级复合索引，而非数据湖常见的"独立索引替代"。

**架构与数据流**：

```
openGauss 查询
  └─ iceberg_fdw: 一次 match_index 探测 → 前缀可用性判定 → 收集同索引谓词（表达式 JSON 数组）
       └─ iceberg-rust-bridge: 透传表达式数组
            └─ iceberg-index 引擎
                 ├─ 构建: 逐列读键 → CompositeKey → 排序 → 分页 → Lookup v2 落盘（Puffin segment）
                 └─ 搜索: locate_bounds（前缀定位）→ locate_composite（二分页面）→ 多列 mask
                                                                    → 候选行地址 → FDW 本地 recheck 兜底
```

**复合索引实现要点**：

- **复合键**：`CompositeKey(Vec<ScalarValue>)`，逐分量字典序（长度收尾为完备性规则，防御性）。单列 = 1 元素复合键，**无独立代码路径**。
- **键参数**：`key_columns`（数组，顺序 = 排序优先级），替代旧 `key_column`。
- **存储**：数据页**每键列一个 Arrow 数组** + 行地址；Lookup v2（`NumKeyColumns` 参数化）。
- **前缀语义**：`locate_bounds` 等值列 lo=hi → 首个非等值列合并 bounds → 后续列全范围；`locate_composite` 按 max_key 二分，**结果恒为保守超集**。
- **页内过滤**：`build_filter_mask_multi` 列内 AND + 跨列 AND。
- **FDW 路由**：`match_index` 一次探测 → 首列命中判定 → **前缀可用性判定**（首列无谓词拒路由）→ 恒本地 recheck。
- **分区表**：按分区分段（`PartitionGroup`），覆盖分区走索引、未覆盖 `full_scan_scalar` 回退；分区谓词文件裁剪在 coverage 层，与键结构正交。

**多列索引支持**：

| 维度    | 说明                                                    |
| ----- | ----------------------------------------------------- |
| 复合索引  | ✅ 支持（字典序复合 + 前缀匹配）                                    |
| 单列索引  | ✅ 即 N=1 复合键，统一路径                                      |
| 多索引创建 | ✅ 单列/多列任意并存                                           |
| 前缀限制  | ⚠️ **有**——`WHERE b=2` on `(a,b)` 退全扫描（字典序复合索引的固有性质） |
| 多谓词执行 | 复合谓词**单趟**范围裁剪 + 多列 mask，非求交                          |
| 裁剪粒度  | **行级**（页内逐行）                                          |

**优劣势**：

| 优势                                   | 劣势                             |
| ------------------------------------ | ------------------------------ |
| 复合谓词单趟范围裁剪，无求交开销                     | **前缀限制**：非前缀退全扫描               |
| 行级精确过滤，比文件级细                         | 键列需按查询模式设计（预测会查的列）             |
| 单列/多列统一实现，无特判                        | 多候选索引 first-match 择优问题（跟踪 #38） |
| 与 gaussdb 深度集成（FDW 路由 + recheck 双保险） | 索引维护依赖自研引擎，非开放格式通用             |

**定位小结**：gaussdb 上为 Iceberg 数据湖自研的行级字典序复合索引（路线 C）。对比路线 B——赢在"复合谓词单趟、无求交"，代价是"前缀限制、需预测键列"；对比路线 A/D——行级精确 vs 文件/布局级（粗但无需预测查询）。

## 四、核心设计题：复合索引 vs 两个单列索引（求交）

这是读完前文最自然的疑问：**"建两个单列索引是不是也能做多谓词优化？那复合索引还有什么必要？"** 分三层回答。

### 4.1 能建：我们的系统本来支持多索引并存

单列索引 = N=1 复合键，`CREATE INDEX (a)` 与 `CREATE INDEX (b)` 可同时建。这点没问题。

### 4.2 能不能"用"：我们的搜索路径目前**没有求交能力**

当前搜索是 **first-match 选一个索引 + 本地 recheck**：

```
WHERE a=1 AND b=2，索引 (a)、(b) 并存
  → 探测先命中 (a) → 用 (a) 查 a=1 候选行地址 → b=2 由 FDW 本地 recheck 逐行过滤
```

**结果正确**（recheck 兜底），但 **(b) 索引完全没用上**——a=1 候选集多大就得读多少行再 recheck。要兑现"多索引优化"，需新增 **BitmapAnd 式求交路径**（分别查 (a)、(b) 行号集求交），这是**新功能**，目前没有。

### 4.3 值不值得：两者互补，关系型数据库两种都有

| 场景                        | 两个单列索引    | 复合索引 (a,b)      |
| ------------------------- | --------- | --------------- |
| `a=1 AND b=2`（高选择率）       | ✅ 小集合求交   | ✅ 直接定位          |
| `a=1 AND b=2`（**a 低选择率**） | ⚠️ 大集合求交贵 | ✅ **不受单列选择率拖累** |
| `a=1 AND b>2`（复合范围）       | ⚠️ 范围集合求交 | ✅ 单趟裁剪键区间       |
| `b=2`（非前缀）                | ✅ 直接用 (b) | ❌ 退全扫描          |
| `ORDER BY a, b`           | ❌ 需排序     | ✅ 走索引序          |

**关键在"a 低选择率"行**：复合索引的裁剪由**复合选择率**决定，不受单列选择率拖累；两个单列索引在低选择率列上会返回巨大集合再求交，反而更慢。这正是关系型数据库（PostgreSQL 的 BitmapAnd）同时提供单列与复合索引的原因——**它们互补，不是替代**。（注：PostgreSQL 的索引作用在其本地表，此处仅作**设计原则**参考，非湖表能力对标。）

### 4.4 对本仓库的启示

- **理想状态**：复合索引 + 单列索引（求交）**两者都支持，规划器择优**——复合赢"高相关性复合谓词单趟裁剪"，单列求交赢"任意组合、无前缀限制"。
- 这是 **#38 多候选择优的延伸**：候选不只是"多个复合索引"，还应有"多个单列索引求交"。也是本文 §5.2"可借鉴 Paimon 独立列 + 并行求交"的落地方向。
- 现状认知：我们的前缀复合是"已落地"的能力；独立列求交是"待补"的能力。两者并存后，`WHERE b=2`（非前缀）也能走 (b) 索引，前缀限制的痛点就消解了。

## 五、选型建议

### 5.1 各路线适用场景

- **路线 A（文件级）**：分析型、查询发散、无法预测键列、强调写路径零侵入。适合"海量文件 + 粗粒度剪枝已够用"。
- **路线 B（独立列 + 求交）**：查询组合发散、需任意列可查、接受求交开销。适合向量检索的标量预过滤。
- **路线 C（字典序复合）**：复合谓词有明确模式（如 `(a,b)` 常一起查）、追求行级单趟裁剪。适合 OLTP 风格精确过滤。
- **路线 D（空间索引/布局）**：多列组合查询受益面广、可接受重写成本。适合分析型多列布局。

### 5.2 本仓库的定位与可借鉴点

- **定位**：gaussdb（openGauss）上为 Iceberg 数据湖自研的行级复合索引（路线 C）。**独特优势**：复合谓词单趟行级裁剪（各数据湖方案没有）。**真实短板**：前缀限制、需预测键列、多候选择优（#38）。

- **竞争格局印证**：目前湖表场景下**没有第二个做到"行级 + 字典序复合 + 前缀"三合一**的——Databricks 的行级二级索引是**单列**（最多 4 个独立索引，路线 B）；Iceberg 社区的 B-Tree/Covering 提案与我们的思路一致但**未落地**；Doris 前缀索引是复合但**块级稀疏**。我们是这条组合路线的先行者。

- **可借鉴（缓解短板）**：
  
  1. **Paimon 独立列 + 并行求交**（PR #7951）：补"独立列索引 + 求交"路径，与复合索引并存、规划器择优——直接消解前缀限制痛点，也缓解 #38。
  
  2. **Hudi/Delta 文件级统计**：作为第一层裁剪天然免费（每文件 min/max），先剪文件再走索引。
  
  3. **Qbeast/Z-Order 布局**：若常按某几列组合扫描，用空间布局让文件更紧，提升文件级跳过。
  
  4. **CarbonData 的 blocklet 级 min/max + 复合键排序**：把文件级裁剪**下沉到文件内数据块**（对分析型大文件尤其有效），与我们的复合键排序结合。
  
  5. **Doris 的两层索引组合**（ZoneMap 文件级第一层 + 倒排/位图精确第二层）：验证我们"文件统计第一层 + 行级复合索引第二层"的方向，可参考其对"任意列文件级跳过 + 按需精确索引"的取舍。

## 附录：Puffin 容器格式与本仓库实现

> 本仓库的**路线就是 gaussdb + Puffin**——`iceberg-index` 的 B-Tree segment 直接用 Puffin 文件落盘，不走 Iceberg 社区"自研二级索引"的规划路线。本附录说明 Puffin 容器格式与本仓库的落地方式。

### A.1 Puffin 是什么

Iceberg 官方**容器文件格式**，存 Manifest 放不下的索引/统计。任意 Blob（布隆、倒排、向量、统计）、自描述 Footer（LZ4 压缩 JSON）、快照绑定、引擎无关。结构：`Magic + Blob₁…Blobₙ + Footer`。

### A.2 本仓库实现：B-Tree segment 即 multi-blob Puffin

`iceberg-index` 的 `plugins/btree/segment.rs` 直接定义 **"B-Tree segment file — multi-blob Puffin v1 wrapper"**：

| 项          | 值                                                                                                         |
| ---------- | --------------------------------------------------------------------------------------------------------- |
| Blob 0     | **Lookup v2**（`blob_type = "huawei.gauss-infra.btree.lookup-v1"`）——页目录（min/max 键 + 文件表 + KeyTypes），见 §2.7 |
| Blobs 1..N | **数据页**（`blob_type = "huawei.gauss-infra.btree.data-v1"`）——每页一个 Arrow RecordBatch（键列 + 行地址）               |
| Blob 元数据   | `fields` 携带构建时的 **field_ids**（运行时 field_id→列映射的来源，保证与构建一致）                                                |
| 懒加载        | 数据页按 `read_blob` 按需加载（`page_blob_indices`），避免整段读入                                                         |
| Puffin 解析  | 由存储 adapter 处理，segment 只做 blob 分类与读取                                                                      |

即：我们已实现 **Puffin 容器 + 自定义复合 BTree Blob**（Lookup v2 + 多列数据页），并利用 Puffin 的 multi-blob + 懒加载能力。

### A.3 Puffin 的通用性：一个容器可存多种索引

| 索引类型                          | 实现者                          | 状态      |
| ----------------------------- | ---------------------------- | ------- |
| 布隆过滤器                         | Iceberg 社区 Phase 1           | 规划中     |
| 倒排索引                          | GreptimeDB                   | 已落地     |
| 向量索引                          | Puffin-Backed Vector Indexes | 研究      |
| 删除向量                          | Iceberg 官方                   | 已落地     |
| **复合 BTree（Lookup v2 + 数据页）** | **本仓库**                      | **已落地** |

Puffin 是**容器**而非索引本身——Blob 类型由实现者自定义并版本化，这正是本仓库 `huawei.gauss-infra.btree.*-v1` 的命名依据。
